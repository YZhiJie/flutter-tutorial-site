状态管理入门 ​

学习目标 ​

学完本章，你将能够：

  • 理解 StatefulWidget 的局限：状态只能在当前 Widget 子树内访问
  • 掌握 InheritedWidget 机制：Theme / MediaQuery / Navigator 背后的通用方案
  • 使用 Flutter 内置的状态提升（State Lifting）模式
  • 了解主流状态管理框架（Provider / Riverpod / Bloc）各自的定位与选型

核心问题

当状态需要跨多个 Widget（甚至整个应用）共享时，把状态放哪儿？ 这就是状态管理要解决的问题。

StatefulWidget 的局限 ​

StatefulWidget 的状态封装在 State 对象里，只有当前 Widget 及其直接子组件能访问。如果两个兄弟 Widget 需要共享状态（比如计数器页面和统计页面都要读到计数值），单纯靠 StatefulWidget 就很别扭。

解法一：状态提升（Lifting State Up）——把共享状态放到两个 Widget 的最近公共父节点，再通过构造参数向下传递。这在层级浅时很干净，但层级深起来会导致大量中间 Widget 需要接收并透传这些参数，叫「参数钻探（prop drilling）」。

解法二：InheritedWidget——让子 Widget 按类型从上下文中直接读取状态，不用逐层传参。

InheritedWidget：Flutter 内置的跨树共享机制 ​

这是 Flutter 里最基础的跨 Widget 树数据共享方案。你平时频繁使用的 Theme.of(context)、MediaQuery.of(context)、Navigator.of(context) 背后就是 InheritedWidget。

它的原理：父 Widget 在树上挂一个 InheritedWidget，子 Widget 可以在任意深度用 context.dependOnInheritedWidgetOfExactType<T>() 拿到它，框架会自动把它们的依赖关系记录下来——当 InheritedWidget 数据变化时，所有依赖它的子 Widget 会自动重建。

运行示例
DartPad 运行环境将在滚动到此处时加载…

这里封装了一个简单的 CounterScope（继承 InheritedWidget），两个子 Widget _CounterDisplay 和 _IncrementButton 分别从 context 读取共享状态，不需要任何参数传递。

查看完整源码
dart
import 'package:flutter/material.dart';

// InheritedWidget：最简单的跨 Widget 数据共享方式
// Theme.of(context) / MediaQuery.of(context) 背后就是这个机制

class CounterScope extends InheritedWidget {
  final int count;
  final VoidCallback increment;

  const CounterScope({
    super.key,
    required this.count,
    required this.increment,
    required super.child,
  });

  static CounterScope of(BuildContext context) {
    return context.dependOnInheritedWidgetOfExactType<CounterScope>()!;
  }

  @override
  bool updateShouldNotify(CounterScope oldWidget) {
    return count != oldWidget.count;
  }
}

void main() => runApp(const MaterialApp(
      home: CounterPage(),
    ));

class CounterPage extends StatefulWidget {
  const CounterPage({super.key});

  @override
  State<CounterPage> createState() => _CounterPageState();
}

class _CounterPageState extends State<CounterPage> {
  int _count = 0;

  void _increment() => setState(() => _count++);

  @override
  Widget build(BuildContext context) {
    return CounterScope(
      count: _count,
      increment: _increment,
      child: Scaffold(
        appBar: AppBar(title: const Text('InheritedWidget 示例')),
        body: const Column(
          mainAxisAlignment: MainAxisAlignment.center,
          children: [
            _CounterDisplay(),
            SizedBox(height: 16),
            _IncrementButton(),
          ],
        ),
      ),
    );
  }
}

// 两个独立子 Widget，通过 InheritedWidget 拿到共享状态
class _CounterDisplay extends StatelessWidget {
  const _CounterDisplay();
  @override
  Widget build(BuildContext context) {
    final scope = CounterScope.of(context);
    return Text('计数: ${scope.count}',
        style: const TextStyle(fontSize: 28, fontWeight: FontWeight.bold));
  }
}

class _IncrementButton extends StatelessWidget {
  const _IncrementButton();
  @override
  Widget build(BuildContext context) {
    final scope = CounterScope.of(context);
    return ElevatedButton(
      onPressed: scope.increment,
      child: const Text('+1'),
    );
  }
}

InheritedWidget 使用场景

  • ✅ 全局配置（主题、语言、路由）
  • ✅ 跨几个 Widget 层的共享状态
  • ❌ 大而复杂的业务状态（直接用框架）
  • ❌ 需要复杂计算/验证的状态管理逻辑

主流框架选型 ​

InheritedWidget 是底层能力，但大项目会用更高层的框架来处理状态管理、副作用、测试等复杂问题。

Provider / Riverpod（推荐入门首选） ​

Provider 是对 InheritedWidget 的薄封装，Riverpod 是 Provider 的进化版。核心价值：

  • 声明式：注册 Provider → 任意位置消费，无参数钻探
  • 测试友好：可以 mock Provider
  • Riverpod 提供更安全的编译时检查、支持多个同名 Provider 并存
dart
// 注册
final counterProvider = StateProvider<int>((ref) => 0);

// 消费
final count = ref.watch(counterProvider);     // 变化时重建
ref.read(counterProvider.notifier).state++;   // 修改

Bloc / Cubit（中大型项目） ​

Bloc（Business Logic Component）是事件驱动的状态管理，把 UI 和业务逻辑严格隔离：UI 只发出事件（Event）、只接收状态（State），中间的 Bloc 负责将事件映射为新状态。适合业务逻辑复杂、需要严格可预测状态流的项目。

dart
// Event → Bloc → State
class CounterIncrement extends CounterEvent {}
class CounterState extends Equatable { final int count; }
// Bloc 收到 CounterIncrement → yield CounterState(count + 1)

GetX / MobX（语法糖浓郁派） ​

GetX 一套（状态、路由、依赖注入、国际化全包）、MobX 响应式魔法（@observable + @action）。代码写起来快，但隐式行为多、调试和团队协作成本高。

Riverpod vs Bloc 怎么选？ ​

维度RiverpodBloc
学习曲线低中
代码量少多（Event/State/Bloc 三件套）
可预测性中等高（事件-状态流明确）
测试简单简单
适用规模中小型、个人项目中大型、多人协作、业务复杂

选型原则

  • 小项目 / 学状态管理 → Riverpod
  • 复杂业务 / 需要严格状态流 → Bloc
  • 别一开始就引入：先用 StatefulWidget + 状态提升把代码跑起来，感觉参数钻探痛了再引入框架。过度架构比没有架构更糟。

常见坑 ​

高频踩坑点

  1. InheritedWidget 没有重建依赖方：漏掉 updateShouldNotify 或返回了 false，导致依赖它的子 Widget 不重建。
  2. Provider 的 watch 和 read 用错：build 里用 ref.watch（需要重建），事件回调里用 ref.read（不需要重建）。反过来会导致无限重建或不重建。
  3. 状态放错位置：用户输入（TextField 的 controller 内容）应该就地管理；需要跨页共享（登录态、购物车）才放全局。
  4. 状态命名不清晰：StateProvider<int>((ref) => 0) 比 StateProvider<int>((ref) => 0) 少了业务含义，命名要能读懂。

课后练习 ​

  1. 状态提升实战：把你已有的计数器示例，改成父 Widget 持有 _count 状态，传给两个子 Widget 分别展示和修改。
  2. InheritedWidget 改造：用 InheritedWidget 封装一个「用户信息」Scope，子 Widget 直接从 context 读当前用户名和头像。
  3. Provider 入门：flutter pub add provider，改造计数器示例为 ChangeNotifierProvider + Consumer 模式。
  4. 选型调研：去 pub.dev 对比 Riverpod 和 Bloc 包的热度、Stars、最近版本时间，结合项目规模写一段话你会选哪个、为什么。
