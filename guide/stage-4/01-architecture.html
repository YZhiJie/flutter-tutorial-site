架构模式（MVVM / Bloc / Riverpod） ​

学习目标 ​

学完本章，你将能够：

  • 区分 UI 层 / 业务层 / 数据层的职责边界
  • 理解 MVVM 架构在 Flutter 中的落地（ViewModel + 双向绑定）
  • 深入 Bloc 的事件-状态流模型，以及何时选它
  • 用 Riverpod 组织 Provider / Notifier / AsyncNotifier 构建清晰的依赖图
  • 知道「不写架构」比「过度架构」好，掌握演进路径

架构的本质

架构就是画清楚数据和副作用的流动方向。UI 不能直接操作数据库？→ Repository 层。状态要跨页面？→ 状态层。要改一处影响一堆？→ 抽象隔离。

分层模型 ​

Flutter 项目典型的三层划分：

UI 层        StatefulWidget / StatelessWidget  → 纯渲染、纯用户交互
 ↓ 调用
业务层       StateNotifier / Bloc / Controller  → 业务规则、状态编排
 ↓ 调用
数据层       Repository + DataSource             → 网络、本地、缓存的统一入口

关键原则：上层依赖下层，下层不依赖上层。UI 层不能 import 数据层；数据层也不能 import Widget。

MVVM 在 Flutter 的落地 ​

Flutter 没有 Android DataBinding 那种自动双向绑定，Flutter 里 MVVM 通常长这样：

dart
// ViewModel：监听数据变化并更新状态
class CounterViewModel extends ChangeNotifier {
  int _count = 0;
  int get count => _count;          // ← 状态暴露给 View

  void increment() {
    _count++;
    notifyListeners();              // ← 通知 View 重建
  }
}

// View：监听 ViewModel
class CounterView extends ConsumerWidget {
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final vm = ref.watch(counterViewModelProvider);
    return Column(
      children: [
        Text('计数: ${vm.count}'),
        ElevatedButton(onPressed: vm.increment, child: Text('+1')),
      ],
    );
  }
}

MVVM 优势：UI 层和业务层天然解耦；ViewModel 可单测。Flutter 里的 MVVM 通常等价于 状态管理框架 + Repository 模式。

Bloc：事件驱动的严格分离 ​

Bloc 模式把状态变化做成明确的「事件 → 状态」管道：

User Action → Event → Bloc → State → Widget rebuild
dart
// Event 类
sealed class CounterEvent {}
final class CounterIncremented extends CounterEvent {}
final class CounterDecremented extends CounterEvent {}

// State 类（Equatable 支持值相等比较）
final class CounterState extends Equatable {
  const CounterState({required this.count});
  final int count;
  @override
  List<Object?> get props => [count];
}

// Bloc 类（纯 Dart 类，零 Flutter 依赖）
class CounterBloc extends Bloc<CounterEvent, CounterState> {
  CounterBloc() : super(const CounterState(count: 0)) {
    on<CounterIncremented>((event, emit) => emit(CounterState(count: state.count + 1)));
    on<CounterDecremented>((event, emit) => emit(CounterState(count: state.count - 1)));
  }
}

// UI：BlocListener 监听一次性事件（导航、Toast），BlocBuilder 重建
BlocListener<CounterBloc, CounterState>(
  listener: (context, state) { /* 导航、SnackBar 等 */ },
  child: BlocBuilder<CounterBloc, CounterState>(
    builder: (context, state) => Text('计数: ${state.count}'),
  ),
)

Bloc 优势：状态流可预测、纯 Dart 易单测、适合多人协作、事件/状态类型安全。劣势：代码量大、学习曲线陡、简单场景显得杀鸡用牛刀。

Riverpod：声明式依赖图 ​

Riverpod 把应用状态和依赖组织成一张图：每个 Provider 是图上的节点，ref 让你从任意位置访问其他 Provider。

dart
// 数据层：Repository
final authRepositoryProvider = Provider<AuthRepository>((ref) => AuthRepository());

// 业务层：Notifier（新版写法）
final authNotifierProvider = NotifierProvider<AuthNotifier, AuthState>(AuthNotifier.new);

class AuthNotifier extends Notifier<AuthState> {
  late final AuthRepository _repo;
  @override
  AuthState build() {
    _repo = ref.watch(authRepositoryProvider); // ← 声明依赖
    return const AuthState.idle();
  }
  Future<void> login(String username, String pwd) async {
    state = const AuthState.loading();
    try {
      final user = await _repo.login(username, pwd);
      state = AuthState.authenticated(user);
    } catch (e) {
      state = AuthState.error(e.toString());
    }
  }
}

与 Provider 对比：

  • ✅ 编译时类型安全（Provider 的 watch/read 返回 dynamic，Riverpod 有泛型）
  • ✅ 不依赖 context（Provider 必须用 context，Riverpod 的 ref 随处可用）
  • ✅ 无全局变量（Provider 的 top-level 是隐式全局，Riverpod 更显式）
  • ✅ 支持 overrideProvider（测试和多环境非常方便）

演进路径：从简单到复杂 ​

阶段 1：StatefulWidget + 状态提升（入门项目）
  ↓ 参数钻探痛了，想换 Provider
阶段 2：Provider / Riverpod（中小型）
  ↓ 业务逻辑复杂，需要事件-状态流可预测
阶段 3：Bloc / Freezed（中大型）
  ↓ 数据结构复杂 + 需要持久化
阶段 4：Riverpod + Freezed + Isar（全栈高级）

不要提前过度架构

小项目（几个页面、几个状态）用 StatefulWidget + 少量状态提升就够了。引入框架的成本（学习、样板代码、团队成员上手）可能比收益大。等真的痛了再上。

常见坑 ​

高频踩坑点

  1. 业务层 import 了 Widget：ViewModel / Bloc 里不能出现 BuildContext、不能调 Navigator。UI 层调事件后，ViewModel 发状态；UI 层根据状态决定是否导航。
  2. Provider / Riverpod 忘记 dispose：NotifierProvider 不会自动 dispose——它会常驻。StateProvider / AsyncNotifierProvider 可以设置 autoDispose: true。
  3. Bloc 在 build 里 add 事件：context.read<Bloc>().add(Event()) 不能放在 build 里，会触发无限循环。放 initState 或事件回调里。
  4. Repository 直接返回 UI 数据：Repository 应该返回领域数据模型（纯 Dart 类），业务层负责把领域数据转换成 UI 需要的状态（如 Loading / Loaded / Error）。

课后练习 ​

  1. 三架构改造：拿一个你已有的 Todo demo（任意风格），分别用 MVVM / Bloc / Riverpod 三种架构重写，对比代码量、可测试性、改动一个逻辑点需要动的文件数。
  2. 依赖图实战：用 Riverpod 搭一个完整的用户登录流程——Repository 层封装网络请求，Notifier 管理 loading / success / error 三态，UI 层根据状态显示 loading spinner / 用户信息 / 错误提示。
  3. 测试：给你的 ViewModel / Bloc 写单元测试（flutter_test），至少覆盖：初始状态、正常流程、网络失败、Token 过期等场景。
  4. 架构演进设计：你接手一个 20 个页面的 Flutter 项目，目前用 StatefulWidget 到处散落状态，你会如何逐步演进到 Riverpod + Freezed？写出分 3 步的演进计划，说明每步的收益和风险。
