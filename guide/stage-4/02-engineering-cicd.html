工程化与 CI/CD ​

学习目标 ​

学完本章，你将能够：

  • 组织 pubspec.yaml、多环境配置、代码生成工作流
  • 编写 Flutter 项目的 lint 规则（analysis_options.yaml）
  • 在 GitHub Actions / GitLab CI 上搭建自动化流水线：lint → test → build → 提审
  • 使用 flavor（多构建变体）区分 dev / staging / prod 环境
  • 理解并处理 fastlane / GitHub Actions 的移动端发布流程

Flutter 工程化的核心三件套

代码质量（lint + format + 静态分析）、自动化流水线（CI）、多环境配置（flavor）。这三件事跟上了，项目协作顺畅度和信心值翻倍。

analysis_options.yaml：代码质量底线 ​

Flutter/Dart 自带强大的静态分析引擎，通过 analysis_options.yaml 控制 lint 规则：

yaml
include: package:flutter_lints/flutter.yaml  # 基础 Flutter lint 集

linter:
  rules:
    prefer_const_constructors: true          # 强制 const
    require_trailing_commas: true             # 多行参数尾逗号（format 默认风格）
    always_use_package_imports: true          # 禁止相对导入
    avoid_print: true                         # 生产代码禁止 print
    prefer_single_quotes: true                # 统一引号风格

analyzer:
  exclude:
    - "**/*.g.dart"                          # 排除生成文件
    - "**/*.freezed.dart"
    - "build/**"
bash
flutter analyze        # 跑静态分析，0 error 0 warning 是底线
flutter format .       # 统一格式化

git hook 自动拦截

用 lefthook 或 husky 配置 pre-commit hook，commit 前自动跑 flutter format 和 flutter analyze，没通过就拒绝提交。

pubspec.yaml 工程化 ​

yaml
name: my_app
description: My Flutter App
publish_to: 'none'         # 应用项目永不发布
version: 1.2.3+102         # 版本字符串 + 构建号

environment:
  sdk: ^3.4.0
  flutter: ">=3.24.0"      # 锁定 Flutter SDK 版本，避免团队成员不同步

dependencies:
  flutter:
    sdk: flutter
  cupertino_icons: ^1.0.6
  # 精确版本号（避免 ^ 造成自动升级引入破坏性变更）
  riverpod: 2.6.1

dev_dependencies:
  flutter_lints: ^5.0.0
  flutter_test:
    sdk: flutter
  build_runner: ^2.4.9

flutter:
  uses-material-design: true
  assets:
    - assets/images/
    - assets/config/

锁定 Flutter SDK 版本

在 pubspec.yaml 声明 flutter 版本 + 提交 .fvm/fvm_config.json（用 FVM 工具）。CI 和团队成员都能通过 FVM 拉到相同的 SDK 版本。

GitHub Actions：完整流水线示例 ​

yaml
# .github/workflows/ci.yml
name: CI

on:
  push: { branches: [main, develop] }
  pull_request: { branches: [main, develop] }

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: 'temurin', java-version: '17' }
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '3.24.0', cache: true }
      - run: flutter pub get
      - run: flutter format --set-exit-if-changed .   # 格式化检查
      - run: flutter analyze                          # 静态分析
      - run: flutter test --coverage                  # 单测
      - uses: codecov/codecov-action@v4               # 覆盖率上报

  apk:
    needs: check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '3.24.0' }
      - run: flutter pub get
      - run: flutter build apk --release --target-platform android-arm64
      - uses: actions/upload-artifact@v4
        with:
          name: release-apk
          path: build/app/outputs/flutter-apk/app-release.apk

Flavor：多环境一套代码 ​

Flutter 官方通过 Dart 定义变量 + --dart-define 注入：

bash
# 开发环境（dev flavor）
flutter run --dart-define=ENV=dev --dart-define=API_BASE=https://dev.api.com

# 生产环境
flutter run --release --dart-define=ENV=prod --dart-define=API_BASE=https://api.com

代码里读取：

dart
final env = const String.fromEnvironment('ENV', defaultValue: 'dev');
final apiBase = const String.fromEnvironment('API_BASE', defaultValue: 'https://dev.api.com');

class Env {
  static final isDev = env == 'dev';
  static final isProd = env == 'prod';
  static String get apiBase => apiBase;
}

Android 原生 Gradle 里可以用 flavor 同时出多个包（dev / staging / prod 各自的 applicationIdSuffix、图标、应用名），iOS 用 Scheme 做类似事。

代码生成工作流 ​

json_serializable / freezed / mockito 等代码生成包：

bash
# 一次性生成
flutter pub run build_runner build --delete-conflicting-outputs

# 监听文件变化自动生成
flutter pub run build_runner watch --delete-conflicting-outputs

CI 里要跑一次 build_runner，并确保生成的文件没有漏提交到 Git。

常见坑 ​

高频踩坑点

  1. pubspec.lock 没提交：lock 文件保证团队成员拉到相同依赖版本。必须进 Git。
  2. flavor 参数拼写不一致：dart-define 变量名大小写敏感。建议统一在 Env 类里封装，不要各处散落 fromEnvironment 调用。
  3. CI 用 latest Flutter 版本：flutter-version: latest 明天跑就可能炸。锁具体版本号。
  4. lint 规则开太严导致 PR 全红：lint 规则是渐进过程。先开基础规则，团队熟悉了再逐步加。
  5. 生成文件与手写文件混：*.g.dart / *.freezed.dart 这些生成文件不要手动修改，下次 build_runner 直接覆盖。

课后练习 ​

  1. lint + format 落地：给你的项目加 analysis_options.yaml，引入 flutter_lints + 自定义规则，跑 flutter analyze 确保 0 error 0 warning，flutter format --set-exit-if-changed . 确保格式统一。
  2. Flavor 实战：项目加 dev / prod 两个 flavor，两个 API_BASE，dev 环境打开发服务器、prod 环境打真实服务器。加两个不同的应用名后缀（App Dev / App）。
  3. CI 流水线：写一个 GitHub Actions workflow，包含 checkout → flutter setup → pub get → analyze → test → build release apk，PR 时自动运行并挂到 PR 上。
  4. 代码生成 + Git：加 json_serializable + freezed，生成模型文件，确认 build_runner 的产物能正确进 Git（gitignore 只应该排除 build/ 目录，不是 *.g.dart）。
