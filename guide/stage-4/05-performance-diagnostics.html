性能诊断方法论与帧预算 ​

学习目标 ​

学完本章，你将能够：

  • 把「卡」翻译成可测量的指标（帧时间分位数、jank 率、首帧耗时、内存峰值）
  • 算清不同刷新率下的单帧预算，并解释 60Hz / 90Hz / 120Hz 的差异
  • 判断卡顿发生在 UI 线程、Raster 线程还是根本不在渲染链路
  • 按「症状 → 第一现场 → 工具 → 结论」的判定树推进，而不是凭经验猜
  • 用 FrameTiming 建立可复现的性能基线，避免用平均值自欺欺人
  • 知道哪些测量是无效的（debug 模式、模拟器、单次滑动）

先建方法论，再背技巧

性能优化最常见的失败不是「不会优化」，而是优化了错的东西。同一句「列表有点卡」，可能来自 build 次数过多、图片解码过大、Raster 过度绘制、甚至只是主线程被同步 IO 堵住。方法论的唯一目的：用最小成本把可能性收敛到一条。

把「卡」翻译成指标 ​

用户说法可测量指标数据来源
滑动不跟手滚动期间 P90 帧时间、jank 率DevTools Performance、FrameTiming
点按钮要等一下输入到首帧的延迟、build 耗时Timeline 的 input → frame 区间
打开 App 慢冷启动到首帧耗时--trace-startup
越用越卡、偶发 OOM内存峰值、GC 次数、对象增长曲线DevTools Memory
动画一顿一顿每帧 raster 耗时、shader 编译事件Timeline 的 Raster 轨道
只有首次进入卡首帧 vs 次帧的差异两次录制的 Diff

指标必须是分位数而不是平均值。一次 200ms 的卡顿会被 299 帧 5ms 的正常帧摊平成「平均 5.6ms」，用户感知却完全相反。

帧预算：不同刷新率下的时间账 ​

预算公式只有一条：

单帧预算(ms) = 1000 / 屏幕刷新率(Hz)
刷新率单帧预算意味着
60Hz16.7msbuild + layout + paint + raster 全部要塞进 16.7ms
90Hz11.1ms中端机常见，余量更小
120Hz8.3msProMotion / 高刷屏，对 Raster 尤其苛刻

预算不是一个池子，而是串行流水线：UI 线程做完 build/layout/paint 才能交给 Raster，Raster 光栅化完才能上屏。所以 12ms 的 build + 10ms 的 raster 依然是掉帧，尽管各自都没「超标」。

别把 16.7ms 当铁律

16.7ms 是 60Hz 的理论值，实际可用余量更小：引擎自身开销、系统合成、VSync 对齐都会吃掉一部分。工程上更实用的口径是「P90 帧时间 ≤ 预算，且 jank 率 < 1%」。

三个线程与三个阶段 ​

测量前只需要记住分工，不需要背原理：

阶段跑在哪典型耗时来源
build / layout / paintUI 线程（Dart）setState 级联、布局嵌套、paint 里的复杂绘制指令
rasterRaster 线程（引擎）过度绘制、大图上传纹理、saveLayer、模糊
合成上屏GPU / 系统合成器通常不是 Flutter 代码能直接优化的部分

判定入口只有一个问题：Timeline 里超预算的那条轨道是谁？ UI 轨道长 → 回到 Dart 代码；Raster 轨道长 → 看绘制与图层。

测量的五条纪律 ​

  1. 只用 profile 模式：flutter run --profile。debug 模式的断言与 JIT 会让所有数字失真。
  2. 只用真机：模拟器没有真实 GPU 与功耗模型，帧率数据不可用。
  3. 单变量：一次只改一处，否则无法归因。
  4. 足够样本：至少录制 5 秒或 300 帧，再做分位数统计。
  5. 固定基线：同一台设备、同一个构建、同一段操作脚本，否则前后对比没有意义。

工具矩阵 ​

命令 / 工具回答什么问题
flutter run --profile真机上的帧时间、内存、CPU
DevTools Performance哪一帧超预算、超在 build / layout / paint / raster 哪一段
DevTools CPU Profiler哪个 Dart 函数吃掉了时间

从数据到结论：判定树 ​

帧时间超预算
├─ UI 轨道长
│  ├─ build 长 → 重建范围过大 / build 里有计算
│  ├─ layout 长 → 嵌套深、Intrinsic 尺寸、列表无固定高度
│  └─ paint 长 → 绘制指令过多、saveLayer、大面积裁剪
├─ Raster 轨道长
│  ├─ 首次出现且随后恢复 → shader 编译 / 图片首次解码
│  ├─ 持续长 → 过度绘制、模糊、大图未下采样、PlatformView
│  └─ 仅滚动时长 → 图片解码、图层未隔离
└─ 两条都不长却仍卡
   ├─ 输入延迟 → 主线程被同步任务占用
   ├─ 首帧未上屏 → 启动链路（第 08 章）
   └─ 内存压力 → GC 抖动（第 07 章）

建立可比的基线 ​

FrameTiming 是框架直接给出的逐帧数据，比截图和肉眼可靠：

dart
// 环形缓冲区记录最近 300 帧，按需算分位数
final List<double> _spans = <double>[];

void _onTimings(List<FrameTiming> timings) {
  for (final t in timings) {
    final total = t.totalSpan.inMicroseconds / 1000.0; // 整帧耗时(ms)
    _spans.add(total);
    // buildDuration / rasterDuration 可分别记录，用于定位阶段
  }
  if (_spans.length > 300) _spans.removeRange(0, _spans.length - 300);
}

// 使用：WidgetsBinding.instance.addTimingsCallback(_onTimings)
// 释放：WidgetsBinding.instance.removeTimingsCallback(_onTimings)

基线建议记录这些字段，写进 PR 或性能看板：

指标口径参考阈值
P50 帧时间中位数≤ 预算的 60%
P90 帧时间分位数≤ 预算
jank 率超预算帧 / 总帧< 1%
首帧耗时冷启动到首帧依业务定义
内存峰值关键流程峰值无持续增长

优化报告怎么写

「优化前 P90 22ms / jank 8.4%，优化后 P90 14ms / jank 0.7%，设备 iPhone 13，profile 模式，同一段 30 秒滚动脚本」——有设备、有口径、有脚本，别人才可能复现。只写「快了很多」等于没写。

可运行示例 ​

dart
import 'package:flutter/material.dart';
import 'package:flutter/scheduler.dart';

// 性能诊断方法论：用 FrameTiming 采集逐帧耗时，算 P50 / P90 / jank 率
// 打开后滑动下方示例内容，观察分位数与超支帧比例

void main() => runApp(const MaterialApp(home: _BudgetPage()));

class _BudgetPage extends StatefulWidget {
  const _BudgetPage();

  @override
  State<_BudgetPage> createState() => _BudgetPageState();
}

class _BudgetPageState extends State<_BudgetPage> {
  static const double _budgetMs = 16.7; // 60Hz 单帧预算
  final List<double> _spans = <double>[];

  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addTimingsCallback(_onTimings);
  }

  @override
  void dispose() {
    WidgetsBinding.instance.removeTimingsCallback(_onTimings);
    super.dispose();
  }

  void _onTimings(List<FrameTiming> timings) {
    if (!mounted) return;
    setState(() {
      for (final t in timings) {
        _spans.add(t.totalSpan.inMicroseconds / 1000.0);
      }
      if (_spans.length > 120) _spans.removeRange(0, _spans.length - 120);
    });
  }

  double _percentile(double p) {
    if (_spans.isEmpty) return 0;
    final List<double> sorted = List<double>.of(_spans)..sort();
    final index = ((sorted.length - 1) * p).round();
    return sorted[index];
  }

  int get _jankCount => _spans.where((s) => s > _budgetMs).length;

  @override
  Widget build(BuildContext context) {
    final double p50 = _percentile(0.5);
    final double p90 = _percentile(0.9);
    final double jankRate =
        _spans.isEmpty ? 0 : _jankCount / _spans.length * 100;
    return ListView(
      padding: const EdgeInsets.all(16),
      children: <Widget>[
        Text(
          '采样帧数 ${_spans.length}｜预算 ${_budgetMs}ms',
          style: Theme.of(context).textTheme.titleSmall,
        ),
        const SizedBox(height: 8),
        Card(
          child: Padding(
            padding: const EdgeInsets.all(16),
            child: Row(
              mainAxisAlignment: MainAxisAlignment.spaceAround,
              children: <Widget>[
                _Stat(label: 'P50', value: '${p50.toStringAsFixed(1)}ms'),
                _Stat(label: 'P90', value: '${p90.toStringAsFixed(1)}ms'),
                _Stat(
                  label: 'jank',
                  value: '${jankRate.toStringAsFixed(1)}%',
                  warn: jankRate > 1,
                ),
              ],
            ),
          ),
        ),
        const SizedBox(height: 8),
        Text(
          '每根柱子是一帧的实际耗时（红色 = 超预算）',
          style: Theme.of(context).textTheme.bodySmall,
        ),
        const SizedBox(height: 8),
        SizedBox(
          height: 90,
          child: ListView.builder(
            scrollDirection: Axis.horizontal,
            itemCount: _spans.length,
            itemBuilder: (ctx, i) {
              final double s = _spans[i];
              final bool over = s > _budgetMs;
              return Padding(
                padding: const EdgeInsets.only(right: 3),
                child: Align(
                  alignment: Alignment.bottomCenter,
                  child: Container(
                    width: 6,
                    height: (s / 40 * 80).clamp(6, 80),
                    color: over ? Colors.red : Colors.green,
                  ),
                ),
              );
            },
          ),
        ),
        const SizedBox(height: 16),
        Text(
          '接下来：故意制造 10 万次循环，观察 P90 与 jank 率的变化——'
          '这就是「用数据把卡翻译成指标」。',
          style: Theme.of(context).textTheme.bodySmall,
        ),
        const SizedBox(height: 8),
        for (int i = 0; i < 30; i++)
          ListTile(
            dense: true,
            title: Text('普通列表项 #$i'),
            subtitle: const Text('用于产生稳定的可测帧'),
          ),
      ],
    );
  }
}

class _Stat extends StatelessWidget {
  const _Stat({required this.label, required this.value, this.warn = false});

  final String label;
  final String value;
  final bool warn;

  @override
  Widget build(BuildContext context) {
    return Column(
      children: <Widget>[
        Text(label, style: Theme.of(context).textTheme.bodySmall),
        const SizedBox(height: 4),
        Text(
          value,
          style: Theme.of(context).textTheme.titleMedium?.copyWith(
                color: warn ? Colors.red : null,
              ),
        ),
      ],
    );
  }
}

常见坑 ​

六个让测量失效的操作

  1. 在 debug 模式看帧率：debug 下 build 慢 3-10 倍是常态，看到的「卡」大多是假的。
  2. 用平均值描述体验：平均值掩盖长尾，必须看 P90 / P99 与 jank 率。
  3. 在模拟器上做性能结论：GPU 与内存模型都不同，数据没有参考价值。
  4. 一次改五处再对比：即使变快了也不知道是哪一处起效，无法沉淀经验。
  5. 只测一次滑动：首帧有编译与缓存预热，单次样本必然偏低或偏高。
  6. 照搬别人的数字：设备档位、屏幕刷新率、业务复杂度都不同，阈值要自己测。

课后练习 ​

  1. 用 flutter run --profile 跑一个列表页，用 FrameTiming 采集 300 帧，算出 P50 / P90 / jank 率，并记录设备与刷新率。
  2. 在同一页面上分别制造两种卡顿：(a) build 里做 10 万次循环；(b) 给整页加 BackdropFilter。用 Timeline 判断分别落在哪条线程。
  3. 把第 2 题的两种卡顿写成一页「判定树」笔记，标注你会用什么工具、看哪条轨道、下一步改哪里。
  4. 选一个真实页面，按「优化前 / 优化后」格式写一份性能报告，包含设备、口径、脚本与量化结果。
  5. 故意用平均值汇报一次优化结果，再换成分位数，体会两种汇报方式的差异。
