内存治理与泄漏排查 ​

学习目标 ​

学完本章，你将能够：

  • 说清 Dart 堆的新生代 / 老年代、Scavenge 与 Mark-Sweep 的触发条件
  • 用 DevTools Memory 面板 + 快照对比法，区分「内存涨」与「真泄漏」
  • 通过 VM Service 的 getAllocationProfile 按类查看存活实例数与字节数
  • 排查五类高频泄漏：StreamSubscription、AnimationController、TextEditingController、闭包持有 context、无上限全局缓存
  • 用 leak_tracker 与 DevTools 的 Leak Tracking 在测试阶段拦住泄漏
  • 用 cacheWidth / ResizeImage 与 ImageCache 上限把图片内存压下来

一句话认知

Dart 有分代 GC，「内存涨了」不等于「泄漏」。泄漏 = 业务上已经不该用，但从 GC Root 仍有引用链可达。所以排查对象永远是「引用链」，不是「内存曲线」。

Dart 内存模型：新生代与老年代 ​

Dart 的对象都在堆上，堆按「年龄」分两代：

区域回收算法触发时机典型对象
新生代（New space）Scavenge（复制式，半空间）新生代分配满短命的临时对象：build 产生的 Widget、字符串拼接、局部 List
老年代（Old space）Mark-Sweep + Compact老年代占用超过阈值长生命周期对象：单例、缓存、已晋升的控制器
  • 新生代对象经历几次 Scavenge 仍存活，就会被晋升到老年代；
  • 大对象（超大 List / 大字符串）直接分配进老年代，避免反复复制；
  • GC Root 包括：正在执行的栈帧、静态变量、Isolate 的消息队列、Native 持有的句柄。只要对象从 Root 可达，GC 就不会回收它。

暂停时间的量级（经验值，随堆大小与设备变化）：Scavenge 通常 1~3ms，Full GC（Mark-Sweep-Compact）10~50ms，堆越大越久——这也是「泄漏越久越卡」的原因。

bash
# 打印每次 GC 的类型、前后堆大小与耗时
flutter run --profile --verbose-gc

Scavenge 频繁 ≠ 泄漏

短命对象多会带来高频 Scavenge，日志刷屏但每帧仍达标。真正要警惕的是：Full GC 后堆占用仍然阶梯式上涨。

DevTools Memory 面板与快照对比法 ​

bash
# 让启动日志把 vm-service 地址写进文件，方便 DevTools / curl 连
flutter run --profile --vmservice-out-file=/tmp/vm.txt
# 也可以直接 flutter run --profile 后按 v 打开 DevTools

面板上三个关键指标：

指标含义关注点
Dart Heap（堆）Dart 对象占用强制 GC 后是否回落
External（外部内存）图片解码、Native 分配的缓冲区图片/解码问题主要看它
RSS / Adb Memory进程真实占用与系统 OOM 风险直接相关

快照对比法是判断泄漏的标准流程：

  1. 点面板上的 GC 按钮，强制一次 Full GC，记录基线；
  2. 抓快照 A；
  3. 重复可疑操作 10~20 次（进出页面、开关弹窗）；
  4. 再强制 GC，抓快照 B；
  5. 看 B−A 的实例数净增：操作已结束却仍在涨的类，就是泄漏嫌疑对象。

为什么要先 GC

Dart 的 GC 不是即时的。不强制回收就抓快照，会把「还没轮到回收的垃圾」误判成泄漏。先 GC 再看，是把噪声去掉。

用 VM Service 精确定位到类 ​

DevTools 的 UI 之外，可以直接调 VM Service 的 getAllocationProfile，拿到按类统计的存活实例：

bash
# vm.txt 里是一行形如 http://127.0.0.1:8181/ 的地址
curl -s "$(cat /tmp/vm.txt)getVM" | jq '.result.isolates[0].id'
# 把返回的 isolateId 填进去，看每个类的存活实例与字节数
curl -s "$(cat /tmp/vm.txt)getAllocationProfile?isolateId=isolates/12345" \
  | jq '.result.classes[] | {cls: .classRef.name, live: .instancesCurrent, bytes: .bytesCurrent}'
字段含义用法
classRef.name类名定位到你的 _PageState、_CacheEntry
instancesCurrent当前存活实例数反复进出页面后仍线性增长 → 泄漏
bytesCurrent当前占用字节结合实例数算平均大小，判断是大对象还是小对象堆积

也可以不写 curl：在 DevTools 的 Console 里执行同名的 service extension，或点 Memory 面板的「Profile memory」采样分配栈。

五类高频泄漏源 ​

泄漏源为什么会漏正确做法
StreamSubscriptionlisten 返回的订阅必须 cancel，否则流一直持有回调与闭包dispose 里 await sub.cancel()
AnimationController未 dispose 时 Ticker 仍注册在 SchedulerBinding 上dispose 里 controller.dispose()
TextEditingController / ScrollController内部持有 ChangeNotifier 监听者列表同上，dispose()
闭包持有 BuildContext异步回调里捕获了 context，路由已销毁用 mounted 检查，或先把需要的数据取出来
全局 Map / List 缓存只增不减，等于把对象钉在老年代设容量上限 + LRU 淘汰，或用 WeakReference
dart
class _PageState extends State<Page> {
  late final StreamSubscription<int> _sub;
  late final AnimationController _anim;
  final TextEditingController _text = TextEditingController();

  @override
  void initState() {
    super.initState();
    _anim = AnimationController(vsync: this, duration: const Duration(seconds: 1));
    _sub = someStream.listen((_) { /* 注意：回调里不要长期持有 context */ });
  }

  @override
  void dispose() {
    _sub.cancel();      // 1. 先断订阅
    _anim.dispose();    // 2. 再释放 Ticker
    _text.dispose();    // 3. 最后释放控制器
    super.dispose();    // 4. 一定放在最后
  }
}

最常见的假修复

把 dispose 写在 deactivate 里，或者只在「用户主动关闭」时释放——页面被 Navigator 移除时并不会走到那条路径。释放逻辑只能写在 dispose。

leak_tracker：把泄漏拦在 CI ​

leak_tracker 是 Flutter 官方的泄漏检测工具，原理是在测试中记录「本应被回收的对象」，GC 后仍可达就判定泄漏，并给出引用链。

yaml
# pubspec.yaml 的 dev_dependencies（版本以 pub 上最新为准）
dev_dependencies:
  leak_tracker:
  leak_tracker_flutter_testing:
dart
// flutter_test 入口里开启；之后每个 testWidgets 结束都会做一次泄漏检查
void main() {
  LeakTesting.enable();
  // 可对已知常驻对象（如全局单例）配置忽略规则，避免误报
}
场景工具说明
组件测试 / Widget 测试leak_tracker_flutter_testingCI 里跑，失败即拦住
真机手动排查DevTools Memory 的 Leak Tracking操作后查看「未释放对象 + 引用链」
线上/预发快照对比 + 关键类计数无法开追踪时的兜底手段

引用链才是答案

leak_tracker 给出的价值不在「漏了」，而在引用链：_PageState → _sub → closure → context。顺着链找到那个忘了 cancel 的字段，通常 5 分钟就能改完。

图片内存：External 的大头 ​

一张图解码后的内存 = 宽 × 高 × 4 字节（RGBA8888）。这个数字和文件大小无关：

图片解码后内存说明
4000×3000 JPEG（3MB 文件）约 48MB相机原图直接上图
1200×900约 4.3MB未下采样
300×225（cacheWidth: 300）约 0.26MB按显示尺寸解码

所以列表里放 10 张原图，光解码就接近 480MB——必然 OOM。

dart
// 按显示宽度解码，内存直接降两个数量级
Image.network(url, width: 300, cacheWidth: 300);

// 用 provider 形式，逻辑更清晰，也能配合其他 ImageProvider 使用
Image(image: ResizeImage(NetworkImage(url), width: 300));

ImageCache 有两个默认上限：最多 1000 张、最多 100 MiB。超过就按 LRU 淘汰。收到内存警告时可以主动清空：

dart
final cache = PaintingBinding.instance.imageCache;
cache.clear();           // 清掉不再使用的缓存图
cache.clearLiveImages(); // 连正在显示的也释放（会导致重新解码，慎用）

下采样只省解码内存

cacheWidth 减少的是「解码后的位图」，原始压缩字节仍会进内存并参与网络/磁盘缓存。超大原图还应在服务端出多尺寸，或下载时就压缩。

可运行示例 ​

DartPad 运行环境将在滚动到此处时加载…
查看完整源码
dart
import 'dart:async';

import 'package:flutter/material.dart';

// 内存治理两件事：资源在 dispose 里释放；缓存必须设上限并淘汰
void main() => runApp(const MaterialApp(home: _MemoryPage()));

class _MemoryPage extends StatefulWidget {
  const _MemoryPage();
  @override
  State<_MemoryPage> createState() => _MemoryPageState();
}

class _MemoryPageState extends State<_MemoryPage> {
  final List<TextEditingController> _texts = <TextEditingController>[];
  final List<StreamController<int>> _streams = <StreamController<int>>[];
  final List<StreamSubscription<int>> _subs = <StreamSubscription<int>>[];

  static const int _cacheLimit = 3;
  final List<String> _cache = <String>[];
  int _seq = 0;

  void _create() {
    setState(() {
      for (var i = 0; i < 3; i++) {
        final id = _seq++;
        _texts.add(TextEditingController(text: '输入框 $id'));
        final c = StreamController<int>.broadcast();
        _streams.add(c);
        // 忘记 cancel 的订阅：页面销毁后流仍握着回调与闭包
        _subs.add(c.stream.listen((_) {}));
      }
    });
  }

  // 释放顺序：先断订阅，再关流，最后释放控制器
  void _disposeResources() {
    for (final s in _subs) {
      s.cancel();
    }
    for (final c in _streams) {
      c.close();
    }
    for (final t in _texts) {
      t.dispose();
    }
    _subs.clear();
    _streams.clear();
    _texts.clear();
  }

  void _addCache() {
    setState(() {
      _cache.add('img_${_seq++}.jpg');
      // 超上限就淘汰最早的一条（LRU 的最简版）
      if (_cache.length > _cacheLimit) _cache.removeAt(0);
    });
  }

  @override
  void dispose() {
    _disposeResources();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => Scaffold(
        appBar: AppBar(title: const Text('内存治理')),
        body: Padding(
          padding: const EdgeInsets.all(16),
          child: Column(
            crossAxisAlignment: CrossAxisAlignment.start,
            children: <Widget>[
              Text('未释放资源：${_texts.length} 个控制器 / ${_subs.length} 个订阅',
                  style: Theme.of(context).textTheme.titleMedium),
              const SizedBox(height: 8),
              Wrap(spacing: 8, children: <Widget>[
                FilledButton(onPressed: _create, child: const Text('创建资源')),
                OutlinedButton(
                  onPressed: () => setState(_disposeResources),
                  child: const Text('dispose 释放'),
                ),
              ]),
              const Divider(height: 32),
              Text('缓存（上限 $_cacheLimit 条）：${_cache.length}',
                  style: Theme.of(context).textTheme.titleMedium),
              const SizedBox(height: 8),
              Wrap(spacing: 8, children: <Widget>[
                for (final key in _cache) Chip(label: Text(key)),
              ]),
              const SizedBox(height: 8),
              OutlinedButton(onPressed: _addCache, child: const Text('写入一条缓存')),
              const Spacer(),
              const Text('要点：资源在 dispose 里释放；缓存要有上限与淘汰策略。'),
            ],
          ),
        ),
      );
}

常见坑 ​

高频踩坑点

  1. 看到内存上涨就喊泄漏：GC 未触发前堆增长是正常的；必须「强制 GC → 快照 → 重复操作 → 再强制 GC」才有结论。
  2. 只 dispose 控制器，忘了 cancel 订阅：StreamSubscription 不会随 State 销毁自动取消，流还在推事件。
  3. 在异步回调里用旧 context：await 之后页面可能已被 pop，直接 setState 会抛异常并顺带把 State 拖住；先判 mounted。
  4. 全局缓存没有上限：Map<String, Bitmap> 只增不减，比泄漏更隐蔽——它「看起来是设计」。
  5. 用 clearLiveImages() 当常规手段：正在显示的图被释放会导致立刻重新解码，可能引发卡顿与内存抖动。
  6. 只看 Dart Heap 忽略 External：图片问题几乎都体现在 External 与 RSS 上，Dart 堆可能很干净。

课后练习 ​

  1. 制造并修复泄漏：写一个页面，initState 里 listen 一个 Stream.periodic 但 dispose 不 cancel；反复进出 20 次后用 getAllocationProfile 查看该类实例数，修复后再测一次，对比两组数字（验证方法：两次都先强制 GC）。
  2. 快照对比实战：用 DevTools 抓 A/B 两份快照，找出净增最多的 3 个类，写下它们的引用链与判断依据。
  3. 缓存上限：给一个图片列表加 LRU 缓存（上限 20 项），用 imageCache.maximumSizeBytes 观察 External 变化，记录峰值前后差值。
  4. 接入 leak_tracker：给一个已有 Widget 测试打开 LeakTesting.enable()，故意漏掉一个 dispose，确认测试失败并读懂报错里的引用链；修好后确认转绿（验证方法：flutter test 的结果变化）。 :::
