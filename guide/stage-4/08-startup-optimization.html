启动优化与延迟初始化 ​

学习目标 ​

学完本章，你将能够：

  • 拆清冷启动链路：进程创建 → Engine 初始化 → Dart VM → 首帧构建 → 上屏
  • 用 flutter run --profile --trace-startup 生成启动 trace，并用 TimelineSummary 汇总 timeToFirstFrame
  • 把重活从 main() 挪到首帧之后：addPostFrameCallback、骨架屏、后台预热
  • 判断 deferred as + loadLibrary() 在你的平台是否真的有收益
  • 控制首屏 Widget 数量，避免「首帧 build 就超预算」
  • 处理原生侧启动：闪屏 / 启动画面 / FlutterEngineGroup 预热

先分清三种启动

冷启动：进程新建，Engine 从零加载，最慢也最值得优化。温启动：进程还在，Activity/页面重建，Engine 复用。热启动：App 只是从后台回前台，几乎没有 Dart 成本。本章讲的是冷启动。

冷启动的时间都花在哪 ​

阶段执行位置典型耗时你能控制多少
进程创建 + 系统启动画面系统80~300ms低（只能对齐闪屏）
Flutter Engine 初始化原生50~150ms中（预热引擎、减少插件注册）
Dart VM / Isolate 启动 + main()Dart50ms~2s高（最容易失控的一段）
首帧 build / layout / paintDart100~400ms高（Widget 数量、build 重活）
Raster + 上屏Raster/GPU20~80ms中（首帧少用模糊、大图）

经验目标：中端机冷启动 首帧 < 1s，用户感知「打开就能操作」< 2s。把预算拆细：Engine 150ms + Dart 100ms + 首帧 300ms + Raster 60ms ≈ 610ms，剩下留给系统。

bash
# 采集启动 trace（必须 profile 或 release，debug 下数据无意义）
flutter run --profile --trace-startup

# trace 默认写到 build/startup_trace.json，可直接拖进 Perfetto / chrome://tracing

别用秒表测启动

人眼掐表误差 200ms 起，且掩盖了「卡在哪一段」。trace 里能精确到 main() 入口、首帧 build 起点、首帧上屏三个时间点，差值就是你要还的债。

读懂启动 trace ​

打开 build/startup_trace.json 后关注这几条：

事件 / 标记含义用途
Engine::Run / DartIsolate::Run引擎与 isolate 启动Engine 段耗时
mainDart 入口执行你写的同步代码占了多少
Frame（第一条）首帧 build/layout/paint首帧 Dart 成本
Raster（第一条）首帧光栅化首帧 GPU 成本
timeToFirstFrame汇总指标优化前后对比的唯一基准

TimelineSummary（flutter_driver 里的工具类）能把 trace 汇总成 timeToFirstFrame、timeToFirstFrameRasterized 等指标，适合放进脚本做回归对比。

判定规则很简单：

  • main 段很长 → 你在 main() 里干了重活（初始化 SDK、读缓存、解析 JSON、建数据库）
  • main 很短但首帧 Frame 很长 → 首屏 Widget 太多，或首帧就触发大图解码
  • Dart 都快、只有第一条 Raster 长 → 首帧用了模糊 / 大阴影 / shader 编译（见上一章）

延迟初始化：把重活挪到首帧之后 ​

最常见的错误写法：

dart
// ❌ main() 里串行 await，首帧被一直推迟
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await Firebase.initializeApp();      // 300ms
  final prefs = await SharedPreferences.getInstance(); // 200ms
  final config = await api.fetchConfig();              // 网络，500ms+
  runApp(const App());
}

正确做法：首帧只画必要 UI，重活排到首帧之后。

dart
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const App());
}

// 首帧渲染完成后才执行（不要在这里做同步长任务，否则下一帧就卡）
void _warmUp() {
  WidgetsBinding.instance.addPostFrameCallback((_) async {
    await _initAnalytics();   // 300ms 的重活，挪到首帧后
    await _preloadImages();   // 图片预热
  });
}
写法首帧时间首帧后体验
main() 里 3 个 await（合计 1.2s）约 1.3s 白屏进入即完整
只 runApp + 首帧后预热约 320ms 出骨架300~800ms 内补全数据

addPostFrameCallback 里别塞同步重活

它在「帧已提交」后执行，但仍占用 UI 线程。如果回调里同步跑 200ms 的计算，下一帧照样掉。重活应该是异步 IO，或丢进 Isolate。

骨架屏与 Splash ​

首帧不必等数据齐：先画背景色 + 骨架块，数据到了再替换。这样用户看到的是「正在加载」，而不是「白屏」。

dart
class HomePage extends StatelessWidget {
  const HomePage({super.key, required this.ready, required this.child});
  final bool ready;
  final Widget child;

  @override
  Widget build(BuildContext context) {
    // 骨架屏与真实内容结构一致，切换时不会跳动
    return AnimatedSwitcher(
      duration: const Duration(milliseconds: 200),
      child: ready ? child : const _SkeletonList(),
    );
  }
}

deferred import：按需加载代码 ​

把非首屏的重模块拆出去，首次使用时才加载：

dart
import 'heavy_report_page.dart' deferred as report;

Future<void> openReport() async {
  await report.loadLibrary();          // 首次调用才加载该库代码
  Navigator.of(context).push(
    MaterialPageRoute<void>(builder: (_) => report.ReportPage()),
  );
}

平台差异要实测

Web 上 deferred 会拆成独立 chunk，收益明确。移动端 AOT 受限于平台拆分机制（Android 需配合 deferred components / Play Feature Delivery 配置），否则 loadLibrary() 可能近似空操作。上线前一定用 trace 对比，别只看代码写了 deferred 就以为快了。

首屏 Widget 数量与首帧成本 ​

首帧的 build / layout / paint 成本大致与 Element 数量线性相关。经验值：

首屏 Element 数量首帧 build 耗时（中端机）评价
< 5005~12ms健康
500~150015~35ms需要精简
> 300040ms+首帧必掉，且内存压力大

压缩手段：

  • 首屏列表只用 ListView.builder，可见项 5~8 个，其余靠滚动懒加载；
  • 复杂卡片先渲染简化版（无阴影、无渐变），数据到位后再升级视觉；
  • 首帧避免 BackdropFilter（实时模糊）、ShaderMask、多层 ClipPath——它们既贵又容易触发 shader 编译；
  • RepaintBoundary 主要解决「后续帧重复重绘」，对首帧帮助有限，别指望它救首帧。
dart
// 首帧先画纯色占位，避免首屏就解码大图
Container(
  height: 180,
  color: Theme.of(context).colorScheme.surfaceContainerHighest,
)

原生侧启动：闪屏与引擎预热 ​

平台关键文件 / API要点
Androidlaunch_background.xml、Android 12+ SplashScreen API闪屏背景色必须与首帧 Scaffold 背景一致，否则「闪白」
iOSLaunchScreen.storyboard系统会缓存启动图，只能是静态内容，不能放动画
双端FlutterEngineGroup预热 / 复用引擎，减少 50~150ms Engine 初始化

Android 上预热引擎的典型写法（Kotlin）：

kotlin
// 在 Application 或首屏 Activity 创建时预热，Dart 入口先不跑首屏逻辑
val group = FlutterEngineGroup(this)
val engine = group.createAndRunEngine(this, DartExecutor.DartEntrypoint.createDefault())
// 真正进入 Flutter 页面时复用该 engine，省掉一次 Engine 初始化

闪屏的「无缝」标准

把闪屏图片 / 背景色和首帧第一屏的背景做成同一个颜色，用户就感知不到「启动→首帧」的切换。多数「启动慢」的投诉，其实是闪屏与首帧色差造成的闪烁感。

可运行示例 ​

DartPad 运行环境将在滚动到此处时加载…
查看完整源码
dart
import 'package:flutter/material.dart';

// 延迟初始化：先出骨架屏（首帧），再把重活挪到首帧之后
void main() => runApp(const MaterialApp(home: _StartupPage()));

class _StartupPage extends StatefulWidget {
  const _StartupPage();
  @override
  State<_StartupPage> createState() => _StartupPageState();
}

class _StartupPageState extends State<_StartupPage> {
  bool _deferred = true;
  bool _loading = true;
  String _status = '准备启动';
  int _run = 0;

  @override
  void initState() {
    super.initState();
    // 首帧提交后才开始初始化，避免在 initState 里同步做重活
    WidgetsBinding.instance.addPostFrameCallback((_) => _begin());
  }

  void _begin() {
    final run = ++_run; // 每次重跑加序号，过期的回调直接丢弃
    setState(() {
      _loading = true;
      _status = _deferred ? '首帧已上屏，后台开始预热' : 'main() 里同步预热（首帧被推迟）';
    });
    Future<void>.delayed(Duration(milliseconds: _deferred ? 700 : 1400), () {
      if (!mounted || run != _run) return;
      setState(() {
        _loading = false;
        _status = _deferred ? '首帧 320ms 出骨架，数据随后补全' : '白屏 1.4s 后才出首帧';
      });
    });
  }

  @override
  Widget build(BuildContext context) {
    final scheme = Theme.of(context).colorScheme;
    return Scaffold(
      appBar: AppBar(title: const Text('启动与延迟初始化')),
      body: Padding(
        padding: const EdgeInsets.all(16),
        child: Column(
          crossAxisAlignment: CrossAxisAlignment.start,
          children: <Widget>[
            SegmentedButton<bool>(
              segments: const <ButtonSegment<bool>>[
                ButtonSegment<bool>(value: true, label: Text('首帧后预热')),
                ButtonSegment<bool>(value: false, label: Text('main() 阻塞')),
              ],
              selected: <bool>{_deferred},
              onSelectionChanged: (s) {
                setState(() => _deferred = s.first);
                _begin();
              },
            ),
            const SizedBox(height: 8),
            SizedBox(height: 170, child: _loading ? _skeleton(scheme) : _content(context)),
            const SizedBox(height: 8),
            Text(_status, style: TextStyle(color: scheme.primary)),
            OutlinedButton(onPressed: _begin, child: const Text('重新模拟一次启动')),
            const Spacer(),
            const Text('真实项目：runApp 之前不要 await 网络/数据库；骨架屏与首屏结构保持一致。'),
          ],
        ),
      ),
    );
  }

  // 骨架屏：首帧就能画出来的轻量占位
  Widget _skeleton(ColorScheme scheme) => Column(
        children: <Widget>[
          for (var i = 0; i < 3; i++)
            Container(
              height: 32,
              margin: const EdgeInsets.only(bottom: 10),
              decoration: BoxDecoration(
                color: scheme.surfaceContainerHighest,
                borderRadius: BorderRadius.circular(8),
              ),
            ),
          const Text('骨架屏（首帧内容）'),
        ],
      );

  Widget _content(BuildContext context) => Center(
        child: Card(
          child: Padding(
            padding: const EdgeInsets.all(20),
            child: Text('首屏真实数据已就绪',
                style: Theme.of(context).textTheme.titleMedium),
          ),
        ),
      );
}

常见坑 ​

高频踩坑点

  1. main() 里同步做重活：任何 await 都会推迟 runApp，网络请求更是把首帧交给运气。
  2. 首帧前发网络请求：请求失败 / 超时会直接拖长白屏；首屏数据应「先骨架、后填充」。
  3. 同步读 SharedPreferences：Android 的 getSharedPreferences 是同步磁盘读，主线程上可能几十毫秒；用异步 API 或首帧后再读。
  4. 闪屏与首帧背景不一致：最典型的「启动闪白」，改一个颜色就能消除。
  5. addPostFrameCallback 里再 setState 不判 mounted：页面已销毁时回调仍可能触发，抛异常并拖住 State。
  6. 用 debug 模式评估启动：debug 下 JIT + 断言会让 main() 慢数倍，必须用 profile / release 复测。

课后练习 ​

  1. 采集基线：给你现有的 demo 跑 flutter run --profile --trace-startup，从 trace 里读出 main 段与首帧 Frame 段耗时，写进一张表。
  2. 延迟初始化改造：在 main() 里人为加 3 个 300ms 的 await，测首帧时间；改成首帧后预热 + 骨架屏，再测一次，给出前后对比（验证方法：同一台设备、同一份 trace 工具）。
  3. 首屏瘦身：把首屏 Element 数量从 1000+ 压到 500 以内（简化卡片、列表懒加载），记录首帧 build 耗时变化。
  4. 闪屏对齐：把 Android launch_background.xml 与 iOS LaunchScreen.storyboard 的背景色改成与首帧 Scaffold 一致，冷启动录屏确认无闪白（验证方法：录屏逐帧看）。 :::
