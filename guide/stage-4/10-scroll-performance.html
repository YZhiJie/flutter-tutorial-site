列表与滚动性能 ​

学习目标 ​

学完本章，你将能够：

  • 说清滚动时 itemBuilder 的调用频率，以及 60fps / 120fps 下每帧的预算
  • 用 itemExtent / prototypeItem 跳过逐项测量，用 cacheExtent 平衡预构建与内存
  • 组合 SliverList、SliverAppBar、SliverPersistentHeader 构建 CustomScrollView
  • 判断 addAutomaticKeepAlives / addRepaintBoundaries 的隐性开销，正确使用 RepaintBoundary
  • 用 precacheImage、cacheWidth 与分页懒加载消除滚动中的图片抖动
  • 用 --profile + Timeline / addTimingsCallback 量化滚动帧耗时

一帧只有 16.7ms

60fps 下每帧预算 16.7ms，120Hz 设备只有 8.3ms。这 16.7ms 要同时完成 build、layout、paint、光栅化。列表滚动时每帧都在为「新滑入视口的 item」跑 build 与 layout，任何一项超预算就会掉帧（jank）。

滚动时到底发生了什么 ​

ListView.builder 并不是「滑到哪建到哪」那么简单。每一帧，视口会重新确定可见区间：

  1. 根据当前滚动偏移，算出需要显示的 item 下标范围
  2. 对新进入缓存区的 item 调用 itemBuilder
  3. 已显示且未离开缓存区的 item，直接复用已有 Element，不重新 build
  4. 离开缓存区的 item 被回收（State 随之 dispose）

因此滚动的开销约为「每帧新建 1-3 个 item」+「所有可见 item 的 layout/paint」。常见误区是「我已经用了 builder，为什么还卡」——builder 只解决建多少，不解决每项建得多贵。

现象根因优先检查
一滑就掉帧item 内部 build 太重itemBuilder 里有没有解析、格式化、深拷贝
滚动发涩、帧时间锯齿固定高度却未声明 extentitemExtent / prototypeItem
内存随滚动上涨keep-alive 或图片缓存过大addAutomaticKeepAlives、cacheWidth
滑动时整屏重绘缺少 repaint 边界RepaintBoundary / addRepaintBoundaries

三个决定成本的参数 ​

dart
ListView.builder(
  itemCount: 2000,
  itemExtent: 64,                       // ① 固定高度：跳过逐项测量
  cacheExtent: 300,                     // ② 视口外预构建的像素范围（默认 250）
  addAutomaticKeepAlives: false,        // ③ 不需要保活的 item 关掉
  addRepaintBoundaries: true,           // 默认 true，每项自动包 RepaintBoundary
  itemBuilder: (context, i) => _Row(i),
)
  • itemExtent：告诉框架每项高度，layout 时直接算位置，省掉「先测再摆」的两遍布局。适合聊天、表格、设置项这类等高列表。
  • prototypeItem：高度不固定但类型相同时，用一个原型 item 量一次，所有 item 沿用该尺寸。与 itemExtent 二选一。
  • cacheExtent：视口上下各预构建多少像素。调大能让快速滑动更顺，但会同时驻留更多 item 和图片，内存吃紧时反而更卡。

itemExtent 用错会裁切内容

itemExtent 是强制约束，内容会被压进固定高度，多行文本可能被截断或溢出。可变高度卡片不要硬套；改用 prototypeItem 或让框架自行测量。

Sliver：把滚动拆成可组合的片段 ​

CustomScrollView 是更底层的滚动容器，每个子节点都是 Sliver（可滚动片段）。列表只是其中一种：

dart
CustomScrollView(
  slivers: [
    const SliverAppBar(pinned: true, title: Text('消息')),
    SliverToBoxAdapter(child: _Banner()),
    SliverList(
      delegate: SliverChildBuilderDelegate(
        (context, i) => _MessageTile(i),
        childCount: 500,
        addAutomaticKeepAlives: false,
        addRepaintBoundaries: true,
      ),
    ),
  ],
)

SliverList + SliverChildBuilderDelegate 与 ListView.builder 等价，但能和其他 Sliver（吸顶头、网格、横幅）拼在同一个滚动体系里，避免「列表套列表」导致的双层滚动和嵌套测量。

RepaintBoundary：该加与不该加 ​

RepaintBoundary 会把子树提升为一个独立合成层（Layer），子树重绘时不影响兄弟节点。收益与代价都很实在：

场景建议原因
列表项内容基本静态不必额外加ListView 默认已为每项加一层
某项内有独立动画（进度条、闪烁）加动画重绘不波及整个列表
每项都是复杂图表谨慎每个 Layer 都占显存，层数过多反而拖慢合成
长列表简单文本项可关 addRepaintBoundaries省掉每项一个 Layer 的内存

结论：先测再决定。简单列表关掉边界通常更快；有局部动画的项，手动包 RepaintBoundary 才是正解。

图片：滚动卡顿的头号来源 ​

图片解码在主 isolate 上发生，大图解码一次可能吃掉十几毫秒。三个动作：

dart
// ① 按显示尺寸解码，别让 4000px 原图进内存
Image.network(url, cacheWidth: 240, fit: BoxFit.cover)

// ② 提前预热：在用户滑到之前把下一屏图片放进 ImageCache
precacheImage(NetworkImage(nextUrl), context);

// ③ 占位与淡入，避免解码完成瞬间的布局跳动
FadeInImage.assetNetwork(
  placeholder: 'assets/placeholder.png',
  image: url,
  imageCacheWidth: 240,
)

分页懒加载则用滚动位置触发，且必须加锁防重入：

dart
_scroll.addListener(() {
  if (_loading) return;
  if (_scroll.position.extentAfter < 400) {
    _loading = true;
    _loadNextPage().whenComplete(() => _loading = false);
  }
});

ScrollController 的监听在一次滑动中会触发很多次，上面的 _loading 就是最便宜的节流；更复杂的场景可用 NotificationListener<ScrollEndNotification> 只在停止时判断。

测量滚动性能 ​

  1. 必须用 profile 模式：flutter run --profile（模拟器数据不可信）
  2. DevTools Performance 面板，点录制，滑动列表 5 秒，停止
  3. 看 Timeline 里每帧的 build / layout / paint 耗时，找最长的帧
  4. 打开 Track Widget Rebuilds，确认是不是有 item 在反复重建

想在代码里直接采样，用 SchedulerBinding.addTimingsCallback（下一章的示例会完整演示）：

dart
SchedulerBinding.instance.addTimingsCallback((timings) {
  for (final t in timings) {
    debugPrint('build=${t.buildDuration.inMicroseconds}us '
        'raster=${t.rasterDuration.inMicroseconds}us');
  }
});

可运行示例 ​

DartPad 运行环境将在滚动到此处时加载…
查看完整源码
dart
import 'dart:async';

import 'package:flutter/material.dart';

// 列表滚动性能演示：
// ① itemExtent 省去逐项测量 ② addRepaintBoundaries 控制每项图层
// 顶部计数展示滚动过程中 itemBuilder 被调用的次数。
void main() => runApp(const MaterialApp(home: _ScrollDemo()));

class _ScrollDemo extends StatefulWidget {
  const _ScrollDemo();

  @override
  State<_ScrollDemo> createState() => _ScrollDemoState();
}

class _ScrollDemoState extends State<_ScrollDemo> {
  static const int _itemCount = 400;
  bool _useItemExtent = true;
  bool _repaintBoundaries = true;
  int _built = 0;
  final ValueNotifier<int> _counter = ValueNotifier<int>(0);
  Timer? _timer;

  @override
  void initState() {
    super.initState();
    // 每 500ms 刷新计数，避免在 itemBuilder 里直接 setState
    _timer = Timer.periodic(const Duration(milliseconds: 500), (_) {
      _counter.value = _built;
    });
  }

  @override
  void dispose() {
    _timer?.cancel();
    _counter.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('列表滚动性能')),
      body: Column(
        children: [
          SwitchListTile(
            value: _useItemExtent,
            title: const Text('itemExtent = 64（固定行高）'),
            onChanged: (v) => setState(() => _useItemExtent = v),
          ),
          SwitchListTile(
            value: _repaintBoundaries,
            title: const Text('addRepaintBoundaries'),
            onChanged: (v) => setState(() => _repaintBoundaries = v),
          ),
          ValueListenableBuilder<int>(
            valueListenable: _counter,
            builder: (context, built, _) => Padding(
              padding: const EdgeInsets.symmetric(horizontal: 16, vertical: 4),
              child: Text('itemBuilder 已调用 $built 次，滚动试试'),
            ),
          ),
          Expanded(
            child: ListView.builder(
              itemCount: _itemCount,
              itemExtent: _useItemExtent ? 64 : null,
              addRepaintBoundaries: _repaintBoundaries,
              itemBuilder: (context, index) {
                _built++;
                return _Row(index: index);
              },
            ),
          ),
        ],
      ),
    );
  }
}

class _Row extends StatelessWidget {
  const _Row({required this.index});

  final int index;

  @override
  Widget build(BuildContext context) {
    return Padding(
      padding: const EdgeInsets.symmetric(horizontal: 16, vertical: 8),
      child: Row(
        children: [
          CircleAvatar(child: Text('${index % 100}')),
          const SizedBox(width: 12),
          Expanded(child: Text('列表项 #$index')),
        ],
      ),
    );
  }
}

常见坑 ​

高频踩坑点

  1. 用了 builder 就以为万事大吉：item 内部若有 DateFormat、jsonDecode、排序，每帧新建几项照样超预算。重计算要提前算好或缓存。
  2. itemExtent 硬套可变高度：内容被裁切，且开发者以为是渲染 bug。可变高度用 prototypeItem 或默认测量。
  3. cacheExtent 越大越好：预构建项同样要走 build/layout，还常驻图片，低端机内存会先崩。
  4. 滥用 AutomaticKeepAliveClientMixin：每个保活项都常驻内存，几百项就是灾难；只给确有状态的项（如正在播放的音频）用。
  5. 列表里放 PlatformView：WebView、地图每帧跨平台桥接纹理，一屏多个必然卡；尽量用静态截图或原生浮层。
  6. 在 ScrollController 监听里做重活：监听每帧都触发，必须加锁/节流；否则一次滑动触发几十次请求。

课后练习 ​

  1. 量化 itemExtent：用配套示例的 400 项列表，分别在开/关 itemExtent 下滚动 5 秒，记录 DevTools 中最长帧的 build 时间，写出差值。
  2. RepaintBoundary 对照：给 10 个 item 各加一个无限旋转的 CircularProgressIndicator，对比「开启/关闭 addRepaintBoundaries」时的 raster 耗时与内存。
  3. 分页实现：实现滚动到底部自动加载下一页（每页 20 条，模拟 1 秒延迟），用计数器验证不会重复请求。
  4. 图片预热：构造 100 条网络图列表，先不做任何处理滚动一遍，再加入 cacheWidth + precacheImage，对比掉帧次数。
  5. CustomScrollView 改造：把示例列表改成 CustomScrollView，加入一个 SliverAppBar 吸顶头，验证滚动位置与吸顶行为。
