性能回归测试与门禁 ​

学习目标 ​

学完本章，你将能够：

  • 说明为什么「靠人眼看卡不卡」不可靠，以及性能数据需要怎样采样才稳定
  • 用 integration_test + flutter test / flutter drive 在真机上自动跑滚动、启动等场景
  • 用 traceAction 采集 Timeline，用 TimelineSummary 读出 build / raster 的分位数
  • 设计基线对比策略：多次采样取中位数、相对阈值、连续两次失败才报警
  • 理解 golden 测试的定位（视觉回归）与 --update-goldens 的正确用法
  • 在 CI 里搭一条性能门禁流水线，并配套回归看板与告警

性能测试和功能测试的区别

功能测试断言「结果对不对」，性能测试断言「分布有没有变差」。单次测量会被设备温度、后台进程、GC 打乱，所以性能门禁必须建立在**多次采样 + 统计量（中位数 / P90）**上，而不是一个孤立的数字。

为什么手动测不准 ​

同一份代码在开发者机器上滚得丝滑，到了用户的中端机上可能满屏 jank。原因：

  • 设备差异：GPU、内存带宽、屏幕刷新率（60/90/120Hz）都不同
  • 环境噪声：后台应用、电量模式、机身温度都会影响帧时间
  • 人为偏差：滑动的速度、距离、时机每次都不一样

所以性能回归必须满足三个条件：固定设备、固定操作脚本、固定统计口径。三者缺一，数据就不可比。

integration_test：把操作脚本化 ​

integration_test 是 Flutter SDK 自带的端到端测试框架（无需第三方包），测试代码跑在真实设备上：

dart
// integration_test/scroll_perf_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:integration_test/integration_test.dart';
import 'package:flutter_mastery_lab/main.dart' as app;

void main() {
  final binding = IntegrationTestWidgetsFlutterBinding.ensureInitialized();

  testWidgets('列表滚动 10 次', (tester) async {
    app.main();
    await tester.pumpAndSettle();

    for (var i = 0; i < 10; i++) {
      await tester.fling(find.byType(ListView), const Offset(0, -600), 1200);
      await tester.pumpAndSettle();
    }
  });
}

运行方式有两种：

bash
# 新版推荐：直接跑在已连接设备上
flutter test integration_test/scroll_perf_test.dart -d <device-id>

# 老项目常见：flutter drive 驱动
flutter drive \
  --driver=test_driver/integration_test.dart \
  --target=integration_test/scroll_perf_test.dart \
  -d <device-id>

test_driver/integration_test.dart 只需一行：

dart
import 'package:integration_test/integration_test_driver.dart';
Future<void> main() => integrationDriver();

必须用 profile 构建

flutter test integration_test/... 默认是 debug 构建，帧时间没有参考价值。要拿到可用于门禁的数据，必须用 flutter drive --profile 在真机上跑。

采集 Timeline：traceAction 与 TimelineSummary ​

IntegrationTestWidgetsFlutterBinding 提供 traceAction，把一段操作包进 Timeline 并输出报告：

dart
testWidgets('滚动性能采样', (tester) async {
  await binding.traceAction(() async {
    for (var i = 0; i < 10; i++) {
      await tester.fling(find.byType(ListView), const Offset(0, -600), 1200);
      await tester.pumpAndSettle();
    }
  }, reportKey: 'scroll_summary');
});

老的 flutter_driver 体系里，对应的 API 是 watchPerformance，返回 TimelineSummary：

dart
final summary = await driver.watchPerformance(
  () async {
    for (var i = 0; i < 10; i++) {
      await driver.scroll(find.byType(ListView), 0, -600, 800);
    }
  },
  timeout: const Duration(minutes: 2),
);

print(summary.averageFrameBuildTimeMillis);
print(summary.percentileFrameBuildTimeMillis(90));   // P90 比均值更能暴露抖动
print(summary.averageFrameRasterizerTimeMillis);
print(summary.missedFrameBuildBudgetCount);          // 超预算帧数
print(summary.missedFrameRasterizerBudgetCount);

门禁里真正有意义的指标：

指标含义建议阈值
averageFrameBuildTimeMillisUI 线程平均耗时≤ 8ms（留一半余量）
percentileFrameBuildTimeMillis(90)90% 的帧不超过此值≤ 12ms
missedFrameBuildBudgetCountbuild 超 16.7ms 的帧数0 或 ≤ 总帧数 1%
averageFrameRasterizerTimeMillis光栅化平均耗时≤ 8ms

看 P90 而不是平均值

平均值会被少数极快帧「拉平」，掩盖偶发卡顿。用户感知的是「最差的那几帧」，所以 P90/P95 更能代表体验。门禁建议同时卡平均值与 P90。

基线与阈值：让数据可比 ​

一次构建的数字没有意义，性能门禁的本质是同一设备上的前后对比：

  1. 在主干建立基线：同一脚本连续跑 5 次，取中位数（剔除首帧冷启动的离群值）
  2. PR 上跑同样的脚本，与基线比较
  3. 阈值采用相对值：build 时间不超过基线的 110%，P90 不超过 120%
  4. 噪声兜底：连续两次流水线都超标才阻断，单次失败先标记「可疑」
bash
# 简单可落地的对比脚本（读取采集出的 JSON）
BASE=$(jq -r '.p90_build_ms' baseline/perf.json)
CUR=$(jq -r '.p90_build_ms' current/perf.json)
LIMIT=$(awk "BEGIN { printf \"%.1f\", $BASE * 1.2 }")

echo "基线 P90=${BASE}ms，当前=${CUR}ms，上限=${LIMIT}ms"
awk "BEGIN { exit ($CUR <= $LIMIT) ? 0 : 1 }" \
  || { echo "::error::滚动 P90 回归超过 20%"; exit 1; }

设备矩阵与 CI 现实 ​

性能门禁最难的不是写测试，而是跑在什么设备上：

环境能否用于性能门禁原因
iOS 模拟器❌使用宿主 Mac 的 GPU，帧时间与真机完全不同
Android 模拟器❌无真实 GPU，raster 数据失真
本地真机✅适合日常验证
Firebase Test Lab✅可指定真机型号，适合规模化
自建设备农场✅设备固定、环境可控，最适合长期基线

CI 上的注意事项：

  • --profile 构建，关闭所有调试输出与动画干扰
  • 固定屏幕亮度、关闭自动亮度、锁定竖屏
  • 每台设备只跑一个任务，避免并行抢占 CPU/GPU
  • 结果连同设备型号、系统版本一起入库，跨设备的数据绝不互相比较

golden 测试：管视觉，不管帧率 ​

golden 测试把界面渲染成图片，与基准图逐像素比较，适合防止「改一处样式，顺手弄坏另一处」。它不是性能测试，但能兜住 UI 回归：

bash
# 首次生成或确认变更后更新基准图
flutter test --update-goldens

# CI 里禁止更新，只做比较；不一致即失败
flutter test

golden 图对平台敏感

字体渲染、抗锯齿在不同平台/版本上存在细微差异，golden 基准图应与 CI 使用同一环境生成。跨平台共享同一套基准图，会出现大量误报。

回归看板与告警 ​

数据只有被看见才有价值：

  1. 每次流水线把 {commit, device, build_ms, raster_ms, p90, missed_frames} 写入时序库
  2. 看板按周展示趋势线，标注发版点
  3. 连续 N 次超标 → 企业微信 / 飞书告警到性能负责人
  4. 发布前人工确认「性能趋势无异常」作为上线检查项

可运行示例 ​

DartPad 运行环境将在滚动到此处时加载…
查看完整源码
dart
import 'dart:ui' show FrameTiming;

import 'package:flutter/material.dart';
import 'package:flutter/scheduler.dart';

// 帧耗时采样：用 addTimingsCallback 采集 60 帧，输出 build / raster 的均值与 P90。
void main() => runApp(const MaterialApp(home: _FrameDemo()));

class _FrameDemo extends StatefulWidget {
  const _FrameDemo();
  @override
  State<_FrameDemo> createState() => _FrameDemoState();
}

class _FrameDemoState extends State<_FrameDemo>
    with SingleTickerProviderStateMixin {
  static const int _target = 60;
  late final AnimationController _controller;
  final List<FrameTiming> _samples = <FrameTiming>[];
  void Function(List<FrameTiming>)? _callback;
  bool _sampling = false;
  String _stats = '点击按钮，动画约 1 秒后统计 60 帧';

  @override
  void initState() {
    super.initState();
    _controller = AnimationController(
        vsync: this, duration: const Duration(seconds: 2));
  }

  @override
  void dispose() {
    if (_callback != null) SchedulerBinding.instance.removeTimingsCallback(_callback!);
    _controller.dispose();
    super.dispose();
  }

  void _start() {
    _samples.clear();
    setState(() { _sampling = true; _stats = '采集中…'; });
    _callback = _onTimings;
    SchedulerBinding.instance.addTimingsCallback(_callback!);
    // forward 只跑 2 秒，采样必定有限；平台无回调时也会自然结束
    _controller.forward(from: 0).whenComplete(_finish);
  }

  void _onTimings(List<FrameTiming> timings) {
    _samples.addAll(timings);
    if (_samples.length >= _target) _finish();
  }

  void _finish() {
    if (!_sampling || !mounted) return;
    _controller.stop();
    if (_callback != null) SchedulerBinding.instance.removeTimingsCallback(_callback!);
    _callback = null;
    if (_samples.length > _target) _samples.length = _target;
    if (_samples.isEmpty) {
      setState(() { _sampling = false; _stats = '未收到帧回调，请在真机上运行'; });
      return;
    }
    final build = _stat((t) => t.buildDuration);
    final raster = _stat((t) => t.rasterDuration);
    final text = '样本 ${_samples.length} 帧\n'
        'build 平均 ${build.$1.toStringAsFixed(1)}ms / P90 ${build.$2.toStringAsFixed(1)}ms\n'
        'raster 平均 ${raster.$1.toStringAsFixed(1)}ms / P90 ${raster.$2.toStringAsFixed(1)}ms';
    debugPrint(text);
    setState(() { _sampling = false; _stats = text; });
  }

  (double, double) _stat(Duration Function(FrameTiming) get) {
    final v = <double>[
      for (final t in _samples) get(t).inMicroseconds / 1000,
    ]..sort();
    final avg = v.reduce((a, b) => a + b) / v.length;
    return (avg, v[(v.length * 0.9).floor()]);
  }

  @override
  Widget build(BuildContext context) {
    return Padding(
      padding: const EdgeInsets.all(24),
      child: Column(
        crossAxisAlignment: CrossAxisAlignment.start,
        children: [
          LinearProgressIndicator(value: _sampling ? null : _controller.value),
          const SizedBox(height: 24),
          FilledButton(
            onPressed: _sampling ? null : _start,
            child: Text(_sampling ? '采集中…' : '开始采样 60 帧'),
          ),
          const SizedBox(height: 12),
          Text(_stats),
        ],
      ),
    );
  }
}

常见坑 ​

高频踩坑点

  1. debug 包跑性能测试：debug 的 JIT 与断言让帧时间翻倍，结论完全错误；门禁只认 profile/release。
  2. 在模拟器上建基线：模拟器没有真实 GPU，raster 时间虚高或虚低，基线一旦建立就永远不可信。
  3. 用单次采样做判断：一次抖动就报警，团队很快会忽略告警；至少 3-5 次取中位数，并设置连续失败条件。
  4. 平均值代替分位数：平均值掩盖长尾卡顿，必须同时看 P90/P95 与超预算帧数。
  5. 跨设备比较数据：把旗舰机的数据和低端机基线对比，等于拿两种尺子量身高。
  6. golden 在 CI 里随手 --update-goldens：等于把回归直接「转正」，基准图被悄悄改掉，门禁形同虚设。

课后练习 ​

  1. 脚本化一次滚动：给配套 App 写一个 integration_test，固定滑动 10 次，在真机上用 --profile 跑通，并打印总帧数与超预算帧数。
  2. 建立基线：同一台设备连续跑 5 次，记录 build 平均值与 P90，取中位数写入 baseline/perf.json。
  3. 制造回归：在列表 item 里加入 await Future.delayed 或重计算，观察 P90 是否超过 120%，验证门禁脚本能失败。
  4. golden 防护：给列表首屏生成一张 golden 图，然后修改 padding，确认 flutter test 变红，--update-goldens 后变绿。
  5. 看板设计：设计一张性能回归看板的字段（至少包含 commit、设备、P90、超预算帧数、趋势），说明告警规则。
