PlatformView 与混合渲染 ​

学习目标 ​

学完本章，你将能够：

  • 说清 PlatformView 的本质：把真实的 android.view.View / UIView 嵌进 Flutter 界面
  • 区分 Android 的 Virtual Display、Hybrid Composition、Texture Layer Hybrid Composition 三种模式
  • 理解 iOS 只有混合合成带来的能力限制与合成成本
  • 正确使用 AndroidView、UiKitView、PlatformViewLink，并知道各自对应哪种模式
  • 估算每帧纹理拷贝的数据量，解释「列表里放很多 PlatformView 就卡」的原因
  • 为 WebView、地图、相机、视频等场景做出选型，并掌握 Timeline 调试方法

PlatformView 是逃生舱

Flutter 的默认答案永远是「用 Flutter 重画」。只有当原生 SDK 只提供 View（地图、WebView、相机预览、广告）时才用 PlatformView；把原生能力包成 MethodChannel + Flutter UI，往往更快、更稳。

一、两套渲染体系如何叠在一起 ​

Flutter 自己维护一棵 Widget/RenderObject 树，最终由 Skia 或 Impeller 渲染成一张表面；而 android.view.View 和 UIView 属于系统原生的视图层级，两者不在同一个渲染管线里。

PlatformView 做的事情就是「把原生视图塞进来」，有两条路：

路径做法结果
纹理路径原生视图先渲染到一块纹理，Flutter 再把纹理当图片合成能参与 Flutter 的变换/裁剪，但有拷贝成本
视图层级路径原生视图直接插进系统视图层级，由系统合成器叠加触摸与原生控件行为最准，但 Flutter 与原生要各自合成

不管哪条路，都绕不开「每帧把原生画面同步到屏幕」这件事，这就是所有 PlatformView 性能问题的根源。

二、Android 的三种合成模式 ​

模式机制主要成本现状
Virtual Display（虚拟显示）原生 View 渲染到虚拟屏幕的纹理，Flutter 采样这张纹理每帧整帧拷贝、变换与裁剪受限Flutter 早期默认，现多被替代
Hybrid Composition（混合合成）原生 View 插入 Android 视图层级，Flutter 内容经 ImageReader 再交给系统合成合并 raster / platform 线程，复杂界面 FPS 下降需 PlatformViewLink + AndroidViewSurface 显式启用
Texture Layer Hybrid（纹理层混合）原生 View 渲染成纹理并上传给 Impeller，Flutter 直接合成每帧纹理上传，快速滚动易 jank当前 AndroidView 的默认实现
HCPP（实验）原生与 Impeller 各自渲染到 Surface，由 SurfaceFlinger 合成需要 Android API 34+ 且支持 VulkanFlutter 3.44+ 可用 initHybridAndroidView

不要假设「默认模式」永远不变

Flutter 会随版本调整默认合成策略，不同 Android 版本、不同 View 类型（如 SurfaceView）也会走不同分支。线上问题要按「实际设备 + 实际 Flutter 版本」排查，而不是背文档结论。

三、iOS：只有混合合成 ​

iOS 上没有虚拟显示，UiKitView 始终把原生 UIView 追加到 Flutter 的视图层级里，由系统合成：

  • 每个 PlatformView 前后会产生额外的 overlay 视图，页面里 PlatformView 越多，合成层越复杂。
  • ShaderMask、ColorFiltered 不支持作用在 PlatformView 上；BackdropFilter 也有限制。
  • Transform、Clip、Opacity 对原生视图有效，但每加一层都要额外合成，成本随之上升。
  • 原生视图上的滚动手势、输入框、无障碍行为由原生控件负责，Flutter 只能通过手势竞技场协调。

因此 iOS 上「一个页面一个 WebView / 一个地图」通常没问题，但「列表每行一个 WebView」几乎必然掉帧。

四、Dart 侧 API 对照 ​

最常见的写法是根据平台二选一：

dart
Widget build(BuildContext context) {
  const viewType = 'my_native_view';
  const params = <String, dynamic>{'title': '来自 Flutter'};
  if (defaultTargetPlatform == TargetPlatform.android) {
    return AndroidView(
      viewType: viewType,
      creationParams: params,
      creationParamsCodec: const StandardMessageCodec(),
    );
  }
  return UiKitView(
    viewType: viewType,
    creationParams: params,
    creationParamsCodec: const StandardMessageCodec(),
  );
}

需要精确控制 Android 模式时，用 PlatformViewLink + 对应的工厂方法：

工厂方法模式
PlatformViewsService.initAndroidViewVirtual Display（历史模式）
PlatformViewsService.initSurfaceAndroidViewTexture Layer Hybrid（默认）
PlatformViewsService.initExpensiveAndroidViewHybrid Composition
PlatformViewsService.initHybridAndroidViewHCPP（API 34+ / Vulkan）

PlatformViewLink 的骨架如下（surfaceFactory 返回 AndroidViewSurface，onCreatePlatformView 里创建控制器）：

dart
PlatformViewLink(
  viewType: 'my_native_view',
  surfaceFactory: (context, controller) => AndroidViewSurface(
    controller: controller as AndroidViewController,
    gestureRecognizers: const <Factory<OneSequenceGestureRecognizer>>{},
    hitTestBehavior: PlatformViewHitTestBehavior.opaque,
  ),
  onCreatePlatformView: (params) =>
      PlatformViewsService.initSurfaceAndroidView(
        id: params.id,
        viewType: 'my_native_view',
        layoutDirection: TextDirection.ltr,
        creationParams: const <String, dynamic>{},
        creationParamsCodec: const StandardMessageCodec(),
      )
        ..addOnPlatformViewCreatedListener(params.onPlatformViewCreated)
        ..create(),
)

点击穿透与手势冲突

PlatformView 默认像一个「洞」，Flutter 的点击可能被原生视图吃掉，原生控件也可能收不到 Flutter 手势。需要精确控制时设置 hitTestBehavior，并把 gestureRecognizers 传给 AndroidView / AndroidViewSurface，否则列表滑动、点击都会被原生层截胡。

五、成本模型：每帧拷贝与列表卡顿 ​

以 1080p 为例，一帧 RGBA 纹理是 1920 × 1080 × 4 ≈ 8.3 MB。如果每帧都要把整块纹理搬一次：

  • 60fps：8.3 MB × 60 ≈ 498 MB/s
  • 一个列表同时可见 3 个 1080p PlatformView：约 1.5 GB/s 的内存带宽
  • 再加上解码、缩放、合成，低端机的 GPU / 内存带宽会先于 CPU 饱和

这解释了三个常见现象：

  1. 列表里放 WebView 卡顿：每个可见 WebView 都在独立渲染并上传纹理，滚动时还会触发重新布局，成本是乘法的。
  2. 混合合成下复杂页面 FPS 下降：raster 线程与 platform 线程被合并，Flutter 的每一帧都要等原生视图就绪。
  3. 快速滚动时画面撕裂 / 空白：纹理上传与 Flutter 合成不同步，尤其容易出现在 TLHC 的快速滚动场景。

六、选型、替代方案与调试 ​

场景推荐原因
网页webview_flutter，单页少量使用本质仍是 PlatformView，数量一多就卡
地图官方地图插件必须用原生 SDK 的渲染与手势
相机预览camera 插件（纹理）纹理路径比 PlatformView 轻
视频video_player（纹理）避免把播放器 View 塞进列表
原生能力（扫码、支付、蓝牙）MethodChannel + Flutter UI只交换数据，不共享视图，成本最低
必须嵌入原生控件PlatformView，且控制数量没有替代方案时再用

官方也建议：动画进行时用截图纹理做占位，等动画结束再显示真正的 PlatformView，避免两套渲染每帧互相等待。

调试时重点看这些：

  • 用 flutter run --profile 跑真机，在 DevTools Performance 里展开 Raster / Platform 线程，搜索 PlatformView 相关事件（创建、mutator、纹理上传）。
  • 对比 --enable-impeller 与关闭 Impeller 的表现，Impeller 下 PlatformView 的合成路径不同，问题也会不同。
  • 检查是否有 SurfaceView：它在某些模式下会导致无障碍、文字放大失效。
  • 用 flutter run --verbose 看平台视图创建日志，确认实际走的是哪种模式。

dart
import 'package:flutter/material.dart';

// 模拟 PlatformView：原生视图先渲染成纹理，再由 Flutter 合成。
// 关闭裁剪后可以看到：原生层的内容会溢出自己的槽位。
void main() => runApp(const _PvDemo());
class _PvDemo extends StatefulWidget {
  const _PvDemo();
  @override
  State<_PvDemo> createState() => _PvDemoState();
}
class _PvDemoState extends State<_PvDemo> with SingleTickerProviderStateMixin {
  late final AnimationController _c = AnimationController(
    vsync: this, duration: const Duration(seconds: 4));
  bool _clip = true; int _frames = 0; // 模拟「每帧重新上传纹理」的计数
  @override
  void initState() {
    super.initState();
    _c.addListener(() => _frames++);
    _c.repeat(reverse: true);
  }
  @override
  void dispose() {
    _c.dispose();
    super.dispose();
  }
  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        backgroundColor: const Color(0xFFF4F6FA),
        body: Padding(
          padding: const EdgeInsets.all(16),
          child: Column(children: [
            Row(children: [
              Expanded(
                child: Text(_clip ? '已启用 ClipRect 裁剪' : '已关闭裁剪：观察溢出')),
              Switch(value: _clip, onChanged: (v) => setState(() => _clip = v)),
            ]),
            Expanded(
              child: AnimatedBuilder(
                animation: _c,
                builder: (context, _) {
                  final shift = -70.0 + 140.0 * _c.value;
                  final native = OverflowBox(
                    minHeight: 0,
                    maxHeight: 220,
                    alignment: Alignment.topCenter,
                    child: SizedBox(
                      height: 220,
                      width: double.infinity,
                      child: CustomPaint(painter: _NativePainter(shift: shift)),
                    ),
                  );
                  return Stack(clipBehavior: Clip.none, children: [
                    Positioned.fill(
                      child: DecoratedBox(
                        decoration: BoxDecoration(
                          color: const Color(0xFFDDE3ED),
                          borderRadius: BorderRadius.circular(12),
                        ),
                        child: const Center(child: Text('Flutter 渲染层')),
                      ),
                    ),
                    // 「原生视图」槽位：高度 140，内容 220
                    Positioned(
                      left: 0, right: 0, top: 56, height: 140,
                      child: DecoratedBox(
                        decoration: BoxDecoration(
                          border: Border.all(color: Colors.blueGrey),
                          borderRadius: BorderRadius.circular(12),
                        ),
                        child: _clip ? ClipRect(child: native) : native,
                      ),
                    ),
                    Positioned(
                      right: 8, bottom: 8, child: Text('纹理更新 #$_frames')),
                  ]);
                },
              ),
            ),
            const Text('彩色块是模拟的原生视图，每帧平移一次；Flutter 浮层始终在上方。'),
          ]),
        ),
      ),
    );
  }
}
class _NativePainter extends CustomPainter {
  _NativePainter({required this.shift});
  final double shift;
  @override
  void paint(Canvas canvas, Size size) {
    canvas.drawRect(Offset.zero & size, Paint()..color = const Color(0xFF0F766E));
    final grid = Paint()..color = Colors.white.withValues(alpha: 0.25);
    final offset = shift % 40;
    for (var x = -40.0; x < size.width + 40; x += 40) {
      canvas.drawLine(
          Offset(x + offset, 0), Offset(x + offset, size.height), grid);
    }
    for (var y = 0.0; y < size.height; y += 40) {
      canvas.drawLine(Offset(0, y), Offset(size.width, y), grid);
    }
    canvas.drawCircle(
        Offset(size.width / 2 + shift, size.height / 2),
        16,
        Paint()..color = const Color(0xFFF59E0B));
  }
  @override
  bool shouldRepaint(covariant _NativePainter old) => old.shift != shift;
}

常见坑 ​

高频踩坑点

  1. 把 PlatformView 当普通 Widget 用：它不参与 Flutter 的绘制树，ClipRect、ShaderMask、透明度等不一定生效。
  2. 列表每项一个 PlatformView：可见项 × 每帧纹理上传，内存带宽直接爆掉；用缩略图 + 点击进入详情。
  3. 忘记传 creationParamsCodec：创建参数无法序列化，原生侧拿到的是空值或直接报错。
  4. 手势冲突：原生 WebView / 地图会吃掉滑动，Flutter 列表滚不动；需要显式配置手势识别器或改用原生滚动。
  5. 在 debug 下评估性能：debug 模式没有 AOT，PlatformView 的线程等待被放大；性能结论必须用 profile / release。
  6. 忽略 iOS 的合成限制：给 PlatformView 套 ShaderMask 或 ColorFiltered 不会生效，误以为是代码问题。

课后练习 ​

  1. 成本估算：一个 720×1280 的 PlatformView，RGBA 每帧多少 MB？60fps 下带宽多少？如果列表同时可见 4 个呢？
  2. 最小接入：写一个只显示原生 TextView 的 PlatformView，分别在 Android 与 iOS 跑通，并记录实际使用的合成模式。
  3. 模式对比：把同一个原生 View 分别用 initSurfaceAndroidView 与 initExpensiveAndroidView 创建，在 DevTools 里对比 Raster / Platform 线程耗时。
  4. 替代方案：把「获取设备型号」从 PlatformView 改成 MethodChannel，比较代码量与启动耗时。
  5. 调试实战：在一个含 WebView 的列表里快速滚动，用 Timeline 找到卡顿发生在纹理上传还是布局阶段，并写出优化方案。
