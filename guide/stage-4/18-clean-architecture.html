架构深化：Clean Architecture 与 Feature-first ​

学习目标 ​

学完本章，你将能够：

  • 说清 presentation / domain / data 三层的边界，以及「谁可以 import 谁」
  • 用依赖倒置与接口隔离，让 UI 不绑定具体的数据实现
  • 按 feature-first 组织 lib/features/<feature>/{data,domain,presentation}
  • 判断 use case 该不该拆，以及 Repository 与 DataSource 各自负责什么
  • 划清 core / shared 的共享边界，避免 feature 之间暗中耦合
  • 从 MVC 风格的代码增量迁移到 Clean，而不是推倒重来

本章定位

阶段四第 01 章解决「选 MVVM / Bloc / Riverpod」；本章解决更底层的问题：代码放在哪一层、层与层靠什么连接、规则怎样才不被随手破坏。

一、分层边界：三层各管什么 ​

层放什么禁止放什么可以依赖
presentation页面、Widget、控制器、UI 状态网络请求、SQL、JSON 解析domain（以及组合根注入的实现）
domain实体（Entity）、用例（UseCase）、仓库契约package:flutter、dart:iocore
dataRepository 实现、DataSource、DTO 与映射页面、BuildContext、导航domain、core

一句话记忆：domain 是「业务是什么」，data 是「业务数据从哪来」，presentation 是「业务长什么样」。依赖只能朝内：data → domain，presentation → domain；domain 谁也不依赖。

dart
// features/notes/domain/note_repository.dart
// 只有契约，没有任何实现细节
abstract class NoteRepository {
  Future<List<Note>> fetchAll();
  Future<void> save(Note note);
}

最常见的越界

presentation 里直接 import '../data/note_api.dart'，是 Clean 架构被撕开的第一道口子。一旦这样写，换网络库、加缓存、写单测都要改 UI。最简单的自检：domain 目录里出现 import 'package:flutter/material.dart' 就是错。

二、依赖倒置与接口隔离 ​

依赖倒置（DIP）把「高层依赖低层实现」翻转为「高层依赖抽象，低层实现抽象」。落到 Flutter 里就是：页面持有 NoteRepository 抽象，HttpNoteRepository 在启动时注入。

dart
// 组合根（composition root）：全项目唯一知道「用哪个实现」的地方
final NoteRepository noteRepository = switch (env) {
  'prod' => HttpNoteRepository(client: ApiClient()),
  _ => InMemoryNoteRepository(),
};

runApp(App(noteRepository: noteRepository));

接口隔离（ISP）要求调用方不被自己不用的方法绑架。一个「读写全包」的仓库，会让只读页面也依赖 save()，测试时不得不实现一堆空方法。

dart
// 需要拆分时，按调用方拆窄接口
abstract class NoteReader {
  Future<List<Note>> fetchAll();
}

abstract class NoteWriter {
  Future<void> save(Note note);
}

class NoteRepository implements NoteReader, NoteWriter { /* ... */ }

拆窄接口的代价是类变多。读与写总是被同一批调用方同时使用就先合并，出现「只读页面被迫依赖写方法」时再拆——接口隔离看的是调用方，不是方法数量。

三、feature-first 目录结构 ​

text
lib/
├── app/                        # 组装层：路由、DI、主题、启动
├── core/                       # 无业务含义的基础设施
│   ├── network/
│   ├── storage/
│   └── result.dart
├── shared/                     # 跨 feature 的领域能力
│   ├── auth/
│   └── user/
└── features/
    └── notes/
        ├── data/
        │   ├── note_repository_impl.dart
        │   ├── note_local_data_source.dart
        │   └── note_dto.dart
        ├── domain/
        │   ├── note.dart
        │   ├── note_repository.dart
        │   └── watch_notes.dart
        └── presentation/
            ├── notes_page.dart
            ├── notes_controller.dart
            └── widgets/note_tile.dart

三条命名与归属约定：

  1. 一个 feature 一个目录，内部固定三层；暂时没内容的层可以不建，但不放空文件夹。
  2. features/a 不允许 import features/b 的 data / presentation；要复用先上移到 shared。
  3. 只被一个 feature 使用的 Widget 留在该 feature 的 presentation/widgets，被两个以上 feature 复用再进 design_system。

页面少、团队 1~2 人时，layer-first（lib/data、lib/domain 全局分层）更直接；页面多、多人并行时，feature-first 才划算。

四、use case 的粒度与 Repository / DataSource 职责 ​

use case 表达「一个用户意图」，而不是「一次接口调用」：

dart
// 值得存在的 use case：组合两个仓库 + 业务规则
class CheckoutOrder {
  CheckoutOrder(this._orders, this._payments);
  final OrderRepository _orders;
  final PaymentRepository _payments;

  Future<Receipt> call(OrderDraft draft) async {
    final order = await _orders.create(draft);
    return _payments.charge(order);
  }
}

判断信号：只做 return _repo.x() 透传 → 不拆；组合多个仓库、有业务规则、或页面之外还有入口要复用 → 拆；只是换个名字 → 不拆。

Repository 面向业务、返回领域实体、负责组合缓存与网络并隐藏来源；DataSource 面向技术、返回 DTO 或原始数据、只负责一个具体来源（HTTP、SQLite、内存）。

dart
// DTO 与实体分离：JSON 结构变化不会污染业务层
Note toEntity(NoteDto dto) => Note(id: dto.id, title: dto.title);

五、跨 feature 共享与过度抽象 ​

共享代码分三类放：

  • core/：没有业务含义，例如 HTTP 客户端、日志、Result<T>、时间工具。
  • shared/：有业务含义但跨 feature，例如登录会话、当前用户资料。
  • design_system/：主题 token 与纯 UI 组件，不依赖任何业务实体。

过度抽象的三个信号

  1. 一个方法只有一行 return _next.x()，调用链却有五层。
  2. 90% 的类只有一个调用方，而且从来没有被替换过。
  3. 改一个字段要同时动 6 个文件。

出现其中任意两个，就删掉中间层。Clean 的目标是边界清晰，不是层数多。一个只有 3 个页面的项目，UI + Repository 两层通常就够了。

六、从 MVC 到 Clean 的增量迁移 ​

不要一次性重写。按下面五步，每一步都能独立提交、独立回滚：

  1. 搬目录：建 features/<name>/presentation，把页面原样搬进去，行为不变。
  2. 抽接口：把 Widget 里的网络 / 数据库调用挪进 data，domain 只留抽象仓库。
  3. 减负控制器：业务规则移入纯 Dart（可单测），Widget 只读状态。
  4. 按需拆 use case：以「出现第二个调用方」为信号，不为每个 Repository 方法都包一层。
  5. 加护栏：用 import_lint 或自定义脚本限制越界 import，接进 CI。

迁移期的双轨制

迁移中允许旧页面继续走老路径，但新代码必须走新分层。给旧代码列一张清单和截止时间，否则「临时兼容」会变成永久架构。

七、依赖图与循环依赖检测 ​

bash
# 1. 看包级依赖（谁依赖了谁）
dart pub deps --style=compact

# 2. 找越界 import：data 层反向引用 presentation
rg "import .*presentation" lib/features/*/data

# 3. 按规则检查（需在 pubspec 加入 import_lint）
dart run import_lint

# 4. 在 CI 里跑静态分析与自定义脚本
dart analyze && dart run tool/check_layers.dart

文件级循环依赖不会全部被 dart analyze 拦下，常见做法是：

  • 写 tool/check_layers.dart，扫描 lib/features/* 的 import，输出跨 feature 或反向依赖的边；
  • 把结果与白名单比对，出现新违规就 exit(1)；
  • 在 code review 里要求新增依赖必须先更新规则表。

循环依赖的最小修复

A 依赖 B、B 又依赖 A，通常不是「缺一个工具类」，而是职责放错了层。先把共用部分下沉到 core 或 domain，再让两边依赖抽象，循环往往自然消失。

dart
import 'package:flutter/material.dart';

// 18 · 依赖倒置：UI 只依赖抽象仓库，换实现不改 UI
// domain 层：实体与契约（纯 Dart，不 import Flutter 之外的实现细节）
class Note {
  const Note(this.id, this.title);
  final String id;
  final String title;
}

abstract class NoteRepository {
  Future<List<Note>> fetchAll();
}

// data 层实现一：内存仓库，测试与离线场景零延迟
class MemoryNoteRepository implements NoteRepository {
  @override
  Future<List<Note>> fetchAll() async => const <Note>[
        Note('1', '依赖倒置：UI 只认接口'),
        Note('2', '实现类可以被随时替换'),
      ];
}

// data 层实现二：远端仓库，用延迟模拟网络
class RemoteNoteRepository implements NoteRepository {
  @override
  Future<List<Note>> fetchAll() async {
    await Future<void>.delayed(const Duration(milliseconds: 500));
    return const <Note>[
      Note('r1', '远端仓库已经接管'),
      Note('r2', 'UI 代码一行都没改'),
    ];
  }
}

// presentation 层：组合根在这里挑选实现，其余代码只依赖抽象
void main() => runApp(const MaterialApp(home: NotesPage()));

class NotesPage extends StatefulWidget {
  const NotesPage({super.key});
  @override
  State<NotesPage> createState() => _NotesPageState();
}

class _NotesPageState extends State<NotesPage> {
  NoteRepository _repository = MemoryNoteRepository();
  late Future<List<Note>> _notes = _repository.fetchAll();
  bool _remote = false;

  void _swap() {
    setState(() {
      _remote = !_remote;
      _repository = _remote ? RemoteNoteRepository() : MemoryNoteRepository();
      _notes = _repository.fetchAll();
    });
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('依赖倒置与 Repository')),
      body: ListView(
        padding: const EdgeInsets.all(16),
        children: <Widget>[
          const Text('presentation → NoteRepository（抽象）← data 实现'),
          const SizedBox(height: 8),
          FilledButton(
            onPressed: _swap,
            child: Text(_remote ? '切回内存仓库' : '切到远端仓库'),
          ),
          const SizedBox(height: 12),
          FutureBuilder<List<Note>>(
            future: _notes,
            builder: (context, snapshot) {
              if (snapshot.connectionState != ConnectionState.done) {
                return const Center(child: CircularProgressIndicator());
              }
              if (snapshot.hasError) {
                return Text('错误：${snapshot.error}');
              }
              return Column(
                children: <Widget>[
                  for (final note in snapshot.data ?? const <Note>[])
                    ListTile(
                      dense: true,
                      leading: CircleAvatar(child: Text(note.id)),
                      title: Text(note.title),
                    ),
                ],
              );
            },
          ),
        ],
      ),
    );
  }
}

常见坑 ​

高频踩坑点

  1. domain 里 import Flutter：实体或 use case 一旦依赖 BuildContext、Color，就无法在纯 Dart 测试里复用。
  2. Repository 直接返回 DTO / JSON：UI 被迫理解后端字段名。Repository 应该返回领域实体，映射放在 data 层。
  3. 每个方法都包 use case：大量一行透传类会让调用链变长、跳转变多，收益为零。
  4. feature 互相 import：feature_a 直接拿 feature_b 的页面或仓库，最后两个功能无法独立拆分、独立测试。
  5. 在 UI 里 new Repository：页面自己决定实现，等于把组合根散落各处，测试和多环境注入都会失效。
  6. 靠「能跑」容忍循环依赖：循环依赖会让单测无法隔离，最终只能整包跑集成测试。

课后练习 ​

  1. 换实现不改 UI：给一个已有页面抽 Repository 接口，写内存实现与「延迟 + 偶发失败」实现，用下拉框切换，确认页面代码零改动。
  2. 迁移一个页面：按本章五步，把项目里最脏的一个页面迁到 features/<name>/，每步单独提交，记录每步改动的文件数。
  3. 加护栏：写一个脚本扫描 lib/features，发现跨 feature import 或 data → presentation 就退出码 1，并接进 CI。
  4. 数调用方：列出项目里所有 use case，标出调用方数量；调用方为 1 且只做透传的，合并回 Repository。
