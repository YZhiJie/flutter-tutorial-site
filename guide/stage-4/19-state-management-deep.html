状态管理深水区 ​

学习目标 ​

学完本章，你将能够：

  • 掌握 Riverpod 的 autoDispose / family / keepAlive 三种生命周期开关
  • 用 riverpod_generator 与 build_runner 消除模板代码，并正确管理生成文件
  • 把 AsyncNotifier 的加载、成功、失败映射成正确的 UI 状态
  • 用 BlocObserver 观察事件与状态流，并用 blocTest 写纯 Dart 测试
  • 按变化频率拆分状态粒度，把重建范围压到最小
  • 给持久化状态设计版本号与迁移，避免升级后老用户白屏

本章要解决的问题

第 01 章解决「用哪个状态框架」。本章解决上线后才会痛的问题：谁该被销毁、刷新时旧数据要不要保留、一次变化重建了多少 Widget、版本升级后本地数据怎么迁移。

一、Riverpod 生命周期：autoDispose / family / keepAlive ​

Riverpod 的 Provider 默认一直活着；加了 .autoDispose 才会在没有监听者时销毁：

开关作用典型场景
.autoDispose最后一个监听者移除后销毁页面级数据、搜索结果
.family用参数创建多个独立实例按 id 查详情、按查询词搜索
ref.keepAlive()在 autoDispose provider 内部延长寿命退出页面后短时间保留缓存
dart
// 页面级：离开页面就释放
final searchQueryProvider = StateProvider.autoDispose<String>((ref) => '');

// 每个 noteId 一个实例，互不影响
final noteProvider =
    FutureProvider.family.autoDispose<Note, String>((ref, id) async {
  final link = ref.keepAlive(); // 手动保活，返回一个可关闭的句柄
  ref.onDispose(link.close); // 需要失效时主动关掉
  return ref.watch(noteRepositoryProvider).fetchById(id);
});

keepAlive 不是免费缓存

ref.keepAlive() 只是把销毁时机往后推。没有失效策略的保活会变成内存泄漏：数据永不过期，用户永远看到旧值。要么配合 ref.invalidate，要么设置 TTL 定时关闭句柄。

二、代码生成：riverpod_generator + build_runner ​

手写 Provider / NotifierProvider 的泛型容易写错。riverpod_generator 用注解生成 provider，类型由签名推导：在 dependencies 加入 riverpod_annotation，在 dev_dependencies 加入 build_runner 与 riverpod_generator，然后写注解：

dart
part 'note_list_provider.g.dart'; // build_runner 生成

@riverpod
class NoteList extends _$NoteList {
  @override
  Future<List<Note>> build() => ref.watch(noteRepositoryProvider).fetchAll();
}
bash
dart run build_runner build --delete-conflicting-outputs   # 生成一次
dart run build_runner watch --delete-conflicting-outputs   # 本地监听

生成结果是一个 noteListProvider，family 参数与 autoDispose 都能从方法签名推导。生成后的目录：

text
lib/features/notes/presentation/
├── note_list_provider.dart      # 手写：注解 + build()
└── note_list_provider.g.dart    # 生成：noteListProvider

生成文件的两条铁律

  1. *.g.dart 不要手改，下次 build 直接覆盖；要改行为就改注解源码。
  2. 生成文件必须提交到 Git。CI 里跑一次 build 后 git diff --exit-code，能发现「改了注解却忘了生成」。

三、AsyncNotifier 与 AsyncValue 的 UI 映射 ​

AsyncNotifier 把异步加载与状态变更收进一个类，状态是 AsyncValue<T>。它自带三种状态，UI 不该自己发明 loading 布尔值：

AsyncValue 状态含义UI
AsyncData(value)有可用数据渲染列表 / 内容
AsyncLoading()首次加载，没有旧值骨架屏 / 转圈
AsyncError(error, st)失败，没有旧值错误卡片 + 重试按钮
AsyncLoading(previous: data)刷新中，手里有旧值保留旧内容 + 顶部细进度条
dart
class NotesNotifier extends AsyncNotifier<List<Note>> {
  @override
  Future<List<Note>> build() async =>
      ref.watch(noteRepositoryProvider).fetchAll();

  Future<void> refresh() async {
    state = const AsyncLoading();
    // guard 把异常自动转成 AsyncError，不用手写 try-catch
    state = await AsyncValue.guard(
      () => ref.read(noteRepositoryProvider).fetchAll(),
    );
  }
}

刷新别把旧数据丢掉

下拉刷新时直接 AsyncLoading() 会让内容瞬间消失。用 skipLoadingOnReload: true，或在 builder 里用 valueOrNull 先渲染旧内容，体验差别非常明显。

四、Bloc 的 BlocObserver 与测试 ​

BlocObserver 是全局钩子，能在不改业务代码的前提下记录所有事件、状态变化和异常：

dart
class AppBlocObserver extends BlocObserver {
  @override
  void onChange(BlocBase<dynamic> bloc, Change<dynamic> change) {
    super.onChange(bloc, change);
    debugPrint('${bloc.runtimeType}: ${change.currentState} → ${change.nextState}');
  }
}

void main() {
  Bloc.observer = AppBlocObserver(); // 仅 debug 环境挂载
  runApp(const MyApp());
}

Bloc 是纯 Dart 类，测试不需要 testWidgets：

dart
blocTest<CounterBloc, int>(
  '点击加一后状态变为 1',
  build: () => CounterBloc(),
  act: (bloc) => bloc.add(const Increment()),
  expect: () => <int>[1],
);

五、不用框架：InheritedWidget 最小方案 ​

Flutter 自带的 InheritedWidget 就能做「向下传递状态 + 依赖变化重建」：

dart
class CounterScope extends InheritedWidget {
  const CounterScope({super.key, required this.count, required super.child});

  final int count;

  @override
  bool updateShouldNotify(CounterScope oldWidget) => count != oldWidget.count;
}

父级用新的 count 包一层 CounterScope，子孙通过 context.dependOnInheritedWidgetOfExactType<CounterScope>() 读取，count 变化时整棵依赖子树重建。

手写方案的边界

InheritedWidget 适合 1~2 个状态、层级很浅的小项目。一旦需要「只监听某个字段」「跨页面共享」「异步状态」，手写通知与依赖管理会比引入 Riverpod 贵得多。

六、可测性与状态粒度 ​

状态层的核心逻辑应该是纯函数或纯 Dart 类，测试不需要 BuildContext、不需要 pump：

dart
test('加两件后 items 与 total 都正确', () {
  const start = Cart(items: 0, total: 0);
  final twice = reduce(reduce(start, 'add'), 'add');
  expect(twice.items, 2);
  expect(twice.total, 18);
});

重建范围取决于「谁监听什么」：一个 ChangeNotifier 管全部时所有监听者都重建；多个 ValueNotifier / 多个 Provider 只重建对应监听者；ref.watch(provider.select(...)) 则只在字段变化时重建，适合大对象里的小字段。

按变化频率拆，而不是按业务拆

同一个页面里，「每秒变化的计时器」和「很少变的用户设置」应该分开存。按业务模块拆但把高频/低频状态混在一起，重建范围仍然很大。

七、全局 vs 局部，以及状态迁移与版本化 ​

全局放登录会话、主题、语言、Feature Flag，以及多个 feature 都要读、生命周期跟 App 一致的状态；局部放输入框内容、展开/折叠、单页筛选条件。原则是全局状态越少越好——只有当前页面关心的状态放进全局容器，会带来「谁都能改、谁都不敢删」的维护成本。

本地持久化还要面对版本升级：

dart
Map<String, Object?> migrate(Map<String, Object?> raw) {
  final version = raw['version'] as int? ?? 1;
  if (version < 2) raw['themeMode'] = 'system'; // 旧版本没有这个字段
  if (version < 3) raw['locale'] = 'zh';
  raw['version'] = 3;
  return raw;
}

迁移函数必须配旧数据 fixture 的单测；直接删字段或改 key，老用户数据解析失败会启动即白屏。

dart
import 'package:flutter/material.dart';

// 19 · 轻量 Notifier：纯函数状态机 + 极窄的重建范围
class CartState {
  const CartState({required this.items, required this.total});
  final int items;
  final int total;
  @override
  String toString() => 'items=$items total=$total';
}

// 纯函数 reducer：不依赖 Widget，可以直接写 unit test
CartState reduce(CartState state, String event) {
  switch (event) {
    case 'add':
      return CartState(items: state.items + 1, total: state.total + 9);
    case 'clear':
      return const CartState(items: 0, total: 0);
    default:
      return state;
  }
}

// 轻量 Notifier：自己管生命周期，只有状态真变了才通知
class MiniNotifier extends ChangeNotifier {
  MiniNotifier(this._state);
  CartState _state;
  CartState get state => _state;

  void emit(CartState next) {
    if (next.items == _state.items && next.total == _state.total) return;
    _state = next;
    notifyListeners();
  }

  void dispatch(String event) => emit(reduce(_state, event));
}

void main() => runApp(const MaterialApp(home: CartPage()));

class CartPage extends StatefulWidget {
  const CartPage({super.key});
  @override
  State<CartPage> createState() => _CartPageState();
}

class _CartPageState extends State<CartPage> {
  final MiniNotifier _cart =
      MiniNotifier(const CartState(items: 0, total: 0));
  int _rebuilds = 0;

  @override
  void dispose() {
    _cart.dispose(); // 建在 State 里，就由 State 负责销毁
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    // 纯函数自检：不需要 Widget，也不需要 pump
    final checked = reduce(reduce(const CartState(items: 0, total: 0), 'add'), 'add');
    return Scaffold(
      appBar: AppBar(title: const Text('手写轻量 Notifier')),
      body: Column(
        children: <Widget>[
          const SizedBox(height: 12),
          FilledButton.tonal(
            onPressed: () => _cart.dispatch('add'),
            child: const Text('加一件（+9 元）'),
          ),
          TextButton(
            onPressed: () => _cart.dispatch('clear'),
            child: const Text('清空'),
          ),
          // 只有这段子树订阅状态，重建范围被压到最小
          ListenableBuilder(
            listenable: _cart,
            builder: (context, _) {
              _rebuilds++;
              return Text('${_cart.state} · 重建 $_rebuilds 次');
            },
          ),
          const SizedBox(height: 12),
          Text('自检 reduce: $checked'),
        ],
      ),
    );
  }
}

常见坑 ​

高频踩坑点

  1. 把全局 Provider 当垃圾桶：所有页面状态都往全局塞，最后没人知道谁改了它、什么时候该清。
  2. autoDispose 与 keepAlive 同时滥用：保活没设失效策略，页面退出后数据一直占内存。
  3. 手改 *.g.dart：下次 build_runner 一跑就丢，还会以「代码没生效」的形式出现。
  4. 刷新时清空列表：AsyncLoading() 覆盖旧值导致内容闪烁，应该保留 previous。
  5. 状态粒度太粗：一个 Notifier 管十个字段，改一个字段整页重建，性能与可读性双输。

课后练习 ​

  1. 生命周期实验：写一个 autoDispose 的 FutureProvider.family，在两个页面间来回切换，用日志观察创建与销毁；再给其中一个加 keepAlive，对比行为。
  2. 代码生成迁移：把项目里 3 个手写 Provider 改成 @riverpod 注解，跑 build_runner，并在 CI 里加 git diff --exit-code 检查生成文件是否同步。
  3. AsyncValue 三态：实现一个列表页，覆盖首次加载、刷新保留旧值、失败重试三种 UI，并用假 Repository 手动触发每种状态。
