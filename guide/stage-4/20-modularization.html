模块化与 monorepo ​

学习目标 ​

学完本章，你将能够：

  • 用 melos 管理多包仓库：bootstrap、exec、run
  • 按 core / design_system / feature_x 划出清晰的包边界
  • 用 path 依赖做本地联调，用版本依赖做发布
  • 用 melos version 生成语义化版本与 CHANGELOG
  • 写脚本检查依赖方向，拦住跨 feature 与反向依赖
  • 配置 CI 按包增量构建，并判断什么时候不该上 monorepo

monorepo 不是「代码放一起」

monorepo（单仓库多包）的核心不是目录好看，而是包边界 + 版本规则 + 增量构建这三件事。没有它们，只是一个更大的单体仓库。

一、melos：多包仓库的调度器 ​

melos 是 Dart / Flutter 生态的多包管理工具，负责把 apps/ 与 packages/ 里的包当成一个工作区来安装、执行命令和发布。

text
my_workspace/
├── melos.yaml
├── pubspec.yaml              # 工作区根（可选，用于统一 lint / 脚本）
├── apps/
│   ├── mobile/               # 面向用户的 App
│   └── admin/                # 第二个 App（可选）
└── packages/
    ├── core/                 # 网络、存储、Result、日志
    ├── design_system/        # 主题 token 与通用组件
    ├── domain/               # 实体与仓库契约（可选）
    └── feature_orders/       # 一个完整功能
yaml
# melos.yaml
name: my_workspace
packages:
  - apps/*
  - packages/*
command:
  bootstrap:
    usePubspecOverrides: true   # 本地用 path 覆盖，发布时仍走版本
bash
dart pub global activate melos
melos bootstrap                   # 链接本地包并安装依赖
melos exec -- flutter analyze     # 对每个包执行命令
melos run analyze                 # 执行 melos.yaml 里定义的脚本

melos 只负责调度

melos 不会替你构建 Flutter 产物，也不会自动解决版本冲突。它把「对每个包跑一条命令」变简单了，包内的工程配置仍要自己维护。

二、packages 怎么切 ​

包放什么允许依赖
coreHTTP 客户端、存储、Result、日志无业务包
design_system颜色 / 字体 token、通用组件core
domain实体、仓库契约、用例core
feature_orders该功能的 data / domain / presentationcore、domain、design_system
app路由、DI 组装、启动所有 feature 包

四条硬规则：

  1. app 可以依赖 feature；feature 不能依赖 app。
  2. 两个 feature 包之间不互相依赖，共享逻辑上移到 core 或 domain。
  3. core 不依赖任何业务包，保证它能在任意 App 里复用。
  4. design_system 不 import 业务实体，只认颜色、间距、组件。

三、path 依赖：本地联调与发布的分界 ​

monorepo 内用 path 依赖，改 core 立刻反映到 mobile，不用先发版：

yaml
# apps/mobile/pubspec.yaml
dependencies:
  app_core:
    path: ../packages/core
  design_system:
    path: ../packages/design_system
方式适用风险
path同仓库本地开发不能直接发布，路径写死
版本号（hosted）跨仓库、对外发布每次改动都要发版
git 依赖临时共享、私有仓库版本不可追溯，CI 容易漂移

dependency_overrides 只在临时排查用

dependency_overrides 会绕过版本约束，本地能跑不代表 CI 能跑。合并前必须删掉，否则线上可能拉到不兼容的版本。

四、版本与发布：melos version ​

monorepo 的版本要跟着包走，而不是整个仓库一个版本号：

bash
# 根据 conventional commits 计算每个包的下一个版本，更新 CHANGELOG
melos version --yes

# 发布到 pub（内部包也可以只打 tag）
melos publish --no-dry-run

约定：

  • 提交信息用 feat: / fix: / BREAKING CHANGE:，melos 才能算对版本。
  • 每个包独立 CHANGELOG.md，tag 形如 app_core-v1.2.0。
  • app 用版本号依赖已发布的包；发布前先 melos bootstrap 验证。

不要手改版本号

手改 pubspec.yaml 的 version 会跳过 CHANGELOG 与 tag 计算，下一次 melos version 直接冲突。版本只能由工具生成。

五、依赖方向约束：让规则可执行 ​

包边界靠人记不住，要写成脚本。下面这个检查器只允许 feature 包依赖自己的代码：

dart
// tool/check_deps.dart
import 'dart:io';

void main() {
  final packages = Directory('packages').listSync().whereType<Directory>();
  var bad = 0;
  for (final dir in packages) {
    final name = dir.path.split(Platform.pathSeparator).last;
    for (final file in dir.listSync(recursive: true).whereType<File>()) {
      if (!file.path.endsWith('.dart')) continue;
      final text = file.readAsStringSync();
      for (final m in RegExp(r'package:(feature_[a-z_]+)/').allMatches(text)) {
        if (m.group(1) != name) {
          stdout.writeln('跨 feature 依赖: ${file.path} → ${m.group(1)}');
          bad++;
        }
      }
    }
  }
  exit(bad == 0 ? 0 : 1);
}
bash
dart run tool/check_deps.dart

更细的规则可以用 import_lint 声明「本包禁止 import 哪些前缀」，把它接进 CI 的 analyze 阶段。

规则检查要进 CI

依赖方向检查放在 code review 里靠人看，迟早会漏。放进 CI 后，违规 import 直接红，修复成本最低。

六、构建缓存与 CI 按包增量 ​

只改一个 feature 包，没必要把所有包的分析、测试、构建都跑一遍：

bash
# 只对自 origin/main 以来发生变化的包执行
melos exec --since=origin/main -- flutter test

# 只对某个包执行
melos exec --scope=feature_orders -- flutter analyze

# 按包并行跑测试（melos 会汇总退出码）
melos exec --concurrency=4 -- flutter test
缓存对象为什么值得缓存失效条件
pub 缓存依赖下载最慢pubspec.lock 变化
.dart_tool/分析器与构建索引SDK 或依赖变化
构建产物release 包体大、耗时长源码或资源变化

CI 的 cache key 至少包含 pubspec.lock 与各包的 pubspec.yaml。增量执行用 --since，缓存负责「没变的部分不重算」，两者配合才有效。

七、何时不该 monorepo / 多 App 共享 ​

适合 monorepo不适合 monorepo
多个 App 共享 core / design_system只有一个 App，团队 1~3 人
包边界稳定、发布节奏接近各团队发布节奏差异极大、权限要求严格
需要一次提交同时改多个包仓库体积已经拖慢 clone / CI

多个 App 共享代码时，共享包要只放稳定能力：主题、网络、基础组件。把某个 App 的临时业务塞进 core，第二个 App 立刻被绑架。

别把 monorepo 当复制粘贴

monorepo 的价值是复用与统一工具链，不是「把所有代码放进一个目录」。包边界模糊、版本不独立、CI 全量跑，这三点出现任意两个，就该重新评估是否拆分。

dart
import 'package:flutter/material.dart';

// 20 · 用纯 Dart 模拟「分层包 + 依赖方向检查」
enum Layer { core, domain, data, presentation }

String layerName(Layer layer) => switch (layer) {
      Layer.core => 'core',
      Layer.domain => 'domain',
      Layer.data => 'data',
      Layer.presentation => 'presentation',
    };

// 每个包允许依赖哪些层：依赖只能朝内，不能反向
const Map<Layer, Set<Layer>> allowedDeps = <Layer, Set<Layer>>{
  Layer.core: <Layer>{},
  Layer.domain: <Layer>{Layer.core},
  Layer.data: <Layer>{Layer.core, Layer.domain},
  Layer.presentation: <Layer>{Layer.core, Layer.domain},
};

class PackageNode {
  const PackageNode(this.name, this.layer, this.deps);
  final String name;
  final Layer layer;
  final List<PackageNode> deps;
}

List<String> violations(List<PackageNode> packages) {
  final result = <String>[];
  for (final pkg in packages) {
    for (final dep in pkg.deps) {
      if (!allowedDeps[pkg.layer]!.contains(dep.layer)) {
        result.add('${pkg.name}(${layerName(pkg.layer)})'
            ' → ${dep.name}(${layerName(dep.layer)})');
      }
    }
  }
  return result;
}

void main() => runApp(const MaterialApp(home: DepPage()));

class DepPage extends StatefulWidget {
  const DepPage({super.key});
  @override
  State<DepPage> createState() => _DepPageState();
}

class _DepPageState extends State<DepPage> {
  bool _illegal = false;

  List<PackageNode> _buildGraph() {
    const core = PackageNode('@app/core', Layer.core, <PackageNode>[]);
    const domain =
        PackageNode('@app/domain', Layer.domain, <PackageNode>[core]);
    final data = PackageNode('@app/data', Layer.data, <PackageNode>[
      core,
      domain,
      if (_illegal) const PackageNode('@app/ui', Layer.presentation, []),
    ]);
    const ui =
        PackageNode('@app/ui', Layer.presentation, <PackageNode>[core, domain]);
    return <PackageNode>[core, domain, data, ui];
  }

  @override
  Widget build(BuildContext context) {
    final graph = _buildGraph();
    final bad = violations(graph);
    final scheme = Theme.of(context).colorScheme;
    return Scaffold(
      appBar: AppBar(title: const Text('依赖方向检查')),
      body: ListView(
        padding: const EdgeInsets.all(16),
        children: <Widget>[
          const Text('规则：domain → core，data → core/domain，'
              'presentation → core/domain。反向 import 即违规。'),
          SwitchListTile(
            contentPadding: EdgeInsets.zero,
            title: const Text('注入违规：data 反向依赖 ui'),
            value: _illegal,
            onChanged: (value) => setState(() => _illegal = value),
          ),
          for (final pkg in graph)
            ListTile(
              dense: true,
              title: Text('${pkg.name}  (${layerName(pkg.layer)})'),
              subtitle: Text(pkg.deps.isEmpty
                  ? '无依赖'
                  : '依赖 ${pkg.deps.map((d) => d.name).join(', ')}'),
            ),
          const Divider(),
          Text(
            bad.isEmpty ? '检查通过：0 条违规' : '发现 ${bad.length} 条违规：',
            style: TextStyle(
              color: bad.isEmpty ? scheme.primary : scheme.error,
              fontWeight: FontWeight.bold,
            ),
          ),
          for (final line in bad)
            Text(line, style: TextStyle(color: scheme.error)),
        ],
      ),
    );
  }
}

常见坑 ​

高频踩坑点

  1. 所有包共用一个版本号：改 core 也要给 feature_orders 升版，版本历史很快失去意义。
  2. feature 包互相 import：两个功能无法独立删除或独立发布，monorepo 退化成单体。
  3. 在 core 里写业务：共享包一旦带上某个 App 的业务假设，其他 App 就无法复用。
  4. CI 每次都全量跑：包越多越慢，最后大家开始跳过 CI。
  5. 忘记提交生成文件或 CHANGELOG：发布 tag 与源码对不上，回滚时找不到对应代码。

课后练习 ​

  1. 搭一个三包工作区：创建 apps/mobile、packages/core、packages/design_system，用 melos bootstrap，让 mobile 同时依赖两个包。
  2. 写依赖检查：给 tool/check_deps.dart 增加规则——core 不允许 import 任何 feature 包，违规时退出码 1。
  3. 版本实验：用 conventional commits 提交一次 feat 与一次 fix，跑 melos version --yes（不发布），观察各包版本与 CHANGELOG 变化。
  4. 增量 CI：在 GitHub Actions 里用 melos exec --since=origin/main -- flutter test，对比全量测试的耗时。
