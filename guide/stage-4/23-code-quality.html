lint 与代码质量门禁 ​

学习目标 ​

学完本章，你将能够：

  • 按「官方推荐 → 团队规则 → 项目例外」三层组织 analysis_options.yaml
  • 在 CI 中正确使用 flutter analyze，让警告真正阻断合并
  • 用 dart fix --apply 批量修复，用 dart format 统一风格
  • 理解自定义 lint（analyzer plugin）的能力边界与性能代价
  • 搭建 analyze + format + test + coverage + 体积的五件套门禁
  • 用 Review 清单、PR 模板与技术债看板管理长期质量

质量门禁的目标

不是「零警告」这个数字，而是让坏代码进不了主干，让好代码不需要靠人盯。规则要少而硬，门禁要快而稳。

analysis_options.yaml 分层 ​

yaml
# 根目录 analysis_options.yaml
include: package:flutter_lints/flutter.yaml

analyzer:
  exclude:
    - "**/*.g.dart"
    - "**/*.freezed.dart"
    - "**/*.mocks.dart"
  language:
    strict-casts: true
    strict-inference: true
    strict-raw-types: true
  errors:
    invalid_annotation_target: ignore

linter:
  rules:
    prefer_const_constructors: true
    require_trailing_commas: true
    avoid_print: true
    unawaited_futures: true
    always_declare_return_types: true

分层建议：

层位置内容
官方推荐package:flutter_lints/flutter.yaml语言与框架通用规则
团队规则根 analysis_options.yaml团队共识：const、尾逗号、禁止 print
项目例外子包 / 目录级配置生成代码、脚本、测试的特殊豁免

子包用 include: ../../analysis_options.yaml 继承根规则，再只追加组件库专属规则（如 public_member_api_docs）。

规则不是越多越好

一次开 50 条新规则，PR 会全红，团队的第一反应是加 // ignore。每季度加 3-5 条，先修存量再开门禁，规则才有权威。

flutter analyze 与 CI ​

bash
flutter analyze                       # 人类可读
dart analyze --fatal-infos            # info 也当失败（更严格）
flutter analyze --no-fatal-warnings   # 临时排障用，别进 CI

CI 中的最小任务：

yaml
- name: Analyze
  run: flutter analyze --fatal-infos

要点：

  • CI 必须锁定 Flutter 版本，否则新 SDK 的新 lint 会让老代码突然变红。
  • analysis_options.yaml 与 pubspec.lock 都要进 Git，确保本地与 CI 同一套规则。
  • 生成代码（*.g.dart、*.freezed.dart）排除在分析之外，避免几万条噪音。
  • 增量治理：存量项目可先 --no-fatal-warnings 只挡 error，再逐步升级。

用 // ignore 要带原因

dart
// ignore: avoid_print // 启动脚本，必须在控制台输出
print('boot');

无理由的 ignore 应该在 Review 里被打回；团队可以统计 ignore 数量作为技术债指标。

dart fix --apply 与格式化 ​

bash
dart fix --dry-run        # 先看会改什么
dart fix --apply          # 应用可自动修复的 lint
dart format .             # 统一格式
dart format --set-exit-if-changed .   # CI 校验，未格式化则失败

格式宽度也可在 analysis_options.yaml 里用 formatter.page_width 统一（如 100）。

自动修复后必须跑测试

dart fix 会改语义敏感的地方（如 const 提升、构造器参数）。大批量 apply 后先跑 analyze + test 再提交，不要盲信工具。

自定义 lint 的原理与限制 ​

Dart 的 lint 建立在 analyzer 之上。custom_lint 通过 analyzer plugin 在分析阶段注入规则：在 dev_dependencies 加 custom_lint 与规则包，并在 analyzer.plugins 注册即可。

dart
class NoRepositoryInUi extends DartLintRule {
  const NoRepositoryInUi() : super(code: _code);
  static const _code = LintCode(
    name: 'no_repository_in_ui',
    problemMessage: 'UI 层不要直接构造 Repository。',
  );
  // runCustomLint 中遍历 AST，命中构造调用时 report
}

限制要提前知道：

限制影响
需要编译器/AST 知识写规则成本高，通常只做团队强约束
分析阶段执行规则过多会拖慢 IDE 与 CI
修复能力有限多数规则只能报错，不能自动 fix
生态绑定换分析器版本可能需要适配

先用现成规则，再写自定义

90% 的团队规范可以用内置 lint 表达。只有当规则涉及「跨文件语义」（如分层依赖、禁止某模块 import 某模块）时，自定义 lint 才划算。

质量门禁五件套 ​

门禁命令建议阈值
静态分析flutter analyze --fatal-infos0 issues
格式dart format --set-exit-if-changed .必须通过
测试flutter test全绿
覆盖率flutter test --coverage + lcov新增代码 ≥ 80%
体积release 产物对比基线增幅 ≤ 3%
bash
#!/usr/bin/env bash
set -euo pipefail
flutter analyze --fatal-infos
dart format --set-exit-if-changed .
flutter test --coverage

pct=$(lcov --summary coverage/lcov.info 2>&1 | grep -oE '[0-9.]+%' | head -1)
echo "coverage: $pct"
# 具体阈值判断交给 CI 脚本或 very_good_coverage

门禁要分级

PR 跑快门禁（analyze + format + 单测，3-5 分钟）；合并后跑慢门禁（集成测试 + 体积 + 性能基线）。不要让每个 PR 都等 40 分钟。

Review 清单与技术债看板 ​

Review 清单（按优先级）：

维度检查点
架构分层是否被打破？UI 是否直接碰数据层？
性能build 里是否有重活？列表是否缺 itemExtent？动画是否 dispose？
安全是否记录 PII？是否硬编码密钥？WebView 是否限制域名？
测试新增逻辑是否有单测？关键交互是否有 Widget 测试？
可维护性命名是否表达意图？是否有无理由的 ignore / TODO？

仓库配套：

markdown
<!-- .github/pull_request_template.md -->
## 变更说明
## 自测
- [ ] flutter analyze 通过
- [ ] dart format 通过
- [ ] 新增/修改逻辑有测试
## 风险与回滚
# .github/CODEOWNERS
/lib/features/checkout/  @team-checkout
/lib/core/network/       @team-platform

技术债看板建议四列：待评估 → 已确认 → 修复中 → 已偿还。每条债务写清「影响、触发条件、预估成本」，并在每个迭代固定留 10%-20% 容量偿还。

技术债不会自己消失

只记录不排期，看板会变成「愧疚墙」。把「高频出问题的模块」与「ignore 数量」作为输入，每季度挑 1-2 项真正修掉。

dart
import 'package:flutter/material.dart';

// 坏代码 → lint 规则修复的对照示例。
// 真实项目里执行 `dart fix --apply`，这里用开关模拟「修复前 / 修复后」。
void main() => runApp(const MaterialApp(home: _Demo()));

class _Fix {
  const _Fix(this.rule, this.bad, this.good);
  final String rule;
  final String bad;
  final String good;
}
const List<_Fix> _fixes = <_Fix>[
  _Fix('prefer_const_constructors', "Text('标题')", "const Text('标题')"),
  _Fix('avoid_print', "print('debug: \$value')", "debugPrint('debug: \$value')"),
  _Fix(
    'always_declare_return_types',
    'add(a, b) => a + b;',
    'int add(int a, int b) => a + b;',
  ),
  _Fix(
    'require_trailing_commas',
    "Column(children: [Text('A')])",
    "Column(\n  children: [\n    Text('A'),\n  ],\n)",
  ),
  _Fix('use_key_in_widget_constructors', 'const _Card()', 'const _Card({super.key})'),
];

class _Demo extends StatefulWidget {
  const _Demo();
  @override
  State<_Demo> createState() => _DemoState();
}
class _DemoState extends State<_Demo> {
  bool _fixed = false;
  @override
  Widget build(BuildContext context) {
    final scheme = Theme.of(context).colorScheme;
    return ListView(
      padding: const EdgeInsets.all(16),
      children: [
        SwitchListTile(
          contentPadding: EdgeInsets.zero,
          title: const Text('执行 dart fix --apply'),
          subtitle: Text(_fixed ? '5 条 lint 问题已自动修复' : '当前有 5 条 lint 问题'),
          value: _fixed,
          onChanged: (v) => setState(() => _fixed = v),
        ),
        Container(
          padding: const EdgeInsets.all(12),
          decoration: BoxDecoration(
            color: (_fixed ? scheme.primary : scheme.error)
                .withValues(alpha: 0.12),
            borderRadius: BorderRadius.circular(8),
          ),
          child: Row(
            children: [
              Icon(_fixed ? Icons.verified : Icons.warning_amber,
                  color: _fixed ? scheme.primary : scheme.error),
              const SizedBox(width: 8),
              Expanded(
                child: Text(
                  _fixed
                      ? '质量门禁：analyze 0 issues · format 通过 · test 通过'
                      : '质量门禁：analyze 报 5 条，CI 会在 PR 上直接打回',
                ),
              ),
            ],
          ),
        ),
        for (final fix in _fixes)
          Card(
            margin: const EdgeInsets.symmetric(vertical: 6),
            child: Padding(
              padding: const EdgeInsets.all(12),
              child: Column(
                crossAxisAlignment: CrossAxisAlignment.start,
                children: [
                  Text(
                    fix.rule,
                    style: TextStyle(
                        color: scheme.primary, fontWeight: FontWeight.w600),
                  ),
                  const SizedBox(height: 8),
                  Row(
                    children: [
                      Icon(_fixed ? Icons.check : Icons.close,
                          size: 16,
                          color: _fixed ? scheme.primary : scheme.error),
                      const SizedBox(width: 6),
                      Expanded(
                        child: Text(
                          _fixed ? fix.good : fix.bad,
                          style: TextStyle(
                            fontFamily: 'monospace',
                            fontSize: 12,
                            color: _fixed ? scheme.onSurface : scheme.error,
                          ),
                        ),
                      ),
                    ],
                  ),
                ],
              ),
            ),
          ),
      ],
    );
  }
}

常见坑 ​

高频踩坑点

  1. 规则开了却不修存量：CI 永久红，团队学会无视红色。先修存量，再开门禁。
  2. 全项目 // ignore_for_file：等于关掉分析器。ignore 必须精确到行并写原因。
  3. CI 用 latest Flutter：新版本新增 lint 让主干突然失败。锁定 SDK 版本，升级单独排期。
  4. 只跑 analyze 不跑 format：格式分歧制造无意义 diff，Review 噪音掩盖真实问题。
  5. 门禁只卡覆盖率数字：为了达标写无断言测试。覆盖率要结合「新增代码」和「关键路径」看。

课后练习 ​

  1. 三层配置：为你的项目写根 analysis_options.yaml，再给一个子包写继承配置，确认两边规则生效。
  2. 存量治理：统计当前 flutter analyze 的 issue 数量与 Top 5 规则，制定「4 周清零」计划。
  3. 自动修复：在一个分支跑 dart fix --apply，统计改动文件数与测试结果，评估风险。
  4. 自定义规则：用 custom_lint 写一条「禁止 UI 层 import data 层」的规则，在示例项目验证。
  5. 门禁流水线：把 analyze + format + test + coverage 串成一个脚本，本地一条命令跑完。
