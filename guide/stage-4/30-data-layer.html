网络与数据层工程化 ​

学习目标 ​

学完本章，你将能够：

  • 按 ApiClient → Interceptor → Repository → DTO/Entity 划分网络层职责
  • 用 Dio 拦截器统一处理鉴权、重试、日志与错误映射
  • 正确设置超时，并用 CancelToken 取消过期请求、避免响应竞态
  • 设计内存缓存、本地缓存与 HTTP 缓存头的组合策略
  • 实现 local-first、乐观更新、分页与增量同步，并处理冲突
  • 用依赖注入与内存 mock 让数据层可测试，理解 json_serializable / freezed 的取舍

分层原则

UI 只认 Entity（领域模型）和 Repository；DTO 是「网络传输格式」，只活在数据层；拦截器只做横切关注点，不写业务分支。分层清楚后，换网络库、加缓存、写测试都不会牵动页面。

一、分层：ApiClient / Interceptor / Repository / DTO ​

层职责不该做的事
ApiClient持有 Dio、BaseOptions、发起请求不写业务判断
Interceptor鉴权、日志、重试、错误归一化不直接改 UI 状态
Repository缓存策略、离线合并、对外暴露领域 API不暴露 DTO / Dio 类型
DTO与后端字段一一对应的序列化模型不掺业务方法
EntityUI 与领域使用的稳定模型不依赖 JSON 字段名
dart
class ApiClient {
  ApiClient(String baseUrl)
      : dio = Dio(BaseOptions(
          baseUrl: baseUrl,
          connectTimeout: const Duration(seconds: 10),
          receiveTimeout: const Duration(seconds: 15),
        ));
  final Dio dio;
}

Repository 持有 ApiClient 与缓存实现，对外只暴露 Entity，缓存与同步细节都不外泄。DTO → Entity 看起来「多此一举」，但它把后端字段变更隔离在数据层：后端把 avatar_url 改成 avatarUrl 时，只改 DTO 的 @JsonKey。

二、Dio 拦截器：鉴权、重试、日志与错误映射 ​

bash
flutter pub add dio
dart
dio.interceptors.add(InterceptorsWrapper(
  onRequest: (options, handler) {
    options.headers['Authorization'] = 'Bearer $token';
    handler.next(options); // 必须调用，否则请求不会继续
  },
  onError: (e, handler) async {
    final attempt = (e.requestOptions.extra['attempt'] as int?) ?? 0;
    final retryable = e.type == DioExceptionType.connectionError ||
        e.type == DioExceptionType.connectionTimeout ||
        (e.response?.statusCode ?? 0) >= 500;
    if (retryable && attempt < 2) {
      await Future<void>.delayed(Duration(milliseconds: 300 * (attempt + 1)));
      return handler.resolve(
          await dio.fetch<dynamic>(e.requestOptions..extra['attempt'] = attempt + 1));
    }
    handler.next(e);
  },
));
  • handler.next / resolve / reject 必须且只能调用一个，忘记调用会让请求永久挂起。
  • 只对幂等请求（GET、PUT、带 idempotency key 的 POST）自动重试，否则可能重复下单。
  • 重试要指数退避并设上限；401 刷新 token 需要加锁；错误统一映射成 ApiException(kind, message, statusCode)，UI 不直接判断 DioExceptionType。

401 刷新要串行化

多个请求同时收到 401 会并发触发 refresh，导致旧 token 覆盖新 token。用 Completer 或互斥锁，让第一个请求负责刷新，其余等待同一个 Future。

三、超时、取消与响应竞态 ​

超时有三类：连接、发送、接收。只设 connectTimeout 不够，长响应还需要 receiveTimeout。

dart
final token = CancelToken();
final future = dio.get<List<dynamic>>('/search',
    queryParameters: {'q': keyword}, cancelToken: token);
token.cancel('query changed'); // 用户继续输入或离开页面

try {
  await future;
} on DioException catch (e) {
  if (e.type == DioExceptionType.cancel) return; // 主动取消，不是错误
}

搜索框还要处理竞态：后发的请求可能先返回。给每次请求分配递增 id，只有最新 id 的结果才允许写入 UI；或者每次输入变化先取消上一个 token。

dart
int _requestId = 0;
Future<void> search(String q) async {
  final id = ++_requestId;
  final result = await api.search(q);
  if (id != _requestId) return; // 过期响应直接丢弃
  setState(() => _items = result);
}

页面 dispose 时取消所有在途 token，避免销毁后继续 setState。

四、缓存策略：HTTP 头 + 内存 + 本地 ​

层级实现命中条件适合
HTTP 缓存Cache-Control、ETag、Last-Modified浏览器/代理或 304可被标准缓存语义描述的资源
内存缓存Map + TTL + LRU进程内、短时间重复读列表页、详情页、搜索建议
本地缓存Hive / sqflite / 文件跨启动、离线可用用户数据、消息、离线内容

HTTP 缓存的关键头：

  • Cache-Control: max-age=60：60 秒内直接用缓存；no-store 禁止缓存敏感接口。
  • ETag + If-None-Match：再次请求带上 ETag，服务端返回 304 Not Modified 时复用旧 body。
  • Last-Modified + If-Modified-Since：按修改时间协商。

内存缓存要带 TTL：get 时检查 expiresAt，过期就删除并返回 null；put 时写入 now + ttl。读取路径还应记录命中率，否则无法判断缓存是否真的有效。

五、local-first、乐观更新与冲突解决 ​

local-first 把本地数据库当作唯一事实来源，UI 只订阅本地数据；同步引擎负责拉取服务端变更并推送本地写操作。

UI → Repository → Local DB（立即返回）
                 ↘ Sync Engine → Outbox → Server
Server → Sync Engine → Local DB → UI 自动更新

写操作走 Outbox：每条带 idempotency-key；失败按退避重试；永久失败标记为冲突交给用户；删除用 tombstone（deletedAt），否则同步时会被服务端旧数据「复活」。

dart
Future<void> toggleDone(Todo todo) async {
  final before = todo.done;
  todo.done = !before; // 本地立即生效
  notifyListeners();
  try {
    await api.updateTodo(todo);
  } catch (_) {
    todo.done = before; // 回滚
    notifyListeners();
    rethrow;
  }
}

冲突解决策略要提前定：

策略规则适用
Last-Write-Wins以 updatedAt 较新者为准简单字段、低冲突
Server Wins服务端版本覆盖本地配置、权限
Field Merge不同字段分别合并协作编辑
人工解决标记冲突让用户选择金额、库存等关键数据

乐观更新必须可回滚

只写「成功路径」的乐观更新，一旦请求失败，UI 会停留在错误状态且没有提示。每次本地改动都要保存旧值，失败时恢复并告知用户。

六、分页、增量同步与实时数据 ​

分页有两种方式：Offset/Limit 实现简单，但插入新数据时容易重复或漏项；Cursor 由服务端返回 nextCursor，适合时间线、消息流。客户端必须按 id 去重，刷新、重试、并发加载都可能返回重叠数据。

dart
final Set<int> _seen = {};
void append(List<Item> page) {
  for (final item in page) {
    if (_seen.add(item.id)) _items.add(item);
  }
  _hasMore = page.length == pageSize;
}

增量同步用 updated_since 拉变更，配合 tombstone 删除。实时数据方案：轮询简单但浪费请求；SSE 单向 text/event-stream，自动重连，适合通知/进度；WebSocket 双向，适合聊天、协作。SSE 重连时带 Last-Event-ID，客户端用 Stream 消费，页面销毁时取消订阅。

GraphQL 用单一端点、客户端声明字段，减少 over-fetching；代价是缓存与错误处理更复杂。没有明确痛点不必为「潮」而迁移。

七、序列化取舍与可测试性 ​

bash
flutter pub add json_annotation dev:json_serializable dev:build_runner
dart run build_runner build --delete-conflicting-outputs
方案优点代价
手写 fromJson零依赖、字段少时最快字段多易错
json_serializable生成 fromJson/toJson、支持 @JsonKey需要 build_runner
freezed不可变、copyWith、==、sealed union代码生成更重

DTO 少（1~2 个）可以手写；业务模型多、需要 copyWith / 状态联合类型时用 freezed。无论哪种，大 JSON 解析不要放在 UI isolate。

可测试性来自依赖注入：Repository 依赖 TodoApi 接口与 TodoCache，测试时注入内存实现，或用 Dio 的 HttpClientAdapter 返回固定响应；不要在业务代码里 new Dio()。本章示例用 _FakeApi 模拟延迟、缓存与在途去重，不联网、不依赖插件。

dart
import 'package:flutter/material.dart';

// 内存 mock：不联网，用 Future.delayed 模拟请求延迟。
void main() => runApp(const _DataLayerDemo());

class _Item {
  const _Item(this.id, this.title);
  final int id;
  final String title;
}

class _Repo {
  static const int pageSize = 8;
  final Map<int, List<_Item>> _cache = {};
  final Map<int, Future<List<_Item>>> _inflight = {};
  String last = '尚未请求';
  int requests = 0;
  int hits = 0;

  Future<List<_Item>> fetch(int page) {
    final cached = _cache[page];
    if (cached != null) {
      hits++;
      last = '第 $page 页：命中内存缓存';
      return Future<List<_Item>>.value(cached);
    }
    final pending = _inflight[page];
    if (pending != null) {
      hits++;
      last = '第 $page 页：复用在途请求';
      return pending;
    }
    requests++;
    last = '第 $page 页：发起请求';
    final future = Future<List<_Item>>.delayed(const Duration(milliseconds: 500), () {
      final items = List<_Item>.generate(pageSize,
          (i) => _Item(page * pageSize + i + 1, '数据 #${page * pageSize + i + 1}'));
      _cache[page] = items;
      _inflight.remove(page);
      return items;
    });
    _inflight[page] = future;
    return future;
  }
}

class _DataLayerDemo extends StatefulWidget {
  const _DataLayerDemo();
  @override
  State<_DataLayerDemo> createState() => _DataLayerDemoState();
}

class _DataLayerDemoState extends State<_DataLayerDemo> {
  final _Repo _repo = _Repo();
  final List<_Item> _items = [];
  int _nextPage = 0;
  bool _loading = false;

  Future<void> _loadNext() async {
    if (_loading) return;
    setState(() => _loading = true);
    // 同时发两次请求，验证「在途去重」只产生一次真实请求
    final results = await Future.wait([
      _repo.fetch(_nextPage),
      _repo.fetch(_nextPage),
    ]);
    setState(() {
      _items.addAll(results.first);
      _nextPage++;
      _loading = false;
    });
  }

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: const Text('分页 · 缓存 · 去重')),
        body: Column(children: [
          Padding(
            padding: const EdgeInsets.all(12),
            child: Column(crossAxisAlignment: CrossAxisAlignment.start, children: [
              Text('已加载 ${_items.length} 条 · 请求 ${_repo.requests} 次 · 命中 ${_repo.hits} 次'),
              Text('最近：${_repo.last}', style: Theme.of(context).textTheme.bodySmall),
            ]),
          ),
          Expanded(
            child: _items.isEmpty
                ? const Center(child: Text('点击下方按钮加载第 0 页'))
                : ListView.builder(
                    itemCount: _items.length,
                    itemBuilder: (context, i) =>
                        ListTile(title: Text('${_items[i].id} · ${_items[i].title}')),
                  ),
          ),
          Padding(
            padding: const EdgeInsets.all(12),
            child: SizedBox(
              width: double.infinity,
              child: FilledButton(
                onPressed: _loading ? null : _loadNext,
                child: Text(_loading ? '加载中…' : '加载下一页（并发请求两次）'),
              ),
            ),
          ),
        ]),
      ),
    );
  }
}

常见坑 ​

高频踩坑点

  1. 拦截器里忘记 handler.next：请求永远挂起，表现为一直 loading，且没有任何异常。
  2. 对非幂等请求盲目重试：POST 重复提交订单/支付；重试前先确认幂等性或带 idempotency key。
  3. 只设连接超时：服务端迟迟不返回 body 时请求永不结束；补上 receiveTimeout。
  4. 缓存没有 TTL / 失效策略：用户看到过期数据且无法刷新；至少提供下拉刷新与主动失效。
  5. 忽略响应竞态：快速搜索时旧响应覆盖新结果；用请求 id 或取消旧 token。

课后练习 ​

  1. 拦截器日志：实现一个只记录方法、URL、状态码、耗时的拦截器，敏感头（Authorization）打码。
  2. 取消搜索：输入框每次变化取消上一个 CancelToken，并对比「不取消」时旧结果覆盖新结果的概率。
  3. 两级缓存：给列表页加内存 TTL 缓存 + 本地持久化，实现「先展示旧数据，再后台刷新」。
  4. 乐观更新：做一个开关列表，点击立即变化，请求失败时回滚并提示。 :::
