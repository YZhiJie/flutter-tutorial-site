技术选型：Flutter vs KMP vs React Native ​

学习目标 ​

学完本章，你将能够：

  • 用 9 个维度把「选哪个框架」拆成可比较的问题，而不是站队
  • 说清 Flutter 的优势与短板：包体积、UI 一致性、Web / 桌面的成熟度
  • 理解 KMP「共享逻辑 + 原生 UI」的边界，不把它和 Compose Multiplatform 混为一谈
  • 说清 React Native 新架构：Fabric、TurboModules、JSI 各自解决什么问题
  • 用权重 + 评分做决策矩阵，并识别必须一票否决的硬门槛
  • 设计 Add-to-App 混合架构与 90 天团队落地路线图

选型不是选最强技术

选型是「在业务约束、团队现状、交付时间下找最优解」。同一家公司，存量 iOS 团队做新 App 和从零组建跨端团队，结论可能完全相反。先写约束，再谈框架。

一、先定义问题：九个选型维度 ​

维度要回答的问题典型证据
性能列表、动画、启动、内存的预算是多少真机 profile 数据，不看 Demo
生态需要的 SDK 是否有官方/成熟插件支付、地图、推送、IM 的覆盖度
原生能力是否依赖相机、蓝牙、后台、传感器插件缺口是否需要自研
团队栈现有成员最熟什么Dart / Kotlin / TS 的人天成本
招聘当地人才供给与薪资招聘周期、简历量
构建发布CI、签名、商店、灰度是否顺畅从提交到上架的时长
热更新是否需要绕过商店发版合规边界与审核风险
多端覆盖要覆盖哪些端、哪些端只是「能跑」Android / iOS / Web / 桌面矩阵
维护成本三年后谁来升级、谁来修插件版本升级频率、社区活跃度

先列「一票否决项」

合规、必须的原生能力、明确的上线日期，属于硬约束。它们不参与加权平均——不满足就直接出局。用总分把一票否决项稀释掉，是选型最常见的自欺。

二、Flutter：优势与短板 ​

Flutter 用自绘引擎把 UI 画到屏幕上，一套 Dart 代码覆盖 Android / iOS / Web / 桌面。

优势：UI 一致性强、热重载快、动画与自定义绘制能力强、多端覆盖广、单团队维护成本低。对「界面复杂、交互一致、需要快速迭代」的产品非常合适。

短板：

短板具体表现缓解方式
包体积release 基线通常比原生大若干 MBAAB + --split-per-abi、裁剪资源、延迟下载
原生深度插件缺失时要写 Platform ChannelPigeon + 自研插件，提前盘点
Web 成熟度首屏体积、SEO、浏览器兼容仍是硬约束只做内部工具 / 轻交互，或单独评估
桌面成熟度窗口、菜单、托盘要自己补用成熟插件，按平台适配
热更新不能绕过商店更新 Dart 代码用远程配置 + 服务端下发业务数据

Flutter 的「一致性」是双刃剑

一套 UI 全平台一样，意味着 iOS 用户会觉得「不像 iOS」。要么接受品牌一致性，要么用 Platform 分支做局部适配。选型时把这条写进设计规范，别等上线再吵。

三、KMP：共享逻辑，原生 UI ​

Kotlin Multiplatform 共享的是业务逻辑、数据层、网络层，UI 仍然用 SwiftUI / Compose 写原生界面。共享 UI 是另一个产品：Compose Multiplatform。

kotlin
// build.gradle.kts：一个 common 模块产出 Android 与 iOS 产物
kotlin {
    androidTarget()
    iosArm64()
    iosSimulatorArm64()
    sourceSets {
        commonMain.dependencies {
            implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.9.0")
            implementation("org.jetbrains.kotlinx:kotlinx-serialization-json:1.7.3")
        }
    }
}
维度KMP 的表现
性能接近原生，UI 由平台渲染
原生能力最强，直接调用平台 API
UI 一致性低（除非另上 Compose Multiplatform）
团队要求Kotlin + Gradle + iOS 工程能力
迁移方式可从单个模块渐进接入，不必重写 App
主要成本双端 UI 工作量、构建链复杂度、人才稀缺

KMP 适合：已有 Android 团队、业务逻辑厚重（计价、同步、加密）、对原生体验要求高的产品。不适合：只有一两个页面、团队没有 Kotlin 经验、指望「一套 UI 全平台」。

四、React Native：Fabric / TurboModules / JSI ​

React Native 的新架构把旧的「JS ↔ 原生桥」拆成了三块：

组件作用解决的问题
FabricC++ 渲染器，UI 树在原生侧同步布局旧桥异步批处理导致的列表卡顿
TurboModules按需加载、类型安全的原生模块启动时全量初始化、调用开销大
JSIJS 直接持有 C++ 对象，可同步调用跨桥序列化与异步延迟
Hermes预编译字节码引擎启动慢、内存高

优势：TS/JS 人才供给大、npm 生态庞大、迭代快、可通过 EAS Update 等方案做 JS 层热更新（仍需遵守商店政策）、原生模块编写成熟。

短板：双端 UI 仍需处理平台差异；新架构迁移有成本（老库不兼容）；构建链与原生工程复杂度不低；极端性能场景仍要写原生。

别拿旧架构的印象评估 RN

「RN 卡、桥慢」是旧架构的结论。评估时必须确认目标版本默认开启新架构，并在真机上测列表滚动、启动、内存。用三年前的体验下结论，和用 Flutter 的早期版本否定 Flutter 一样不严谨。

五、Web 优先与其他方案 ​

方案适合代价
PWA / 响应式 Web内容、电商、轻交互、获客页原生能力弱、离线与推送受限
Capacitor / IonicWeb 团队快速包壳、内部工具重交互与性能上限低
纯原生（Swift + Kotlin）重原生、强合规、极致体验双团队、双倍交付成本
Flutter跨端一致 UI、复杂动画、多端覆盖包体、原生深度、Web 限制
KMP共享重逻辑、保留原生 UI双端 UI 成本、人才稀缺
React NativeJS 团队、生态依赖强、需热更新新架构迁移、原生工程复杂度

一个常见的组合是：核心 App 用 Flutter / RN，重原生模块用原生写，运营页用 Web。关键不是统一技术栈，而是把边界切在可维护的地方。

六、决策矩阵：权重打分 ​

先定权重（总和 100），再给每个候选打 1–5 分，最后算加权分：

得分 = Σ(权重 × 评分) / (5 × Σ权重) × 100

假设团队是「已有 Flutter 经验、需要覆盖移动端 + 桌面、原生能力中等」：

维度权重FlutterKMPRN
性能25453
生态20435
原生能力15353
团队栈20424
招聘10325
热更新5224
多端覆盖5523
加权总分10074.068.077.0

在这组权重下 RN 略胜，因为生态、招聘、热更新权重被放大；如果把「原生能力」权重提到 35、招聘降到 5，KMP 会明显反超。结论对权重极度敏感，所以权重必须在选型会之前定好并留档。

打分只能辅助，不能代替判断

矩阵的价值是逼团队把隐含偏好写成数字，并在会上对齐分歧。真正上线前，还要用 2–4 周做技术 Spike：真机性能、插件缺口、构建时长、包体增量，四项都要有数据。

七、Add-to-App 与团队落地路线图 ​

存量 App 不想重写，可以用 Add-to-App 把 Flutter 作为模块嵌入：

kotlin
// Android：缓存 FlutterEngine，多个入口复用，避免每次冷启动
val engine = FlutterEngine(context)
engine.dartExecutor.executeDartEntrypoint(DartEntrypoint.createDefault())
// 之后用 FlutterActivity / FlutterFragment 挂载，路由与状态由原生壳管理
要点说明
引擎复用FlutterEngineGroup 共享快照，降低启动与内存
路由边界Flutter 只管模块内页面，返回栈交回原生
状态传递用 MethodChannel / Pigeon 传最小数据，不共享大对象
包体嵌入后安装包会增大，需评估渠道与低端机
灰度按入口/用户放量，保留原生页面作为回滚

90 天路线图：

阶段目标退出标准
0–30 天技术 Spike + 硬门槛验证四项指标有数据，无插件缺口
30–60 天一个低风险模块试点崩溃率、帧率、包体达标
60–90 天扩到 2–3 个模块 + CI 固化团队可独立发版，回滚演练通过

选型失败多半是组织问题

没有明确的 owner、没有 CI、没有代码规范、没有回滚演练，换哪个框架都会烂。技术选型只能解决「工具」问题，解决不了「谁负责、怎么验收、出问题谁兜底」。

dart
import 'package:flutter/material.dart';
// 选型打分器：拖动权重，实时计算 Flutter / KMP / RN 的加权分。
// 一票否决项不参与平均，先过硬门槛再算分。
void main() => runApp(const MaterialApp(home: _ScorePage()));

const List<String> _dims = <String>['性能', '生态', '原生能力', '团队栈', '多端覆盖'];
/// 每个候选在各维度的 1~5 分，顺序与 _dims 一致。
const Map<String, List<int>> _scores = <String, List<int>>{
  'Flutter': <int>[4, 4, 3, 4, 5],
  'KMP': <int>[5, 3, 5, 2, 2],
  'React Native': <int>[3, 5, 3, 4, 3],
};

class _ScorePage extends StatefulWidget {
  const _ScorePage({super.key});
  @override
  State<_ScorePage> createState() => _ScorePageState();
}

class _ScorePageState extends State<_ScorePage> {
  List<int> _weights = <int>[25, 20, 15, 20, 20];

  double _score(String name) {
    final scores = _scores[name]!;
    var weighted = 0;
    var total = 0;
    for (var i = 0; i < _dims.length; i++) {
      weighted += _weights[i] * scores[i];
      total += _weights[i];
    }
    return total == 0 ? 0 : weighted / (total * 5) * 100;
  }

  @override
  Widget build(BuildContext context) {
    final scheme = Theme.of(context).colorScheme;
    final ranked = _scores.keys.toList()
      ..sort((a, b) => _score(b).compareTo(_score(a)));
    return Scaffold(
      appBar: AppBar(title: const Text('技术选型打分器')),
      body: ListView(
        padding: const EdgeInsets.all(16),
        children: <Widget>[
          Text('拖动权重，观察结论如何翻转；评分是同一套业务约束下的相对值。',
              style: TextStyle(color: scheme.onSurfaceVariant)),
          const SizedBox(height: 8),
          for (var i = 0; i < _dims.length; i++)
            Row(children: <Widget>[
              SizedBox(width: 68, child: Text(_dims[i])),
              Expanded(
                child: Slider(
                  value: _weights[i].toDouble(),
                  max: 30,
                  divisions: 30,
                  label: '${_weights[i]}',
                  onChanged: (v) => setState(() => _weights[i] = v.round()),
                ),
              ),
              SizedBox(
                  width: 24,
                  child: Text('${_weights[i]}', textAlign: TextAlign.end)),
            ]),
          Row(children: <Widget>[
            Text('权重和 ${_weights.reduce((a, b) => a + b)}'),
            const Spacer(),
            TextButton(
              onPressed: () =>
                  setState(() => _weights = <int>[25, 20, 15, 20, 20]),
              child: const Text('重置'),
            ),
          ]),
          const Divider(),
          for (final name in ranked)
            Card(
              margin: const EdgeInsets.symmetric(vertical: 6),
              child: Padding(
                padding: const EdgeInsets.all(12),
                child: Column(
                  crossAxisAlignment: CrossAxisAlignment.start,
                  children: <Widget>[
                    Row(children: <Widget>[
                      if (name == ranked.first)
                        Padding(
                          padding: const EdgeInsets.only(right: 6),
                          child: Icon(Icons.emoji_events,
                              size: 18, color: scheme.primary),
                        ),
                      Expanded(
                        child: Text(name,
                            style: const TextStyle(fontWeight: FontWeight.w600)),
                      ),
                      Text('${_score(name).toStringAsFixed(1)} 分'),
                    ]),
                    const SizedBox(height: 8),
                    LinearProgressIndicator(
                      value: _score(name) / 100,
                      minHeight: 8,
                    ),
                  ],
                ),
              ),
            ),
          const SizedBox(height: 8),
          Text('当前 ${ranked.first} 领先。把「原生能力」权重拉到 30 以上，KMP 会反超。',
              style: TextStyle(color: scheme.primary)),
        ],
      ),
    );
  }
}

常见坑 ​

高频踩坑点

  1. 只比 Demo 性能：Demo 没有你的列表、图片、埋点、低端机；选型要比真实页面。
  2. 用加权平均掩盖一票否决：合规或必须的原生能力不满足，总分再高也不能上。
  3. 把 KMP 当成「一套 UI 全平台」：KMP 共享逻辑，共享 UI 要另上 Compose Multiplatform。
  4. 用旧桥接印象评估 RN：新架构默认开启后，性能与启动模型已经变了，必须实测。
  5. Add-to-App 不复用引擎：每个入口新建引擎，启动慢、内存高，用户第一眼就是卡。
  6. 忽略热更新的合规边界：iOS 对动态下发可执行代码有明确限制，别把 OTA 当默认能力。

课后练习 ​

  1. 权重实验：用本章矩阵给自己的项目打分，分别把「性能」「团队栈」「多端覆盖」权重翻倍，观察结论如何变化。
  2. 硬门槛清单：列出你项目的 3 条一票否决项，并说明如何用 Spike 在一周内验证。
  3. 包体估算：分别估算 Flutter 与 RN 版本的安装包增量，写出拆 ABI、裁剪资源的具体动作。
  4. Add-to-App 演练：在一个原生 Demo 里嵌入 Flutter 模块，实现引擎复用与返回原生页面的路由边界。
  5. 90 天计划：为你的团队写落地路线图，包含试点模块、观测指标、回滚方式与负责人。
