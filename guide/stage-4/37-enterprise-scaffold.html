企业级工程骨架：从 0 到 1 的架构装配 ​

学习目标 ​

学完本章，你将能够：

  • 用 feature-first 组织目录，并说清 domain / data / presentation 的依赖方向
  • 不引第三方 DI 库也能落地构造注入与依赖替换，同时看懂 Riverpod / get_it 的等价写法
  • 实现路由守卫与「401 → 刷新 token → 重放请求」的会话链，并用单飞刷新避免并发打爆刷新接口
  • 用全局错误边界兜住未捕获异常，用 Result 把预期内失败变成可处理数据
  • 通过 --dart-define / flavors 装配 dev、staging、prod 三套配置
  • 设计启动编排顺序、feature flag 灰度与 Mock 边界，避免它们变成散落的 if

骨架 ≠ 脚手架

「企业级骨架」不是把一堆库堆进 pubspec.yaml，而是把变化点集中到少数几个位置：组合根决定实现、配置层决定环境、守卫决定会话、边界决定失败。业务页面只消费契约。

一、feature-first 目录组织 ​

layer-first（models/、services/、ui/ 全放一起）在 20 人以上团队会迅速失控：改一个功能要跨五个顶层目录，代码归属不清。feature-first 按业务能力切分：

lib/
├── app/                        # 组合根：启动、配置、依赖装配、路由表
│   ├── bootstrap.dart
│   ├── app_scope.dart
│   ├── router.dart
│   └── env.dart
├── core/                       # 无业务语义的公共能力
│   ├── result.dart
│   ├── failure.dart
│   └── logging.dart
├── features/
│   ├── auth/
│   │   ├── domain/             # 实体 + 仓库契约（纯 Dart）
│   │   ├── data/               # HTTP / 本地实现 + DTO
│   │   └── presentation/       # 页面、状态、组件
│   ├── checkout/
│   └── settings/
└── shared/                     # 跨 feature 复用的 UI 小组件

三条硬规则：

规则含义反例
依赖朝内presentation → domain ← data页面直接 import 数据层实现
domain 纯净不 import Flutter、不 import data/presentation实体里塞 Color / BuildContext
feature 自治跨 feature 只能依赖对方 domain结算页直接调订单页的内部状态

domain 用纯 Dart 的好处是单测极快，也方便未来抽包。示例 App 里的 di_rules_demo.dart 就把这三条规则做成了可执行的检查器。

二、依赖注入：构造注入是主路径 ​

DI 的目标只有两个：换实现不改调用方、测试能塞 Fake。最小实现不需要库：

dart
// 契约
abstract class OrderRepository {
  Future<Result<List<Order>>> load();
}

// 实现
class HttpOrderRepository implements OrderRepository { /* ... */ }
class FakeOrderRepository implements OrderRepository { /* ... */ }

// 组合根：唯一决定用哪个实现的地方
final OrderRepository orderRepository =
    kDebugMode ? FakeOrderRepository() : HttpOrderRepository(dio);

页面通过构造参数接收：

dart
class CheckoutPage extends StatelessWidget {
  const CheckoutPage({super.key, required this.orders});

  final OrderRepository orders;
}

跨多层传递时，用 InheritedWidget 做一个轻量作用域（示例 App 的 AppScope 就是这个思路）：

dart
class AppScope extends InheritedWidget {
  const AppScope({required this.orders, required super.child});

  final OrderRepository orders;

  static AppScope of(BuildContext context) =>
      context.dependOnInheritedWidgetOfExactType<AppScope>()!;

  @override
  bool updateShouldNotify(AppScope old) => orders != old.orders;
}

真实项目里的两种主流写法 ​

Riverpod（推荐新项目，编译期安全 + 可覆盖）：

dart
final orderRepositoryProvider = Provider<OrderRepository>((ref) {
  final dio = ref.watch(dioProvider);
  return HttpOrderRepository(dio);
});

// 单测 / 预览时覆盖实现
ProviderScope(
  overrides: [orderRepositoryProvider.overrideWithValue(FakeOrderRepository())],
  child: const App(),
);

// 页面
final orders = ref.watch(orderRepositoryProvider);

get_it（存量项目常见，运行时定位）：

dart
final getIt = GetIt.instance;

void configureDependencies({required bool fake}) {
  getIt.registerLazySingleton<OrderRepository>(
    () => fake ? FakeOrderRepository() : HttpOrderRepository(getIt<Dio>()),
  );
}

// 页面
final orders = getIt<OrderRepository>();

示例 App 的差异要讲清

本章示例 App 没有引入 Riverpod / get_it，它用 InheritedWidget + 构造函数 演示同一套机制：组合根装配、契约注入、实现替换。机制是真实的，但省掉了库的容器、生命周期与作用域管理。生产项目请优先选成熟的 DI 方案。

三、路由守卫与会话刷新 ​

守卫放在路由层，不要散在页面里 ​

用 go_router 时，守卫就是 redirect：

dart
GoRouter(
  redirect: (context, state) {
    final session = context.read<SessionStore>();
    final loggingIn = state.matchedLocation == '/login';
    if (!session.isLoggedIn) return loggingIn ? null : '/login?from=${state.uri}';
    if (loggingIn) return '/home';
    return null;
  },
  routes: [/* ... */],
);

页面里再写一遍 if (!loggedIn) return LoginPage() 会造成两套判断，深链、返回栈、刷新恢复都会失配。

401 链：刷新一次，重放原请求 ​

正确顺序是：请求 → 401 → 单飞刷新 → 用新 token 重放 → 仍 401 则登出。用 Dio 拦截器实现：

dart
class AuthInterceptor extends Interceptor {
  AuthInterceptor(this.dio, this.session);

  final Dio dio;
  final SessionStore session;
  Future<String>? _refreshing;

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) async {
    if (err.response?.statusCode != 401 || err.requestOptions.extra['retried'] == true) {
      return handler.next(err);
    }
    // 单飞：并发的 401 共用同一个刷新 Future
    final token = await (_refreshing ??= session.refresh()
        .whenComplete(() => _refreshing = null));
    final options = err.requestOptions
      ..extra['retried'] = true
      ..headers['Authorization'] = 'Bearer $token';
    try {
      final response = await dio.fetch(options);
      return handler.resolve(response);
    } on DioException catch (e) {
      return handler.next(e);
    }
  }
}

三个必须处理的细节：

  1. 单飞：刷新接口自身不能带旧 token，也不能递归拦截；并发 401 只刷新一次。
  2. 防循环：标记 retried，重放还 401 就直接登出，不能无限重试。
  3. 刷新失败要全局登出：清 token、清用户态、跳登录，并保留 from 方便回跳。

示例 App 的 session_guard_demo.dart 没有网络层，它用内存里的「过期开关 + 模拟 401」演示同一条链路：守卫拦截、单飞刷新、重放计数。

四、错误边界与 Result / Either ​

全局边界：兜住「没想到」的错误 ​

Flutter 有三类必须接的入口：

dart
void main() {
  FlutterError.onError = (details) {
    FlutterError.presentError(details);
    CrashReporter.report(details.exception, details.stack);
  };

  PlatformDispatcher.instance.onError = (error, stack) {
    CrashReporter.report(error, stack);
    return true; // 已处理，避免二次上报
  };

  runZonedGuarded(() => runApp(const App()), (error, stack) {
    CrashReporter.report(error, stack);
  });
}

再加一个兜底 UI，避免用户看到灰屏或红屏：

dart
ErrorWidget.builder = (details) => FallbackErrorCard(details: details);

Result：预期内的失败不要用异常 ​

网络超时、404、校验失败都是业务流程，不是程序 bug。用 Result / Either 显式建模：

dart
sealed class Result<T> {
  const Result();
}

class Ok<T> extends Result<T> {
  const Ok(this.value);
  final T value;
}

class Err<T> extends Result<T> {
  const Err(this.failure);
  final Failure failure;
}

调用方必须处理两支，错误因此不会被「忘记捕获」：

dart
switch (await repository.load()) {
  case Ok(value: final value):
    render(value);
  case Err(failure: final failure):
    showRetry(failure.message);
}

边界与 Result 的分工：

层负责例子
全局错误边界未捕获异常、框架错误、致命问题空指针、断言失败、布局溢出导致的中断
Result / Either预期内失败与降级网络失败、权限不足、表单校验

示例 error_boundary_demo.dart 把两者做成开关：关掉边界能看到错误冒泡成 fatal；切到 Result 则错误变成可重试的数据。

五、多环境配置 ​

配置从编译期注入，避免把环境判断散落在业务代码里：

dart
enum AppEnv { dev, staging, prod }

class AppConfig {
  const AppConfig({required this.env, required this.apiBase, required this.logLevel});

  factory AppConfig.fromEnvironment() {
    const raw = String.fromEnvironment('APP_ENV', defaultValue: 'dev');
    return switch (raw) {
      'prod' => const AppConfig(env: AppEnv.prod, apiBase: 'https://api.corp.com', logLevel: 'warn'),
      'staging' => const AppConfig(env: AppEnv.staging, apiBase: 'https://api-stg.corp.com', logLevel: 'info'),
      _ => const AppConfig(env: AppEnv.dev, apiBase: 'https://api-dev.corp.com', logLevel: 'debug'),
    };
  }
}

构建命令：

bash
flutter build apk --dart-define=APP_ENV=prod
flutter run --dart-define=APP_ENV=staging

原则：

  • 只注入非敏感值。--dart-define 会留在产物里，密钥必须走服务端下发或原生安全存储。
  • 配置对象只读。运行中需要切换的（灰度、远程配置）与编译期固定的（包名、签名、环境）分开管理。
  • 默认值必须是安全的。缺省回落到 dev 可以，但绝不能缺省连生产库。
  • iOS / Android 的 flavors 负责包名、图标、签名；Dart 侧只认 AppConfig。

示例 config_flags_demo.dart 演示三套配置随环境切换，以及配置、日志级别、灰度比例一起变化。

六、启动编排 ​

启动阶段的常见事故不是慢，而是顺序错：远程配置依赖登录态、登录依赖本地存储、本地存储又依赖日志。建议显式分阶段：

dart
Future<void> bootstrap() async {
  await runStep('日志与崩溃上报', () => Logger.init());
  await runStep('读取编译期配置', () async => config = AppConfig.fromEnvironment());
  await runStep('本地存储', () => Storage.init());
  await runStep('恢复会话', () => session.restore());
  await runStep('远程配置与开关', () => remoteConfig.load());
  await runStep('路由与首屏', () => router.refresh());
}

判断标准：

阶段失败时策略
日志 / 崩溃失败可降级，不能阻塞启动
本地存储失败进入安全模式，提示修复或重试
会话恢复失败视为未登录，不要卡在启动页
远程开关超时后使用内置默认值，禁止无限等待
首屏数据可以骨架屏 + 重试，不必阻塞整个 App

启动页不要无限转圈：给每个阶段设置超时，超时后带上默认配置进入应用，再把失败上报。

七、Feature flag 与灰度 ​

Feature flag 不是「远程开关」四个字，至少要解决三件事：稳定分桶、可回滚、可本地覆盖。

dart
bool enabled(String userId, String flagKey, int percent) {
  if (percent <= 0) return false;
  if (percent >= 100) return true;
  final bucket = stableHash('$userId:$flagKey') % 100;
  return bucket < percent;
}

关键点：

  • 按用户稳定分桶，不能每次启动随机，否则同一用户会来回切换体验。
  • 默认值与 kill switch：远程配置拉取失败时用本地默认；出事时能一键关闭，而不是发版。
  • QA 覆盖：允许本地强制开启未放量功能，但覆盖值与构建绑定，不能随包发布。
  • flag 要还债：全量后删除旧分支，否则一年后没人知道这个开关还控制什么。

示例 config_flags_demo.dart 用 FNV-1a 风格的哈希演示「同一用户固定桶」，并展示 QA 覆盖优先于灰度比例。

八、Mock 边界怎么划 ​

Mock 只应该出现在仓库契约这一层：

位置是否合适说明
页面里 if (kDebugMode) 假数据否生产代码被测试分支污染
Repository 实现是页面只认契约，Fake 与 Http 平级
网络层拦截（Mock 服务器）是适合联调与端到端
Widget 内部注入 BuildContext 造数据否无法复用，容易泄漏到线上

推荐两套 Fake：

  • 单元测试 Fake：内存实现，零延迟，可控错误。
  • 演示 / 联调 Fake：带少量延迟与随机失败，用来验证 loading 与重试。

示例 di_rules_demo.dart 在组合根切换 Fake / 远端，页面一行不改；同时检查 import 规则，防止 Mock 或数据实现越层。

// ---------------------------------------------------------------- Result
sealed class Result<T> {
  const Result();
}

class Ok<T> extends Result<T> {
  const Ok(this.value);
  final T value;
}

class Err<T> extends Result<T> {
  const Err(this.message);
  final String message;
}

// ---------------------------------------------------------------- 依赖
abstract class OrderRepository {
  Future<Result<String>> fetchOrders(String token);
}

class HttpOrderRepository implements OrderRepository {
  HttpOrderRepository({required this.refreshToken});

  final Future<String> Function() refreshToken;
  bool tokenExpired = false;
  int attempts = 0;

  @override
  Future<Result<String>> fetchOrders(String token) async {
    attempts++;
    await Future<void>.delayed(const Duration(milliseconds: 180));
    if (tokenExpired) {
      tokenExpired = false;
      final fresh = await refreshToken();
      return fetchOrders(fresh); // 重放，真实项目用拦截器统一做
    }
    if (attempts % 3 == 0) {
      return const Err<String>('订单接口返回 500');
    }
    return Ok<String>('订单列表 · token=$token · 第 $attempts 次请求');
  }
}

class FakeOrderRepository implements OrderRepository {
  @override
  Future<Result<String>> fetchOrders(String token) async =>
      const Ok<String>('Fake：两条订单（单测专用）');
}

/// 组合根：整个 App 唯一知道「用哪个实现」的地方。
class AppScope extends InheritedWidget {
  const AppScope({
    super.key,
    required this.orders,
    required super.child,
  });

  final OrderRepository orders;

  static AppScope of(BuildContext context) =>
      context.dependOnInheritedWidgetOfExactType<AppScope>()!;

  @override
  bool updateShouldNotify(AppScope oldWidget) => orders != oldWidget.orders;
}

// ---------------------------------------------------------------- 应用
class EnterpriseScaffoldApp extends StatefulWidget {
  const EnterpriseScaffoldApp({super.key});

  @override
  State<EnterpriseScaffoldApp> createState() => _EnterpriseScaffoldAppState();
}

class _EnterpriseScaffoldAppState extends State<EnterpriseScaffoldApp> {
  AppEnv _env = AppEnv.dev;
  bool _fake = false;
  late final HttpOrderRepository _http = HttpOrderRepository(
    refreshToken: _refreshToken,
  );
  late OrderRepository _orders = _fake ? FakeOrderRepository() : _http;

  bool _loggedIn = false;
  bool _expired = false;
  String _token = 't1';
  String _route = '/home';
  int _refreshes = 0;
  Future<String>? _refreshFuture;
  final List<String> _log = <String>[];
  String? _resultText;

  // 单飞刷新：并发 401 只触发一次刷新
  Future<String> _refreshToken() {
    final existing = _refreshFuture;
    if (existing != null) return existing;
    _note('401 → 刷新 token');
    final future = Future<String>.delayed(const Duration(milliseconds: 400), () {
      _token = 't${int.parse(_token.substring(1)) + 1}';
      _refreshes++;
      return _token;
    });
    _refreshFuture = future;
    future.whenComplete(() => _refreshFuture = null).ignore();
    return future;
  }

  void _note(String line) {
    if (!mounted) return;
    setState(() {
      _log.insert(0, line);
      if (_log.length > 8) _log.removeLast();
    });
  }

  void _guardOpen(String path) {
    if (!_loggedIn) {
      _note('守卫拦截 $path：需要登录');
      return;
    }
    setState(() => _route = path);
  }

  Future<void> _loadOrders() async {
    _note('→ GET /orders');
    final result = await _orders.fetchOrders(_token);
    if (!mounted) return;
    switch (result) {
      case Ok<String>(value: final value):
        setState(() => _resultText = value);
        _note('← Ok：$value');
      case Err<String>(message: final message):
        setState(() => _resultText = message);
        _note('← Err：$message（错误成为数据，可重试）');
    }
  }

  @override
  Widget build(BuildContext context) {
    final AppScope scope = AppScope(orders: _orders, child: _body());
    return Theme(
      data: ThemeData(colorSchemeSeed: Colors.indigo, useMaterial3: true),
      child: scope,
    );
  }

  Widget _body() {
    return Scaffold(
      appBar: AppBar(
        title: Text('企业骨架 · ${_env.name}'),
        actions: <Widget>[
          TextButton(
            onPressed: () => setState(() => _env = AppEnv.values[
                (AppEnv.values.indexOf(_env) + 1) % AppEnv.values.length]),
            child: Text(_env.name.toUpperCase()),
          ),
        ],
      ),
      body: Column(
        children: <Widget>[
          Container(
            width: double.infinity,
            color: Colors.indigo.withValues(alpha: 0.08),
            padding: const EdgeInsets.all(8),
            child: Text(
              'API: ${AppConfig(_env).apiBase} · '
              '订单实现: ${_orders is FakeOrderRepository ? 'Fake' : 'HTTP'}',
              style: const TextStyle(fontSize: 12),
            ),
          ),
          Expanded(child: _screen()),
          SizedBox(
            height: 150,
            child: ListView(
              padding: const EdgeInsets.all(8),
              reverse: true,
              children: <Widget>[
                for (final line in _log)
                  Text(line, style: const TextStyle(fontSize: 12)),
              ],
            ),
          ),
        ],
      ),
    );
  }

  Widget _screen() {
    if (!_loggedIn) {
      return Center(
        child: FilledButton.icon(
          onPressed: () {
            setState(() => _loggedIn = true);
            _note('登录成功：token=$_token');
          },
          icon: const Icon(Icons.login),
          label: const Text('登录'),
        ),
      );
    }
    return ListView(
      padding: const EdgeInsets.all(16),
      children: <Widget>[
        Text('当前路由 $_route · token ${_expired ? '已过期' : '有效'}'),
        const SizedBox(height: 12),
        Wrap(
          spacing: 8,
          runSpacing: 8,
          children: <Widget>[
            FilledButton(
              onPressed: () => _guardOpen('/home/detail'),
              child: const Text('打开详情'),
            ),
            OutlinedButton(
              onPressed: () {
                setState(() => _expired = true);
                _http.tokenExpired = true;
                _note('token 已标记为过期');
              },
              child: const Text('让 token 过期'),
            ),
            OutlinedButton(
              onPressed: _loadOrders,
              child: const Text('请求订单'),
            ),
            OutlinedButton(
              onPressed: () {
                setState(() {
                  _fake = !_fake;
                  _orders = _fake ? FakeOrderRepository() : _http;
                });
              },
              child: const Text('切换 Fake / HTTP'),
            ),
            OutlinedButton(
              onPressed: () {
                setState(() {
                  _loggedIn = false;
                  _expired = false;
                  _route = '/home';
                });
                _http.tokenExpired = false;
                _note('退出登录');
              },
              child: const Text('退出'),
            ),
          ],
        ),
        const SizedBox(height: 12),
        Text(
          '刷新次数 $_refreshes · 当前 token $_token\n'
          '结果：${_resultText ?? '还没有请求'}',
        ),
      ],
    );
  }

常见坑 ​

高频踩坑点

  1. 守卫写在页面里：深链、返回栈与刷新恢复各自为政，登录后回不到原页面。
  2. 刷新不做单飞：并发请求同时 401，刷新接口被打爆，甚至互相覆盖 token。
  3. 401 无限重试：重放请求再次 401 又触发刷新，形成死循环。
  4. 异常当业务失败：所有错误都 try/catch 成一句 Toast，无法区分 bug 与可重试失败。
  5. 配置写死在业务里：if (env == prod) 散落十几个文件，新环境接入要全仓搜索。
  6. 启动阶段无超时：远程配置挂掉时启动页永远转圈。
  7. 灰度每次随机：用户刷新一次就换一套 UI，客服无法复现问题。
  8. Mock 混进生产分支：kDebugMode 判断留在业务页面，发版后再也删不干净。

课后练习 ​

  1. 守卫回跳：给示例加一个 from 参数，登录后回到被拦截的原路由，并补一个 widget 测试。
  2. 刷新失败处理：模拟刷新接口 500，验证会清空会话、跳登录且不会重放无限循环。
  3. 三套配置：用 --dart-define 跑一次 staging 构建，确认 API 地址与日志级别都变了。
  4. Result 全链路：把示例里的订单请求改成 Result，页面分别渲染 Ok / Err / loading。
  5. 分层规则进阶：在规则检查里再加一条「presentation 不得 import 另一 feature 的 data」，并写出反例。
  6. 灰度回滚：给「新版结算」加 kill switch，要求远程关闭后无需发版即可恢复旧流程。
