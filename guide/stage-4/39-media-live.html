音视频播放与直播接入 ​

学习目标 ​

学完本章，你将能够：

  • 说清播放器从初始化到释放的完整生命周期，处理前后台切换与页面销毁
  • 用音频会话（audio session）正确申请焦点，处理 duck / pause 打断与耳机拔出
  • 把播放状态同步到通知栏、锁屏与媒体键，并知道各平台差异
  • 实现倍速、字幕、清晰度切换、seek 与缓冲策略，并解释每个参数对体验的影响
  • 定义并采集直播的首帧、卡顿率、码率、延迟四项核心指标，设计弱网降级
  • 明确 RTMP / WebRTC 的能力边界：哪些是 Flutter 端的事，哪些必须服务端做
  • 评估 PlatformView 与视频纹理的性能成本，避免不必要的混合渲染

本章的两套代码

  • 真实依赖实现：labs/enterprise_app 使用 just_audio + audio_service + audio_session，包含真实播放、seek、倍速、缓冲统计与通知栏状态同步。
  • 零依赖机制演示：app/ 用纯 Flutter SDK 实现播放状态机与直播指标面板，不引入任何包。 两者解决的问题相同，能力边界完全不同，不要混为一谈。

一、选型：先定职责，再挑包 ​

音视频从来不是一个包能覆盖的事，先拆职责：

职责常见方案说明
解码与播放just_audio基于 ExoPlayer / AVPlayer，支持 HLS、倍速、seek、缓冲事件流
视频渲染video_player官方插件，输出纹理（texture），不是 PlatformView
后台播放与通知栏audio_service维护 PlaybackState / MediaItem，对接媒体通知与媒体键
音频焦点与路由audio_session申请焦点、监听打断、耳机拔出、录音冲突
全格式 / 桌面视频media_kit基于 libmpv，格式覆盖广，但包体与平台矩阵更重

本章实验工程的选型理由：

  1. Dart 3 / Flutter 3.47 兼容：just_audio 0.10.x、audio_service 0.18.x、audio_session 0.2.x 均在当前 SDK 下解析通过。
  2. 平台覆盖可验证：三个插件的 pubspec.yaml 都声明了 android / ios / macos / web（audio_service 与 just_audio 的 Darwin 实现是共享源码），实验工程可在 macOS 与 Web 直接跑。
  3. 能力齐全：just_audio 暴露 positionStream、bufferedPosition、processingStateStream、setSpeed、seek，足以讲清播放控制与缓冲；audio_service 负责通知栏与锁屏，职责不混。
  4. 不选 media_kit 的原因：它更适合「桌面全格式播放器」而非移动端企业应用，包体和原生依赖更重，会掩盖本章要讲的焦点与生命周期问题。

真实项目里，音频用 just_audio、视频用 video_player 是常见组合；如果视频格式复杂或需要桌面端播放，再评估 media_kit。

二、播放器生命周期 ​

状态不只「播放 / 暂停」 ​

一个负责任的播放器至少有以下状态：

idle → loading → ready ⇄ playing ⇄ paused
                    ↘ buffering ↗
                              ↘ completed
任何状态 → error / disposed
  • idle：播放器对象存在，但没有音源。
  • loading：正在解析音源、创建解码器、拉取首个分片。
  • ready：可以播放，尚未开始（首帧/首个音频包已就绪）。
  • buffering：播放中数据不足，用户看到转圈。
  • completed：播放到结尾，资源仍在，等待重播或释放。

just_audio 用 ProcessingState 表达前四类，用 playing 布尔量表达「用户意图」，两者要分开看：playing == true && processingState == buffering 就是「想播但没数据」。

初始化顺序 ​

dart
final handler = await AudioService.init(
  builder: DemoAudioHandler.new,
  config: const AudioServiceConfig(
    androidNotificationChannelId: 'com.example.app.playback',
    androidNotificationChannelName: '播放',
    androidNotificationOngoing: true,
  ),
);

final session = await AudioSession.instance;
await session.configure(const AudioSessionConfiguration.music());

await handler.load(); // setAsset / setAudioSource

顺序要点：

  1. AudioService.init 要在 runApp 之后、UI 需要播放器之前完成；它是全局单例，不要在页面里反复初始化。
  2. AudioSession.configure 决定焦点策略，必须在真正播放前完成。
  3. 音源加载是异步的，UI 要能显示 loading / error，而不是白屏等待。

前后台切换 ​

平台行为你需要做什么
Android默认进入后台会被限制，长期播放需要前台服务audio_service 已封装；声明 service 与通知渠道
iOS进入后台会暂停音频，除非声明后台音频能力UIBackgroundModes: audio；配置 AVAudioSession
macOSApp 存活期间可继续播放无需额外声明；窗口关闭是否退出由 App 决定
Web标签页切走可能被节流；自动播放受限首次播放必须由用户手势触发

Flutter 侧用 WidgetsBindingObserver 监听 didChangeAppLifecycleState，但它只适合做埋点与暂停策略，不要指望它在后台继续驱动播放——真正的保活得靠平台能力。

释放 ​

dart
@override
void dispose() {
  _interruptionSub?.cancel();
  _noisySub?.cancel();
  _player.dispose();
  super.dispose();
}

常见错误：

  • 只 pause() 不 dispose()：解码器、通知栏、媒体会话全部泄漏。
  • 在 dispose 里 await：dispose 是同步的，异步清理要用 unawaited 并确保对象不再被使用。
  • 全局 handler 被页面 dispose 后再次进入页面，播放器已被销毁：页面只负责订阅，播放器归属要明确。

三、音频焦点与打断恢复 ​

audio_session 把各平台的焦点行为统一成事件流：

dart
final session = await AudioSession.instance;
await session.configure(const AudioSessionConfiguration.music());

session.interruptionEventStream.listen((event) {
  if (event.begin) {
    if (event.type == AudioInterruptionType.duck) {
      player.setVolume(0.3);       // 导航播报等短暂降低音量
    } else {
      player.pause();              // 来电 / 其他 App 抢占
    }
  } else {
    // 打断结束：不要自动续播，等用户确认
  }
});

session.becomingNoisyEventStream.listen((_) {
  player.pause();                  // 耳机拔出
});

策略建议：

  • duck 用降音量，pause 用暂停，不要一律暂停，否则导航播报会把音乐打断成碎片。
  • 打断结束不自动恢复。用户可能正在接电话，自动续播是事故。
  • 恢复前重新 setActive(true)，并检查当前焦点是否真的可用。
  • 耳机拔出立即暂停，不要转外放，这是隐私问题。
  • 录音、通话、TTS 与音乐共用会话时，优先级要显式设计，别依赖默认值。

四、通知栏、锁屏与媒体键 ​

audio_service 的核心是把「播放器状态」翻译成系统能理解的 PlaybackState：

dart
playbackState.add(
  PlaybackState(
    controls: <MediaControl>[
      MediaControl.rewind,
      if (player.playing) MediaControl.pause else MediaControl.play,
      MediaControl.stop,
      MediaControl.fastForward,
    ],
    systemActions: const <MediaAction>{MediaAction.seek},
    processingState: /* 映射 ProcessingState */,
    playing: player.playing,
    updatePosition: player.position,
    bufferedPosition: player.bufferedPosition,
    speed: player.speed,
  ),
);

平台差异：

平台展示位置关键配置
Android媒体通知、锁屏、蓝牙媒体键通知渠道、前台服务类型、Android 13 通知权限
iOS锁屏 / 控制中心 / AirPodsMPNowPlayingInfoCenter，后台音频能力
macOS控制中心 / 媒体键 / Touch Bar（旧机型）MPNowPlayingInfoCenter，App 需保持运行
Web浏览器媒体会话（Media Session API）浏览器支持度不一，不能作为唯一控制入口

验收时必须用真机 + 锁屏 + 蓝牙耳机验证，模拟器与 Web 都测不出媒体键与通知栏的真实行为。

五、播放控制：倍速、字幕、清晰度、seek、缓冲 ​

倍速 ​

setSpeed() 改变播放速率，音频通常做音高校正（pitch correction）。注意：

  • 超过 2x 后音质与可懂度明显下降，产品上要限制档位（常见 0.5 / 1.0 / 1.5 / 2.0）。
  • 倍速要与字幕、直播延迟一起考虑：加速播放会让直播越追越前，需要限制追赶上限。
  • 倍速变化要同步到通知栏 / 锁屏（PlaybackState.speed），否则系统 UI 显示错误。

字幕 ​

  • 常见格式：WebVTT、SRT、ASS。Flutter 端通常只负责渲染与时间轴同步，解析在 Dart 或原生层完成。
  • 字幕时间轴必须跟 position 对齐；seek 后要立刻重算当前字幕，不能等下一帧。
  • 多语言字幕要做「选择 + 记忆」；字幕样式要可配置字号、背景、描边，保证弱视与户外可读。
  • 直播字幕依赖服务端 ASR，延迟与断句是服务端问题，客户端只能做平滑展示。

清晰度切换 ​

HLS/DASH 的多码率本质是同一份主播放列表下多个变体：

  • 自动模式：播放器根据带宽与缓冲选择码率（ABR）。
  • 手动模式：用户锁定档位，切换时保持 position，避免跳回开头。
  • 切换瞬间要有过渡：短暂缓冲优于黑屏；切换失败要能回退到原档位。
  • 清晰度标签要写「分辨率 + 码率」，只写「高清/超清」用户无法判断。

Seek ​

  • 精确 seek 会从关键帧解码到目标位置，慢；关键帧 seek 快但位置不准。播放器通常提供两种模式。
  • 目标位置要 clamp 到 [0, duration]，直播场景还要 clamp 到可回看窗口。
  • seek 期间 UI 应先进入 seeking 状态，避免进度条与真实播放位置来回跳。
  • 频繁拖动要节流，松手后再执行最终 seek。

缓冲策略 ​

常见参数（不同播放器命名不同）：

参数作用调大调小
起播缓冲开始播放前至少缓冲多久起播慢、抗卡顿强起播快、易卡
重缓冲阈值卡顿后恢复前至少缓冲多久恢复慢、二次卡顿少恢复快、易反复卡
最大缓冲最多缓存多久抗抖动强、内存/流量高省流量、抗抖动弱

原则：起播快与不卡顿是权衡。直播要偏「低延迟」，点播要偏「平滑」；同一套参数不要通吃。

六、直播指标与弱网策略 ​

四个核心指标 ​

指标定义采集点参考阈值
首帧时间从点击播放到首帧可见/首包可听播放器回调、埋点打点< 1s（互动场景 < 500ms）
卡顿率卡顿总时长 / 播放总时长buffering 状态累计< 5%
码率实际平均码率播放器统计 / CDN 日志不低于档位下限
延迟端到端（采集 → 渲染）直播时间戳、WebRTC getStatsHLS 3~10s，WebRTC < 1s

指标要分场景、分网络、分档位看。把「Wi-Fi 下 4K」和「弱网 480p」混在一个平均值里，结论一定错。

弱网策略 ​

  1. 降档优先：ABR 降码率 / 降分辨率，比直接卡住体验好。
  2. 缩短 GOP：关键帧更密，seek 与恢复更快，但码率上升，需要服务端配合。
  3. 预缓冲：进入弱网前多缓一点，用延迟换流畅。
  4. 重试退避：失败重试要指数退避 + 抖动，避免雪崩。
  5. 音频优先：视频拉流失败时可先保音频，至少不断声。
  6. 网络切换：Wi-Fi ↔ 蜂窝切换要重建连接并保留播放位置，不能从头开始。
  7. 降级要可观测：每次降档都打点，否则线上只知道「卡」，不知道「为什么卡」。

七、RTMP / WebRTC 的边界 ​

这是最容易被误解的部分：Flutter 端能做的和必须服务端做的，边界很清楚。

能力Flutter 端服务端 / 基础设施
RTMP 推流采集摄像头/麦克风、编码（需原生或第三方插件）接收推流、转码、切片、分发
RTMP 播放不能直接播；需转 HLS/FLV 或原生播放器转协议、CDN 分发
HLS / DASH 播放just_audio / video_player 直接播生成多码率切片、维护播放列表
WebRTC 信令发起/接收 SDP、ICE，需 flutter_webrtc 等插件信令服务器、房间管理
WebRTC 媒体采集、渲染、编码（插件封装）SFU/MCU 转发、TURN 穿透、级联
鉴权携带 token / 签名 URL签发、校验、防盗链
延迟保障选择协议、调缓冲、上报指标边缘节点、就近接入、链路优化

结论：

  • RTMP 是推流协议，不是给播放器用的。客户端「播 RTMP」通常意味着服务端先转成 HLS/FLV。
  • WebRTC 的低延迟靠服务端 SFU + TURN，客户端只负责采集、编解码与信令；没有服务端，Flutter 端再优化也降不到 1s 以内。
  • 本章实验工程没有引入 WebRTC 依赖，正文只讲边界；需要真机摄像头、信令服务与 TURN 才能验证。

八、PlatformView 与视频纹理的性能成本 ​

video_player 在移动端使用外部纹理（Android SurfaceTexture / iOS CVPixelBuffer），不是 PlatformView。这很重要：

方案原理成本
纹理（texture）原生渲染到纹理，Flutter 合成一次额外拷贝/合成，通常更轻
PlatformView（混合合成）原生视图嵌入 Flutter 图层树额外的图层合成、输入事件转发、截图/动画可能异常
多个 PlatformView每个都是一次混合合成数量线性增长，低端机掉帧明显

实践建议：

  • 视频优先用 video_player 的纹理路径，不要为了「自定义」把视频塞进 PlatformView。
  • 一屏多个视频（列表、直播宫格）要限制同时解码数量，离屏即释放。
  • 视频上叠加 Flutter 控件（弹幕、字幕）时，纹理方案天然更友好。
  • 需要原生播放器 UI 或特殊格式时，再评估 PlatformView，并实测合成开销。
  • 性能验收看「滚动时的帧耗时」与「首帧时间」，不要只看静止画面是否流畅。

void main() => runApp(const MediaLabApp());

class MediaLabApp extends StatelessWidget {
  const MediaLabApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      theme: ThemeData(colorSchemeSeed: Colors.teal, useMaterial3: true),
      home: const MediaLabHome(),
    );
  }
}

enum PlaybackPhase { idle, loading, ready, playing, paused, completed }

class MediaLabHome extends StatefulWidget {
  const MediaLabHome({super.key});

  @override
  State<MediaLabHome> createState() => _MediaLabHomeState();
}

class _MediaLabHomeState extends State<MediaLabHome> {
  PlaybackPhase _phase = PlaybackPhase.idle;
  Duration _position = Duration.zero;
  final Duration _total = const Duration(seconds: 12);
  double _speed = 1.0;
  String _message = '点「初始化」开始';

  final Random _random = Random();
  final List<int> _bitrates = <int>[];
  final List<int> _latencies = <int>[];
  int _stalled = 0;
  int _firstFrameMs = 0;

  void _send(String event) {
    setState(() {
      switch (event) {
        case 'init':
          if (_phase == PlaybackPhase.idle) {
            _phase = PlaybackPhase.loading;
            _message = '请求音频焦点、创建解码器…';
          } else {
            _message = '初始化被拒绝：当前 ${_phase.name}';
          }
        case 'loaded':
          if (_phase == PlaybackPhase.loading) {
            _phase = PlaybackPhase.ready;
            _firstFrameMs = 380;
            _message = '就绪，首帧 380ms';
          } else {
            _message = '只有 loading 才能进入 ready';
          }
        case 'play':
          if (_phase == PlaybackPhase.ready ||
              _phase == PlaybackPhase.paused ||
              _phase == PlaybackPhase.completed) {
            _phase = PlaybackPhase.playing;
            if (_position >= _total) _position = Duration.zero;
            _message = '播放中（${_speed}x）';
          } else {
            _message = '播放被拒绝：先完成初始化';
          }
        case 'pause':
          if (_phase == PlaybackPhase.playing) {
            _phase = PlaybackPhase.paused;
            _message = '暂停：资源保留，等待恢复';
          }
        case 'interrupt':
          if (_phase == PlaybackPhase.playing) {
            _phase = PlaybackPhase.paused;
            _message = '音频焦点被抢占：系统不会自动恢复';
          }
        case 'release':
          _phase = PlaybackPhase.idle;
          _position = Duration.zero;
          _message = '释放播放器与通知栏控制';
      }
    });
  }

  void _tick() {
    if (_phase != PlaybackPhase.playing) return;
    setState(() {
      _position += Duration(milliseconds: (200 * _speed).round());
      if (_position >= _total) {
        _position = _total;
        _phase = PlaybackPhase.completed;
        _message = '播放完成';
      }
    });
  }

  void _injectSamples() {
    setState(() {
      _bitrates.clear();
      _latencies.clear();
      _stalled = 0;
      for (int i = 0; i < 12; i++) {
        final bool stalled = i % 5 == 0;
        _bitrates.add(900 + _random.nextInt(400) - (stalled ? 300 : 0));
        _latencies.add(320 + _random.nextInt(500) + (stalled ? 900 : 0));
        if (stalled) _stalled++;
      }
    });
  }

  int get _p95 {
    if (_latencies.isEmpty) return 0;
    final List<int> sorted = List<int>.of(_latencies)..sort();
    final int rank = (0.95 * sorted.length).ceil();
    return sorted[min(sorted.length - 1, max(0, rank - 1))];
  }

  @override
  Widget build(BuildContext context) {
    final double progress = _total.inMilliseconds == 0
        ? 0
        : _position.inMilliseconds / _total.inMilliseconds;
    final double avgBitrate = _bitrates.isEmpty
        ? 0
        : _bitrates.reduce((int a, int b) => a + b) / _bitrates.length;
    final double stallRate =
        _bitrates.isEmpty ? 0 : _stalled / _bitrates.length;
    return Scaffold(
      appBar: AppBar(title: const Text('播放状态机与直播指标')),
      body: ListView(
        padding: const EdgeInsets.all(16),
        children: <Widget>[
          Chip(label: Text('状态 ${_phase.name}')),
          const SizedBox(height: 8),
          LinearProgressIndicator(value: progress.clamp(0.0, 1.0)),
          Text('${_position.inSeconds}s / ${_total.inSeconds}s · $_message'),
          const SizedBox(height: 12),
          Wrap(
            spacing: 8,
            runSpacing: 8,
            children: <Widget>[
              FilledButton(
                onPressed: () => _send('init'),
                child: const Text('初始化'),
              ),
              OutlinedButton(
                onPressed: () => _send('loaded'),
                child: const Text('加载完成'),
              ),
              FilledButton(
                onPressed: () =>
                    _send(_phase == PlaybackPhase.playing ? 'pause' : 'play'),
                child: Text(_phase == PlaybackPhase.playing ? '暂停' : '播放'),
              ),
              OutlinedButton(
                onPressed: () => _send('interrupt'),
                child: const Text('模拟来电'),
              ),
              OutlinedButton(
                onPressed: () => _send('release'),
                child: const Text('释放'),
              ),
            ],
          ),
          const SizedBox(height: 8),
          Wrap(
            spacing: 8,
            children: <Widget>[
              for (final double speed in <double>[0.5, 1.0, 1.5, 2.0])
                ChoiceChip(
                  label: Text('${speed}x'),
                  selected: _speed == speed,
                  onSelected: (_) => setState(() => _speed = speed),
                ),
            ],
          ),
          const Divider(height: 32),
          Text('直播指标（模拟采样，算法真实）',
              style: Theme.of(context).textTheme.titleMedium),
          Text('首帧 $_firstFrameMs ms · 卡顿率 '
              '${(stallRate * 100).toStringAsFixed(1)}% · '
              '平均码率 ${avgBitrate.toStringAsFixed(0)}kbps · P95 $_p95 ms'),
          Text(
            stallRate >= 0.15
                ? '结论：卡顿偏高，先降档或缩短 GOP'
                : '结论：${avgBitrate >= 900 && _p95 < 800 ? '质量达标' : '需要关注'}',
            style: Theme.of(context).textTheme.bodySmall,
          ),
          const SizedBox(height: 8),
          FilledButton.tonal(
            onPressed: _injectSamples,
            child: const Text('注入一组弱网样本'),
          ),
          const SizedBox(height: 12),
          Text(
            '真实播放器还要处理：audio_session 音频焦点、audio_service 通知栏 / 锁屏、'
            '缓冲策略、HLS/DASH 清晰度切换与 WeakNetwork 降级。',
            style: Theme.of(context).textTheme.bodySmall,
          ),
        ],
      ),
    );
  }

  @override
  void initState() {
    super.initState();
    _timer = Timer.periodic(const Duration(milliseconds: 200), (_) => _tick());
  }

  late final Timer _timer;

  @override
  void dispose() {
    _timer.cancel();
    super.dispose();
  }
}

常见坑 ​

高频踩坑点

  1. 把 playing 当播放状态：playing == true 但 processingState == buffering 时并没有声音。
  2. 页面 dispose 只 pause：解码器、通知、媒体会话泄漏，返回页面后状态错乱。
  3. 反复 AudioService.init：全局单例被重复初始化，媒体键失效或通知重复。
  4. 打断结束自动续播：用户正在通话，音乐突然恢复，属于严重体验事故。
  5. 耳机拔出转外放：隐私风险；必须监听 becomingNoisy 并暂停。
  6. 通知栏不更新倍速/位置：系统 UI 与真实播放状态不一致，用户以为卡住。
  7. 清晰度切换从头开始：没有保留 position，用户每次切换都要重新找位置。
  8. seek 不 clamp：拖到负值或超过时长，播放器抛异常或静默失败。
  9. 缓冲参数一套通吃：点播调大缓冲导致起播慢，直播调小缓冲导致频繁卡顿。
  10. 只测 Wi-Fi：弱网、切网、锁屏、蓝牙耳机才是事故高发场景。
  11. 拿 RTMP 当播放协议：客户端播不了，最后还是要服务端转 HLS。
  12. 把 WebRTC 延迟问题归给 Flutter：没有 TURN/SFU 与边缘节点，客户端优化无效。
  13. 视频塞进 PlatformView：混合合成成本高，动画与截图异常，优先纹理方案。
  14. 指标只算平均值：P95 才能反映真实卡顿体验，平均值会被大量正常样本稀释。

课后练习 ​

  1. 状态机补全：给 PlaybackStateMachine 增加 seeking 与 error 状态，要求非法迁移被拒绝并记录原因。
  2. 打断策略：实现 duck 与 pause 两种打断，验证打断结束后不会自动播放。
  3. 缓冲参数：为「起播快」与「不卡顿」各配一套参数，用模拟数据对比首帧与卡顿率。
  4. 指标面板：把 P50 / P95 换成 P99，并增加「按档位分组」的统计维度。
  5. 清晰度切换：设计一个切换流程，要求保留播放位置、失败可回退、切换期间有加载态。
  6. 弱网降级：写出「连续 3 个采样卡顿 → 降一档 → 10 秒后尝试回升」的状态机。
  7. 真机验证：在真机上验证锁屏、通知栏、蓝牙媒体键、来电打断与耳机拔出五项行为。
  8. 性能对比：用 video_player 纹理与 PlatformView 各做一个视频页，对比滚动帧耗时与首帧时间。
  9. 边界文档：为一个直播需求画出「客户端 / 服务端 / CDN」职责表，明确 RTMP 与 WebRTC 的分工。
