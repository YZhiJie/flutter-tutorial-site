本页目录

实时通信与 IM：长连接、可靠消息与离线 ​

学习目标 ​

学完本章，你将能够：

  • 在 WebSocket、SSE、轮询之间做出有依据的选型，而不是「IM 就必须 WebSocket」
  • 设计握手鉴权流程，处理 token 过期、重复登录与多端互踢
  • 实现心跳、断线检测与带抖动的指数退避重连，避免重连风暴
  • 用序号、消息 id、去重与乱序缓存保证「不丢、不重、有序」
  • 设计 ACK / 重试 / 幂等，理解「至少一次 + 去重」如何逼近「恰好一次」
  • 做离线消息与增量同步：游标、缺口补齐、多端已读同步
  • 处理未读数、已读回执与撤回，并知道服务端与客户端的职责边界
  • 在弱网下做增量列表刷新，避免整表重建与滚动位置跳动

本章的两套代码

  • 真实依赖实现：labs/enterprise_app 使用官方 web_socket_channel，配套仓库内 tool/ws_mock_server.dart 本地服务，可实测断网、重连、重复、乱序、缺口与增量同步。
  • 零依赖机制演示：app/ 与本章 DartPad 片段用纯 Flutter SDK + 计时器模拟同样的状态机与消息算法。 两边的算法可以对照阅读，但真实网络行为只能在 labs 工程里验证。

一、选型：WebSocket、SSE 还是轮询 ​

维度WebSocketSSE轮询 / 长轮询
方向全双工服务端 → 客户端单向客户端发起
协议ws:// / wss://HTTP/1.1 或 HTTP/2 流HTTP
代理与网关需要支持 Upgrade，部分企业代理不友好普通 HTTP，穿透好最好
鉴权浏览器不能自定义 header，需 query / cookie / 首帧认证标准 header 可用标准 header 可用
断线恢复需自己做心跳、重连、补发浏览器自动重连，仍需游标补数据天然按请求重试
移动端后台系统会挂起连接，需推送兜底同左同左
典型场景IM 聊天、协同编辑、在线状态通知流、行情、构建日志低频状态同步、兜底

选型建议：

  • 双向、低延迟、需要客户端频繁上行：WebSocket。
  • 只是服务端推送，客户端偶尔上行：SSE 更简单，重连由浏览器处理。
  • 消息频率低、实时性要求不高：轮询足够，运维成本最低。
  • 移动端必须接受「连接会断」：无论选哪个，都要有推送（APNs / FCM）兜底，不能把长连接当消息必达通道。

Flutter 侧：WebSocket 用官方 web_socket_channel；SSE 可用 http 的流式响应自行解析，或评估第三方 SSE 包。本章实验工程只引入 web_socket_channel，不额外引 SSE 依赖。

二、握手鉴权 ​

推荐流程 ​

客户端                         服务端
  │  ws(s)://host/ws?token=...   │
  │ ───────────────────────────▶ │ 校验 token（短生命周期）
  │ ◀─────────────────────────── │ 101 Switching Protocols
  │ {"type":"auth","token":...}  │ 若 URL 不便携带，改用首帧认证
  │ ───────────────────────────▶ │
  │ ◀─────────────────────────── │ {"type":"auth_ok","userId":...,"sessionId":...}
  │ {"type":"ping"} 每 15~30s    │
  │ ───────────────────────────▶ │
  │ ◀─────────────────────────── │ {"type":"pong"}

要点：

  1. token 用短生命周期，连接建立后再由服务端绑定用户，不依赖每次消息带 token。
  2. 浏览器 WebSocket 不能设置自定义 header：用 query、cookie 或「连接后第一帧 auth」；query 方案要避免 token 进访问日志，优先首帧认证。
  3. 认证失败要带关闭码（如 4001 unauthorized），客户端据此决定「刷新 token 后重连」还是「停止重试」。
  4. 多端登录策略要显式设计：踢掉旧连接、全部保留、还是只允许一端；服务端下发 kicked 事件，客户端不要无脑重连。
  5. 重连必须重新鉴权，不能复用旧 session。

token 过期与刷新 ​

连接 → 401/4001 → 刷新 token → 重新握手 → 补拉增量消息

刷新失败（refresh token 也失效）时进入「需要重新登录」状态，停止自动重连，跳转登录页。不要在没有 token 的情况下无限重试。

三、心跳与重连退避 ​

连接状态机 ​

idle → connecting → connected → reconnecting → offline
             ↘ failed（不可恢复：鉴权失败 / 版本不兼容）
  • connected 下心跳超时（例如连续 2 个周期没有 PONG）要主动判定连接不可用，进入 reconnecting。
  • offline 是「重试耗尽或用户主动离线」，必须有明确的恢复入口（手动重连 / 网络恢复监听）。
  • failed 不要自动重试，展示原因并引导用户操作。

心跳设计 ​

参数建议说明
心跳间隔15~30s太短耗电、太长发现断线慢
PONG 超时2 个心跳周期连续缺失判定断线
前台/后台后台降频或交给推送移动端后台连接不可靠
服务端超时2~3 倍心跳间隔服务端主动清理僵尸连接

应用层心跳比协议层 ping 更可控：能携带版本、房间、最后序号，也方便在 mock 服务里验证。

退避重连 ​

dart
Duration delayFor(int attempt, {double randomValue = 0.5}) {
  final baseMs = initial.inMilliseconds * pow(multiplier, attempt);
  final capped = min(baseMs, maxDelay.inMilliseconds);
  final factor = 1 - jitter + 2 * jitter * randomValue;
  return Duration(milliseconds: (capped * factor).round());
}
  • 指数退避：0.5s → 1s → 2s → 4s → 8s，封顶 30s。
  • 抖动：±20%~30%，避免服务端重启后所有客户端同一毫秒重连。
  • 最大次数：例如 10 次后进入 offline，等待用户或系统事件触发。
  • 网络变化立即重连：监听 Wi-Fi / 蜂窝切换，重置退避计数，但要做去抖，避免频繁切换导致连接风暴。
  • 服务端也要限流：连接速率、单用户连接数、单 IP 连接数。

四、消息序号、去重与顺序 ​

服务端分配序号 ​

  • 会话级 seq：每个会话独立递增，适合聊天列表。
  • 用户级 seq：一个用户所有会话共享递增，适合「增量同步一个游标拉全部」。
  • 不要用时间戳当序号：设备时钟漂移、同一毫秒多条消息都会导致排序错误。

客户端三件事 ​

  1. 去重：以消息 id 为准，重复 id 直接丢弃；seq 已消费过的旧消息也丢弃。
  2. 乱序缓存：收到 seq > lastSeq + 1 时先放缓冲区，不直接展示。
  3. 连续推进：只有拿到 lastSeq + 1 才依次出队，保证 UI 顺序稳定。
dart
bool accept(IncomingMessage message) {
  if (seenIds.contains(message.id)) return false; // 重复
  if (message.seq <= lastSeq) return false;        // 过期
  buffer[message.seq] = message;
  while (buffer.containsKey(lastSeq + 1)) {
    ordered.add(buffer.remove(lastSeq + 1)!);
    lastSeq++;
  }
  return true;
}

缺口长期不补时要主动触发增量同步，而不是无限等待。

五、ACK、重试与幂等 ​

  • 客户端发送消息时带 clientMsgId（本地生成，全局唯一），服务端以它做幂等键。
  • 服务端先落库再 ACK；ACK 丢失时客户端重试，服务端识别重复 id 返回同一个结果。
  • 重试必须用同一个 id，生成新 id 会导致重复消息。
  • ACK 超时用退避重试，超过上限标记为「发送失败」，允许用户手动重发。
  • 发送顺序：同一会话内串行发送，避免后发先至；跨会话可以并发。
  • 语义结论：至少一次投递 + 客户端/服务端去重 ≈ 恰好一次。真正的 exactly-once 需要服务端事务与幂等表配合。

六、离线消息与增量同步 ​

游标同步 ​

客户端持久化 lastSeq（或 lastReadSeq），重连后发：

json
{"type":"sync","sinceSeq":123}

服务端按序重放 seq > 123 的消息，客户端用同一套去重 / 排序逻辑消费。分页时用「上一页最小 seq」继续往前拉，不要用页码。

冷启动与多端 ​

  • 冷启动先读本地缓存（SQLite / drift / Isar），立刻渲染列表，再后台增量同步。
  • 多端已读：服务端保存「每个用户对每个会话的 readSeq」，登录后下发，客户端合并而不是覆盖本地更大值。
  • 离线期间的消息可能很多，同步要分页 + 限流，避免一次拉爆内存。
  • 同步期间的新消息可能继续到达，用同一个去重内核处理，不要开两套状态。

增量列表刷新 ​

  • 列表按 seq 追加，不要每次全量替换。
  • 使用稳定 key（消息 id），避免 ListView 重建导致滚动跳动。
  • 一批消息合并成一次 UI 更新（例如 16~50ms 合并窗口），不要每条都 setState。
  • 图片 / 头像懒加载，滚动停止后再预取。

七、未读数、已读回执与撤回 ​

未读数 ​

  • 服务端权威：unread = maxSeq - readSeq，多端一致。
  • 客户端可以乐观更新，但要以服务端返回为准回滚。
  • 免打扰会话的未读要用「小圆点」而非数字，避免误导。

已读回执 ​

  • 不要每读一条就上报；按会话批量、节流上报（如 1s 合并一次）。
  • 上报内容是「已读到 seq=N」，不是「消息 id 列表」，数据量小且天然幂等。
  • 群聊已读人数可能很大，产品上通常只展示「已读 / 未读」或抽样，不做全员名单。

撤回 ​

  • 服务端保留墓碑（tombstone），只标记撤回，不物理删除，保证序号连续。
  • 撤回有窗口期（如 2 分钟），超时拒绝。
  • 客户端本地先隐藏，再等服务端广播；多端通过同一条撤回事件同步。
  • 撤回后未读数要重算，不能把已撤回消息算进未读。

这不是生产实现

mock 服务是单进程内存态，没有鉴权、持久化、多端同步与限流；它只用于验证客户端协议与算法。生产环境还需要：鉴权、消息存储、推送兜底、多端游标、服务端限流与监控。

dart
import 'dart:async';
import 'dart:math';

import 'package:flutter/material.dart';

/// 零依赖演示：连接状态机 + 消息去重/排序/缺口补齐。
/// 真实 WebSocket 客户端见 labs/enterprise_app 与第 40 章正文。
void main() => runApp(const RealtimeLabApp());

class RealtimeLabApp extends StatelessWidget {
  const RealtimeLabApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      theme: ThemeData(colorSchemeSeed: Colors.indigo, useMaterial3: true),
      home: const RealtimeHome(),
    );
  }
}

enum ConnPhase { idle, connecting, connected, reconnecting, offline }

class RealtimeHome extends StatefulWidget {
  const RealtimeHome({super.key});

  @override
  State<RealtimeHome> createState() => _RealtimeHomeState();
}

class _RealtimeHomeState extends State<RealtimeHome> {
  final Random _random = Random(3);
  final List<int> _ordered = <int>[];
  final List<int> _buffer = <int>[];
  final List<String> _logs = <String>[];

  ConnPhase _phase = ConnPhase.idle;
  int _attempt = 0;
  int _heartbeats = 0;
  int _pongs = 0;
  int _lastSeq = 0;
  int _serverSeq = 0;
  DateTime? _retryAt;
  Timer? _ticker;

  @override
  void initState() {
    super.initState();
    _ticker = Timer.periodic(const Duration(milliseconds: 500), (_) => _tick());
  }

  @override
  void dispose() {
    _ticker?.cancel();
    super.dispose();
  }

  void _log(String message) {
    setState(() {
      _logs.insert(0, message);
      if (_logs.length > 8) _logs.removeLast();
    });
  }

  Duration _delayFor(int attempt) {
    final double base = min(500 * pow(2, attempt).toDouble(), 8000);
    final double factor = 0.8 + _random.nextDouble() * 0.4;
    return Duration(milliseconds: (base * factor).round());
  }

  void _connect() {
    if (_phase == ConnPhase.connected || _phase == ConnPhase.connecting) return;
    setState(() {
      _phase = ConnPhase.connecting;
      _retryAt = null;
    });
    _log('开始连接');
    Timer(const Duration(milliseconds: 800), () {
      if (!mounted || _phase != ConnPhase.connecting) return;
      setState(() {
        _phase = ConnPhase.connected;
        _attempt = 0;
      });
      _log('连接成功');
    });
  }

  void _loseNetwork() {
    setState(() {
      _phase = ConnPhase.reconnecting;
      _attempt = 1;
      _retryAt = DateTime.now().add(_delayFor(0));
    });
    _log('断网：0.5s 后第 1 次重连');
  }

  void _tick() {
    if (_phase == ConnPhase.connected) {
      setState(() {
        _heartbeats++;
        if (_random.nextInt(8) != 0) _pongs++;
      });
    } else if (_phase == ConnPhase.reconnecting &&
        _retryAt != null &&
        DateTime.now().isAfter(_retryAt!)) {
      _connect();
    }
  }

  void _receive(int seq) {
    if (seq <= _lastSeq) {
      _log('丢弃重复/过期 seq=$seq');
      return;
    }
    setState(() {
      if (!_buffer.contains(seq)) _buffer.add(seq);
      _buffer.sort();
      while (_buffer.isNotEmpty && _buffer.first == _lastSeq + 1) {
        _lastSeq++;
        _ordered.add(_lastSeq);
        _buffer.removeAt(0);
      }
    });
    _log('收到 seq=$seq，有序长度 ${_ordered.length}，缺口 ${_buffer.length}');
  }

  void _normal() {
    _serverSeq++;
    _receive(_serverSeq);
  }

  void _duplicate() {
    if (_ordered.isEmpty) return;
    _receive(_ordered.last);
  }

  void _outOfOrder() {
    final int high = _serverSeq + 2;
    _serverSeq = high;
    _receive(high);
    _receive(high - 1);
  }

  void _gap() {
    _serverSeq++;
    _log('服务端漏发 seq=$_serverSeq（可点增量同步补齐）');
    setState(() {});
  }

  void _sync() {
    final int target = _serverSeq;
    for (int seq = _lastSeq + 1; seq <= target; seq++) {
      if (!_ordered.contains(seq)) _receive(seq);
    }
  }

            spacing: 8,

常见坑 ​

高频踩坑点

  1. 把长连接当必达通道：App 被杀、系统挂起后连接必断，必须有推送与离线拉取兜底。
  2. token 放 URL 且长期有效：进日志、进代理、泄漏风险高；用短 token + 首帧认证。
  3. 鉴权失败还无限重连：401/4001 要停止重试并刷新 token 或跳登录。
  4. 多端登录不处理互踢：旧连接被踢后自动重连，形成两端互相踢的死循环。
  5. 心跳只发不收：没有 PONG 超时判定，半开连接会一直「假装在线」。
  6. 固定间隔重连：服务端重启后所有客户端同时重连，直接打垮服务。
  7. 用时间戳排序：跨设备时钟不一致，消息顺序错乱。
  8. 只按 seq 去重、不按 id 去重：多端同步时同一条消息可能被分配不同 seq。
  9. 重试生成新消息 id：服务端无法幂等，用户看到重复消息。
  10. 乱序消息直接上屏：列表顺序跳动，已读位置计算全错。
  11. 缺口只等待不主动同步：一条消息丢失会导致后面全部阻塞。
  12. 每次消息都 setState：消息密集时掉帧；要合并刷新。
  13. 列表全量替换：滚动位置丢失、所有 item 重建。
  14. 撤回物理删除：序号出现空洞，后续排序与已读计算全部失效。
  15. 未读数客户端自算：多端不一致，换设备后数字对不上。

课后练习 ​

  1. 连接状态机：补上 failed 状态，区分可重试错误（网络）与不可重试错误（鉴权 / 协议版本）。
  2. 退避策略：实现带抖动的指数退避，并写出「网络恢复立即重连但 1 秒内只重连一次」的去抖逻辑。
  3. 心跳超时：连续 2 个周期无 PONG 判定断线，写出状态迁移与日志。
  4. 去重与排序：构造 1、3、2、3（重复）、1（过期）的到达序列，验证最终有序结果为 1、2、3。
  5. ACK 重试：模拟 ACK 丢失，要求重试用同一 id，服务端只落库一次。
  6. 增量同步：设计 sinceSeq 分页协议，处理同步过程中新消息继续到达的情况。
  7. 多端已读：设计服务端表结构与客户端合并规则，保证两端未读数最终一致。
  8. 撤回：实现墓碑 + 窗口期 + 未读重算，验证多端同步。
  9. 弱网刷新：把逐条 setState 改成批量合并，测量消息密集时的帧耗时变化。
  10. 协议联调：用 tool/ws_mock_server.dart 扩展一个「服务端主动踢下线」指令，客户端要停止重连并提示。
