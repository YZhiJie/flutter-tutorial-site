43 · 数据持久化与离线同步 ​

学习目标 ​

学完本章，你将能够：

  • 在 drift、sqlite3、isar 之间做选型，说清代码生成、平台支持与迁移能力的取舍
  • 设计可迁移的 schema：版本表、向前迁移、默认值、索引与数据回填
  • 用 EXPLAIN QUERY PLAN 判断查询是否命中索引，而不是凭感觉加索引
  • 识别 SQLCipher 的真实接入条件，知道普通 SQLite 的「加密开关」为什么不能直接生效
  • 实现 outbox 模式：本地先写、操作入队、幂等推送、失败重试
  • 区分服务端优先、客户端优先与字段级三方合并，并说明各自适用的业务
  • 设计增量同步游标与断点续传，避免全量拉取和重复拉取
  • 为缓存设置容量与淘汰策略，并用命中率而不是「缓存越大越好」做决策

本章的两套代码

  • 真实依赖实现：labs/enterprise_app 引入 sqlite3（直接绑定，无代码生成）、path、path_provider，在桌面端运行真实 SQLite：v1 → v2 迁移、索引与查询计划、outbox、服务端冲突与增量游标都有单元测试。
  • 零依赖机制演示：app/ 的「数据层」新增 2 个示例，用内存集合模拟 outbox、冲突合并、迁移与 LRU 淘汰；不涉及任何第三方依赖。
  • 边界声明：本章不实现真实网络同步服务端。FakeSyncServer 是内存对象，只用于验证客户端同步算法；SQLCipher 只做能力探测，未替换原生库。

一、选型：drift、sqlite3、isar 怎么选 ​

先明确一件事：选型不是选「最流行」，而是选「迁移与调试成本最低」。

方案本质优点代价适合
sqlite3直接绑定 SQLite C API无代码生成、SQL 完全可控、迁移显式、依赖少需要自己写 SQL、映射与迁移；无类型安全查询 DSL中小型数据层、需要看清每条 SQL、教学与排障
driftSQLite + 代码生成类型安全查询、编译期校验、迁移工具、流式 watch引入 build_runner / 生成代码；升级时需要重新生成表结构多、查询复杂、团队需要强约束
isar面向对象的 NoSQL 引擎查询快、API 简洁、支持索引与 watch社区维护版本迭代节奏与 SQL 生态不同；复杂关联与迁移要重新学习读多写少、对象图为主、不需要 SQL 报表

本实验工程选择 sqlite3，原因很实际：

  1. 不引入代码生成：实验工程要能 flutter test 直接跑，不想额外维护 build_runner 流程；
  2. 迁移可见：ALTER TABLE、CREATE INDEX、PRAGMA user_version 都写在代码里，读者能逐行对照；
  3. 依赖固定：sqlite3: 2.9.4 使用动态库加载，不触发 native assets 构建钩子；
  4. 平台限制明确：桌面端可直接用系统 SQLite；移动端要额外引入 sqlite3_flutter_libs，Web 不支持。

不要用「模拟数据库」冒充 SQLite

app/ 里的内存实现只是机制演示：它没有事务、没有真实索引、没有磁盘持久化。真实项目必须落到 labs/enterprise_app 这种带真实依赖的工程里验证。

二、schema 设计与版本迁移 ​

2.1 最小可用 schema ​

本章的待办表：

sql
-- v1
CREATE TABLE todos(
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  done INTEGER NOT NULL DEFAULT 0,
  deleted INTEGER NOT NULL DEFAULT 0,
  version INTEGER NOT NULL DEFAULT 1,
  updated_at INTEGER NOT NULL
);

设计要点：

  • 软删除：deleted 而不是直接 DELETE，否则离线端无法把删除动作同步出去；
  • 版本号：version 用于乐观并发控制，服务端用它判断「你改的时候别人是否也改过」；
  • 时间戳：updated_at 用毫秒整数，避免时区与字符串排序问题；
  • 不存 UI 状态：选中态、展开态等不要进库，否则每次交互都写磁盘。

2.2 迁移不是「加个字段」那么简单 ​

一次安全的迁移至少包含：

  1. 读取当前版本（SQLite 用 PRAGMA user_version）；
  2. 在事务里执行结构变更；
  3. 给新列设置默认值，必要时回填历史数据；
  4. 创建索引；
  5. 写回新版本号；
  6. 失败时回滚。

本工程 v2 迁移：

sql
ALTER TABLE todos ADD COLUMN note TEXT NOT NULL DEFAULT '';
CREATE INDEX idx_todos_updated_at ON todos(updated_at DESC);
CREATE INDEX idx_todos_alive ON todos(deleted, updated_at DESC);
PRAGMA user_version = 2;

迁移的三个致命错误

  • 先改代码后迁移：新代码读 note，旧库没有列，启动即崩。
  • 迁移里做耗时回填：几百万行 UPDATE 放在启动路径上，用户看到白屏。
  • 迁移不可重复执行：没有版本判断，第二次启动重复加列直接报错。

实验页展示迁移前后的列集合、行数与耗时；点「重建 v1 并迁移」可以反复观察。

三、索引与查询性能 ​

索引不是越多越好。判断标准只有两个：

  1. 查询计划是否真的使用它；
  2. 写入与存储成本是否可接受。

用 EXPLAIN QUERY PLAN 看：

dart
final ResultSet plan = db.select(
  'EXPLAIN QUERY PLAN SELECT * FROM todos WHERE updated_at > 100 LIMIT 20',
);
for (final Row row in plan) {
  print(row['detail']); // SCAN todos 或 SEARCH todos USING INDEX ...
}

本工程实验页对 5000 行数据做对比，同时展示：

  • 无索引：SCAN，全表扫描；
  • 有索引：SEARCH ... USING INDEX idx_...，只访问命中行；
  • 20 次查询的合计耗时。

索引选择经验

  • 列表页最常见的查询是「未删除 + 按更新时间倒序」，复合索引 (deleted, updated_at DESC) 比单列索引更贴合。
  • 低选择性列（如布尔值）单独建索引收益有限，通常要和其他列组合。
  • 索引会增加写入成本与包体积；迁移时一次性建索引比运行时反复建更稳。
  • 排序字段与过滤字段顺序要匹配查询：WHERE deleted = 0 ORDER BY updated_at DESC 对应 (deleted, updated_at)。

四、加密存储：SQLCipher 的真实条件 ​

「数据库加密」在 Flutter 里通常指 SQLCipher：它是 SQLite 的加密分支，支持 PRAGMA key / PRAGMA rekey。

真实接入需要三步：

  1. 使用带 SQLCipher 的原生库（例如 sqlcipher_flutter_libs，或自行编译）；
  2. 打开连接后立刻执行 PRAGMA key = '...'；
  3. 用 PRAGMA cipher_version 验证当前库确实是 SQLCipher，而不是普通 SQLite。

本工程的实验页做了一个真实探测：

dart
final ResultSet rs = db.select('PRAGMA cipher_version');
final bool supported = rs.isNotEmpty && '${rs.first.values.first}'.isNotEmpty;

在普通 SQLite 上，该查询返回空，页面会明确提示「未检测到 SQLCipher」，开关处于禁用状态。这不是功能缺失的伪装，而是运行库能力的真实反馈。

常见的「假加密」

  • 在普通 SQLite 上执行 PRAGMA key：不会加密，也不会报错，数据仍是明文。
  • 自己写 XOR / Base64「加密」：不是密码学，不要用于生产。
  • 只加密字段不加密索引：索引仍可能泄露原文特征。

生产建议：

  • 密钥走系统安全存储（Keychain / Keystore），不要硬编码；
  • 加密库升级要验证旧库可读，迁移前先备份；
  • Web 端没有 SQLCipher，需要换方案（如服务端加密 + 本地 IndexedDB 仅存密文）。

五、outbox 模式与幂等 ​

离线优先的核心不是「先写本地」，而是把本地写入变成一个可重放的操作。

5.1 表结构 ​

sql
CREATE TABLE outbox(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  entity_id TEXT NOT NULL,
  op TEXT NOT NULL,
  idempotency_key TEXT NOT NULL UNIQUE,
  base_version INTEGER NOT NULL,
  payload TEXT NOT NULL,
  base_payload TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  attempts INTEGER NOT NULL DEFAULT 0
);
  • payload：修改后的完整实体快照；
  • base_payload：修改前快照，供字段级三方合并使用；
  • base_version：服务端已知版本，用于冲突检测；
  • idempotency_key：同一操作的唯一标识，服务端重复收到时只应用一次。

5.2 合并离线编辑 ​

用户离线连续改三次标题，不应该产生三条推送。工程里的做法是：

  • 同一 entity_id 只保留一条 outbox；
  • 更新 payload 与 idempotency_key；
  • base_version 与 base_payload 保持第一次修改前的值。

这样服务端只看到「从 base 到最新」的一次变化，既减少请求，也让冲突语义更清晰。

5.3 幂等 ​

服务端记录已应用的 idempotency_key。重复请求直接返回「已处理」，不重复写库。

幂等键怎么设计

推荐 实体 id + 目标版本号，例如 t1:3。不要用随机 UUID：重试时无法复用同一个键，就失去幂等意义。

六、冲突检测与解决 ​

6.1 什么时候会冲突 ​

客户端推送时带上 base_version。服务端当前版本与它不一致，说明两端都改过，进入冲突流程。

6.2 三种策略 ​

策略行为适合风险
服务端优先整体采用服务端版本配置、审批、财务等强一致数据用户本地修改被覆盖
客户端优先整体保留本地版本个人草稿、离线笔记覆盖别人刚改的内容
字段级合并逐字段三方合并待办、通讯录、资料卡需要 base 快照，逻辑更复杂

字段级合并规则：

  1. 只有一端改了某字段 → 采用改的那一端；
  2. 两端都改了同一字段 → 比较 updatedAt，新的胜出；时间相同则服务端胜出；
  3. 删除是一票通过：任意一端删除，结果为删除。

没有 base 就没有「字段级合并」

只知道「本地当前值」和「服务端当前值」，无法判断谁改了什么。必须保存修改前快照，这正是 outbox 里 base_payload 的作用。

七、增量同步与断点续传 ​

全量拉取的问题：流量大、合并慢、弱网下永远拉不完。

本工程用单调递增 revision 作为游标：

dart
final List<ServerRecord> records = server.changesSince(cursor, limit: 20);
for (final ServerRecord record in records) {
  // 合并到本地
  cursor = record.revision;
}

要点：

  • 游标持久化在本地 meta 表，进程重启后可继续；
  • 每次限制批量大小（如 20），避免一次拉爆内存；
  • 拉取成功后再推进游标，失败时保持旧游标，下次从断点继续；
  • 合并规则：本地版本更新则保留本地，服务端版本更新则覆盖；两边都改则走冲突策略。

断点续传的正确姿势

「先拉取、再合并、最后写游标」的顺序不能反。先写游标再合并，一旦合并失败，这段数据就永久丢失了。

八、缓存容量与淘汰 ​

数据库之上通常还有一层内存缓存。缓存不是越大越好：

  • 太大：内存占用高，GC 压力大，移动端容易被系统杀；
  • 太小：命中率低，频繁回查数据库。

常见策略：

策略淘汰依据适合
LRU最久未使用列表页、详情页缓存
LFU使用频率最低热点差异明显的场景
TTL过期时间时效性数据、接口缓存
容量 + TTL双重约束大多数生产场景

本工程用 LruCache 演示容量与命中率的关系，并统计命中、未命中与淘汰次数。

缓存键要带「版本」

用实体 id 做键时，实体更新后旧缓存仍然命中。建议键里带 version，或更新时主动失效。

九、实验工程：真实实现到哪一步 ​

可运行示例 ​

下面这段零依赖示例把本地待办、outbox 计数、服务端修改、字段级合并与游标放在一个页面：

DartPad 运行环境将在滚动到此处时加载…
查看完整源码
dart
import 'package:flutter/material.dart';

/// 零依赖演示：本地待办 + outbox + 字段级冲突合并 + 增量游标。
/// 真实 SQLite（schema / 迁移 / 索引 / 事务）见 labs/enterprise_app 第 43 章。
void main() => runApp(const SyncDemoApp());

class SyncDemoApp extends StatelessWidget {
  const SyncDemoApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      theme: ThemeData(colorSchemeSeed: Colors.indigo, useMaterial3: true),
      home: const SyncDemoHome(),
    );
  }
}

class _Todo {
  _Todo(this.id, this.title, {this.done = false, this.version = 1});

  final String id;
  String title;
  bool done;
  int version;
}

enum Policy { server, client, field }

class SyncDemoHome extends StatefulWidget {
  const SyncDemoHome({super.key});

  @override
  State<SyncDemoHome> createState() => _SyncDemoHomeState();
}

class _SyncDemoHomeState extends State<SyncDemoHome> {
  final List<_Todo> local = <_Todo>[
    _Todo('t1', '写周报'),
    _Todo('t2', '修同步冲突'),
  ];

  final List<_Todo> server = <_Todo>[
    _Todo('t1', '写周报'),
    _Todo('t2', '修同步冲突'),
  ];

  final List<String> log = <String>[];
  final Set<String> applied = <String>{};
  Policy policy = Policy.field;
  int outbox = 0;
  int cursor = 0;
  int revision = 0;

  _Todo find(List<_Todo> list, String id) => list.firstWhere((_Todo t) => t.id == id);

  void localEdit() {
    final _Todo t = local.first;
    t.title = '${t.title}（本地改）';
    t.version++;
    outbox = 1;
    log.insert(0, '本地修改 t1 → v${t.version}，写入 outbox');
    setState(() {});
  }

  void remoteEdit() {
    final _Todo t = find(server, 't1');
    t.title = '服务端改的标题';
    t.version++;
    revision++;
    cursor = 0;
    log.insert(0, '服务端修改 t1 → v${t.version}');
    setState(() {});
  }

  void sync() {
    if (outbox > 0) {
      final _Todo mine = local.first;
      final _Todo theirs = find(server, 't1');
      if (theirs.version != mine.version - 1) {
        if (policy == Policy.server) {
          mine.title = theirs.title;
        } else if (policy == Policy.client) {
          theirs.title = mine.title;
        } else {
          mine.title = mine.title.contains('本地改') ? mine.title : theirs.title;
        }
        mine.version = (mine.version > theirs.version ? mine.version : theirs.version) + 1;
        theirs.title = mine.title;
        theirs.version = mine.version;
        log.insert(0, '冲突：${policy.name} → 合并为「${mine.title}」v${mine.version}');
      } else {
        find(server, 't1').title = mine.title;
        find(server, 't1').version = mine.version;
      }
      revision++;
      applied.add('t1:${mine.version}');
      outbox = 0;
      log.insert(0, '推送成功，幂等键 t1:${mine.version} 已记录');
    }
    if (revision > cursor) {
      cursor = revision;
      log.insert(0, '按游标拉取增量到 revision=$cursor');
    }
    setState(() {});
  }

常见坑 ​

高频踩坑点

  1. 没有版本表：靠代码判断「表存在就跳过」，迁移逻辑很快失控。
  2. 迁移不包事务：中途失败留下半张新表，启动直接报错。
  3. 新列没有默认值：历史行读取失败。
  4. 软删除没同步：本地删了，服务端不知道，下次拉取又回来。
  5. outbox 不合并：离线改十次发十个请求，冲突概率翻倍。
  6. 幂等键用随机值：重试时换了新键，服务端重复应用。
  7. 先写游标再合并：合并失败后这段数据再也拉不到。
  8. 无索引就上线：数据量小看不出，半年后列表页开始卡。
  9. 索引建太多：写入放大、包体积增加，收益却不确定。
  10. 把 PRAGMA key 当加密：普通 SQLite 静默忽略，数据仍是明文。
  11. 缓存键不带版本：更新后仍读旧缓存。
  12. 缓存无上限：图片 / 列表全塞内存，移动端被系统回收。
  13. 服务端优先一刀切：用户离线写的笔记被静默覆盖，投诉必然出现。
  14. 没有 base 快照：字段级合并退化成整体覆盖。
  15. Web 直接 import dart:io：构建失败，必须条件导入。
