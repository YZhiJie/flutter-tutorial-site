学习目标 ​

学完本章，你将能够：

  • 区分 fake 与 mock 的边界，写出「同一套契约跑多个实现」的 Repository 测试

  • 识别 flaky 的根因，设计可复现、可统计、可治理的 E2E 策略

这一章不是「测试理论课」，而是测试代码本身作为示例。所有关键测试都能在 labs/enterprise_app/test/ 里找到可运行的源码；app/ 提供零依赖的可视化预览。

一、pump 的时序模型 ​

先把三个 API 说清楚：

API做了什么不会做什么
pump()调度一帧：构建、布局、绘制、执行微任务不推进真实计时器；不会等 Future.delayed 完成
pump(Duration)把假时钟推进指定时长，再调度一帧不会自动反复 pump 直到稳定
pumpAndSettle()反复 pump，直到没有待处理帧（或超时）遇到无限动画会一直跑到超时

一个常见的误解是：

dart
await tester.pumpWidget(const _DelayedBox());
expect(find.text('loading'), findsOneWidget);

await tester.pump(); // ❌ 不会让 500ms 的 Future 完成
expect(find.text('done'), findsOneWidget); // 失败

正确写法是推进假时间：

dart
await tester.pump(const Duration(milliseconds: 500));
expect(find.text('done'), findsOneWidget);

pumpAndSettle 不是万能等待

pumpAndSettle 只适合有限动画。遇到 AnimationController.repeat()、持续 loading 指示器、无限滚动，它会一直有下一帧，最终抛出 pumpAndSettle timed out。测试里应优先用 pump(Duration) 精确推进。

1.1 Ticker 驱动的逐帧测试 ​

需要断言动画中间状态时，手动 pump：

dart
final controller = AnimationController(
  vsync: const TestVSync(),
  duration: const Duration(milliseconds: 100),
);
controller.forward();
await tester.pump();                              // 启动 ticker
await tester.pump(const Duration(milliseconds: 25));
expect(controller.value, closeTo(0.25, 0.001));
await tester.pump(const Duration(milliseconds: 50));
expect(controller.value, closeTo(0.75, 0.001));

注意首帧只负责启动 ticker；如果要走完 100ms，需要让累加的 pump 时间覆盖整个时长。测试结束前显式 controller.dispose()，避免残留 ticker。

1.2 真实异步用 runAsync ​

Future.delayed 在测试里默认走假时钟。要等真实 IO / 定时器：

dart
await tester.runAsync(() async {
  await Future<void>.delayed(const Duration(milliseconds: 10));
});

labs/enterprise_app/test/pump_timing_test.dart 包含：

  • pump 不推进 Future 的对照

二、Finder 策略与 Semantics ​

2.1 Finder 的选择顺序 ​

推荐优先级：

  1. find.byKey：最稳定，适合关键交互点；
  2. find.bySemanticsLabel：贴近用户感知与无障碍；
  3. find.text：适合文案断言，但文案改动会碎；
  4. find.byType / find.byWidgetPredicate：适合结构性断言；
  5. find.descendant / find.ancestor：限定范围，避免全局匹配。
dart
expect(find.byKey(const Key('syncButton')), findsOneWidget);
expect(find.text('Status idle'), findsOneWidget);
expect(
  find.descendant(of: find.byType(Card), matching: find.text('Card title')),
  findsOneWidget,
);

避免「碰巧找到」

find.text('Save') 在页面上有 5 个「Save」按钮时会直接失败或匹配错元素。用 find.descendant 限定容器，或给关键控件加 Key。

2.2 Semantics 断言 ​

dart
final handle = tester.ensureSemantics();
expect(find.bySemanticsLabel('sync now'), findsOneWidget);
expect(
  tester.getSemantics(find.byKey(const Key('syncButton'))),
  matchesSemantics(label: 'sync now', isButton: true, hasTapAction: true),
);
handle.dispose();

ensureSemantics() 会打开语义树；测试结束必须 dispose()，否则会影响后续用例。

合并语义节点

Semantics(label: ...) 默认会合并子节点，子按钮的文本也可能进入 label。想让 label 精确可控，使用 excludeSemantics: true 并提供自己的 onTap。

三、fake 与 mock 的边界 ​

类型是什么适合风险
fake手写的轻量实现，行为接近真实内存仓库、假时钟、假网络行为可能与真实实现漂移
mock预置调用与返回，验证交互验证「是否调用了某个方法 / 参数」过度绑定实现细节，重构即碎
stub固定返回值单一分支测试覆盖不足

选择原则：

  • 测业务规则：用 fake，让真实的数据流跑起来；
  • 测交互协议：用 mock，断言调用次数与参数；
  • 测真实 SQL / 序列化：别用 fake，直接跑真实实现（如 SQLite 内存库）。

本工程的同步算法测试用的是 fake 服务端（FakeSyncServer），因为它需要真实地推进版本、产生 revision 与冲突；如果用 mock 固定返回，就测不到冲突逻辑。

四、Repository 契约测试 ​

核心思想：同一套用例，跑多个实现。接口定义行为，实现各自不同。

dart
abstract interface class TodoStore {
  List<TodoItem> list();
  TodoItem add(String title);
  void toggleDone(String id);
  void remove(String id);
}

void runTodoStoreContract(
  String name,
  TodoStore Function() create,
  void Function(TodoStore store) dispose,
) {
  group('契约：$name', () {
    late TodoStore store;
    setUp(() => store = create());
    tearDown(() => dispose(store));

    test('新增后可见且默认未完成', () {
      final item = store.add('写周报');
      expect(store.list().single.done, isFalse);
      expect(store.list().single.version, 1);
      expect(item.id, isNotEmpty);
    });

    test('删除后从列表消失', () {
      final item = store.add('临时项');
      store.remove(item.id);
      expect(store.list(), isEmpty);
    });
  });
}

然后分别跑：

dart
runTodoStoreContract('FakeTodoStore', () => _FakeTodoStore(), (_) {});
runTodoStoreContract(
  'SqliteTodoRepository',
  () => _SqliteTodoStore(),
  (store) => (store as _SqliteTodoStore).dispose(),
);

本工程真实跑了两套：

  • _FakeTodoStore：内存 Map；
  • _SqliteTodoStore：包住真实 SQLite（interop 内存库，schema 迁移照常执行）。

契约测试的价值

新增实现（缓存层、远端仓库、离线队列）时，不需要重写用例；只要实现契约，同一套测试自动覆盖。契约测试还能暴露 fake 与真实实现的语义差异，例如「删除未知 id 是否抛错」。

契约要写「行为」而不是「实现」

不要在契约里断言 SQL 语句、表名或内部字段。断言用户可见行为：列表内容、状态变化、异常类型。

五、golden 测试：矩阵、字体与平台 ​

5.1 为什么 golden 容易碎 ​

golden 是像素级快照，受以下因素影响：

  • 字体（默认测试字体 Ahem 会把文字画成方块）；
  • 平台（Material / Cupertino 的控件样式不同）；
  • 分辨率与 devicePixelRatio；
  • 主题（亮 / 暗、Material 版本）；
  • 阴影、抗锯齿、引擎版本。

5.2 字体加载 ​

测试环境不会自动加载项目字体。需要显式加载：

dart
setUpAll(() async {
  final bytes = File('test/fonts/Roboto-Regular.ttf').readAsBytesSync();
  final loader = FontLoader('Roboto')
    ..addFont(Future.value(ByteData.view(bytes.buffer)));
  await loader.load();
});

图标同样如此：不加载 MaterialIcons，图标会变成方块。本工程把 Roboto 与 MaterialIcons 字体放在 test/fonts/，只在测试中使用。

5.4 多平台 / 多分辨率 ​

  • 平台：把 ThemeData(platform: ...) 作为参数，分别生成 Android / iOS / macOS 基准；
  • 分辨率：设置 tester.view.physicalSize 与 devicePixelRatio，覆盖 320 / 360 / 640 等宽度；
  • 字号：通过 MediaQuery.textScaler 覆盖 1.0 / 1.3 / 1.5；
  • 主题：亮 / 暗各一份。

矩阵全部生成会让 golden 数量爆炸。工程上的折中：

  1. 关键状态 × 主题：生成 golden；
  2. 平台 × 分辨率 × 字号：用布局断言（无溢出、关键文本可见）而不是像素对比；
  3. golden 基准按平台维护，CI 只在与基准相同的平台运行。

本工程的测试：

  • 6 张 golden（loading / error / data × light / dark）；
  • 一个「3 平台 × 2 分辨率 × 1.3 字号」的布局断言，检查 takeException() 为空且关键内容可见。

golden 的三个坑

  • 不加载字体会得到方块字基准，之后永远对不上；
  • 跨平台复用 golden 会因字体 / 阴影差异必挂；
  • 用 pumpAndSettle 等动画结束后再截图，否则截到中间帧。

六、E2E 稳定性与 flaky 治理 ​

6.1 flaky 的判定 ​

只看一次失败无法下结论。至少运行 5 次：

结果判定
全通过稳定通过
全失败稳定失败（坏用例，不是 flaky）
有通过有失败flaky
少于 5 次样本不足

本工程实现了 FlakyDetector 与 RetryRunner，并用单元测试锁定判定规则。

6.2 常见根因 ​

  1. 真实时间：DateTime.now()、sleep、超时阈值；
  2. 未固定随机：Random() 未设种子；
  3. 动画未稳定：pumpAndSettle 遇到无限动画；
  4. 网络与外部服务：真实接口、CDN、第三方登录；
  5. 共享状态：用例之间没隔离，顺序依赖；
  6. 设备差异：分辨率、系统版本、权限弹窗；
  7. 异步竞态：没等待关键 Future 就断言。

6.3 治理流程 ​

text
发现失败 → 重跑复现（固定种子 / 固定时钟 / 固定网络）
        → 记录失败率（≥5 次）
        → 判定 flaky
        → 隔离到 quarantine 任务，不阻塞主分支
        → 定位根因 → 修复 → 连续 N 次通过后移出隔离

不要用「自动重试」掩盖 flaky

重试只能降低红灯概率，不能修复根因。把重试次数、隔离名单、修复期限写进流程，而不是无限重试。

6.4 设备农场与 Patrol ​

  • 设备农场：多机型、多系统版本并行跑 E2E，暴露真实设备差异（权限、输入法、深色模式、刘海屏）；
  • Patrol：在 integration_test 之上提供原生交互能力（权限弹窗、通知、系统设置）与录制回放；
  • 录制回放：把人工路径录制为脚本，先跑 smoke，再逐步替换为稳定断言；
  • 分片：按模块拆分 E2E 任务，减少单任务时长与相互影响。

本工程没有接入真实设备农场或 Patrol（需要真机 / 云服务），正文只给出策略；本地可复现的部分放在单元 / widget 测试里。

dart
// 纯 Dart 可运行示例：同一套 Repository 契约跑两个实现，并演示 flaky 判定。
// 真实 Flutter 测试（pump / Semantics / golden）见 labs/enterprise_app/test/。

abstract interface class TodoStore {
  List<String> list();

  String add(String title);

  void toggle(String id);

  void remove(String id);
}

class FakeTodoStore implements TodoStore {
  final Map<String, String> _items = <String, String>{};
  final Map<String, bool> _done = <String, bool>{};
  final Set<String> _deleted = <String>{};
  int _sequence = 0;

  @override
  List<String> list() => _items.keys
      .where((String id) => !_deleted.contains(id))
      .toList(growable: false);

  @override
  String add(String title) {
    _sequence++;
    final String id = 'fake-$_sequence';
    _items[id] = title;
    _done[id] = false;
    return id;
  }

  @override
  void toggle(String id) {
    _require(id);
    _done[id] = !_done[id]!;
  }

  @override
  void remove(String id) {
    _require(id);
    _deleted.add(id);
  }

  void _require(String id) {
    if (!_items.containsKey(id)) throw ArgumentError('missing $id');
  }
}

/// 第二个实现：故意用不同的内部结构（List + Map），验证契约不依赖实现细节。
class ListTodoStore implements TodoStore {
  final List<Map<String, Object>> _rows = <Map<String, Object>>[];
  int _sequence = 0;

  @override
  List<String> list() => _rows
      .where((Map<String, Object> row) => row['deleted'] == false)
      .map((Map<String, Object> row) => row['id']! as String)
      .toList(growable: false);

  @override
  String add(String title) {
    _sequence++;
    final String id = 'list-$_sequence';
    _rows.add(<String, Object>{
      'id': id,
      'title': title,
      'done': false,
      'deleted': false,
    });
    return id;
  }

  @override
  void toggle(String id) {
    final Map<String, Object> row = _find(id);
    row['done'] = !(row['done']! as bool);
  }

  @override
  void remove(String id) {
    _find(id)['deleted'] = true;
  }

  Map<String, Object> _find(String id) {
    for (final Map<String, Object> row in _rows) {
      if (row['id'] == id) return row;
    }
    throw ArgumentError('missing $id');
  }
}

void expectTrue(bool value, String message) {
  if (!value) throw StateError('FAIL: $message');
}

/// 同一套契约：任何实现都必须满足。
void runContract(String name, TodoStore Function() create) {
  final TodoStore store = create();
  expectTrue(store.list().isEmpty, '$name 初始为空');
  final String id = store.add('写周报');
  expectTrue(store.list().length == 1, '$name 新增后可见');
  store.toggle(id);
  store.toggle(id);
  expectTrue(store.list().contains(id), '$name 两次 toggle 仍存在');
  store.remove(id);
  expectTrue(!store.list().contains(id), '$name 删除后隐藏');
  try {
    store.remove('missing');
    throw StateError('FAIL: $name 未对不存在 id 报错');
  } on ArgumentError {
    // 期望行为
  }
  print('PASS contract: $name');
}

enum FlakyStatus { stablePass, stableFail, flaky, insufficient }

FlakyStatus classify(List<bool> results) {
  if (results.length < 5) return FlakyStatus.insufficient;
  final int passes = results.where((bool pass) => pass).length;
  if (passes == results.length) return FlakyStatus.stablePass;
  if (passes == 0) return FlakyStatus.stableFail;
  return FlakyStatus.flaky;
}

void main() {
  runContract('FakeTodoStore', () => FakeTodoStore());
  runContract('ListTodoStore', () => ListTodoStore());

  final List<bool> samples = <bool>[true, false, true, true, false];
  print('flaky 判定: ${classify(samples).name}');
  print('重试 3 次 [F, F, T] → 第 3 次通过：重试只是止血，不是修复');
}

常见坑 ​

高频踩坑点

  1. 用 pump() 等 Future.delayed：永远等不到，必须 pump(Duration)。
  2. 对无限动画用 pumpAndSettle：超时是必然结果。
  3. 测试结束不 dispose 语义句柄：污染后续用例。
  4. Finder 太宽：多个同名文本导致匹配失败或匹配错元素。
  5. fake 与真实实现语义漂移：契约测试能提前发现。
  6. mock 过度：断言内部调用顺序，重构即碎。
  7. golden 不加载字体：基准图全是方块。
  8. 跨平台复用 golden：平台字体 / 阴影不同，必挂。
  9. golden 截到动画中间帧：先稳定再截图。
  10. 用 DateTime.now() 做断言：跨午夜、慢机器都会漂。
  11. 随机数不固定种子：失败无法复现。
  12. 重试掩盖根因：红灯变绿灯，问题还在。
  13. E2E 依赖真实第三方服务：登录页改版就全挂。
  14. 用例顺序依赖：单跑通过、全量失败。
  15. 把 flaky 当稳定失败处理：直接删除用例，失去覆盖。
