46 · 性能专项：图片、网络首屏、功耗 ​

学习目标 ​

学完本章，你将能够：

  • 用统一口径度量图片的内存与解码成本，并给出可执行的预算
  • 画出一张请求瀑布图，分清 TTFB、关键路径、并行收益与重复请求
  • 定义首屏指标（首帧 / 首内容 / 可交互），并判断并行与串行的取舍
  • 说清功耗、温控与后台任务的观测方法，以及为什么它们很难进 CI
  • 拆解启动耗时（引擎预热、deferred 组件、闪屏衔接），定位最大头
  • 建立「基线 → 容差 → 回归」的性能门禁，而不是每次靠手感

与第 38 章的边界

38 · 图片与媒体工程 讲怎么做：目标尺寸解码、缓存策略、预加载、压缩上传。本章只讲怎么度量、怎么定预算、怎么回归：同一张图解码后占多少内存、P90 解码多久、首屏关键路径多长、功耗预算怎么定。两章不重复实现细节。

一、先统一度量口径 ​

性能讨论最容易变成「我感觉变快了」。先固定四件事：

  1. 设备分档：低端 / 中端 / 高端，至少各一台；模拟器结论不作数。
  2. 构建模式：profile 还是 release；debug 模式下的耗时没有参考价值。
  3. 采样方式：单次采样只能看趋势，结论要用 P50 / P90 / P99。
  4. 指标定义：同名指标必须同口径，例如「首帧」是引擎第一帧还是业务首帧。
dart
class MetricSnapshot {
  const MetricSnapshot(this.name, this.value, this.unit);
  final String name;
  final double value;
  final String unit;
}

没有基线的性能数据等于没有数据。每次优化前先存一份 baseline，优化后用同一口径比较。

二、图片：内存预算与解码成本 ​

2.1 内存口径 ​

图片解码后的内存和文件大小无关，近似为：

解码后字节 = 宽 × 高 × 4（RGBA8888）

一张 1080 × 1920 的图，文件可能只有 200KB，解码后却是 7.9MB；6 张就是 47MB。若在 3x 屏按物理像素解码，内存会是逻辑尺寸的 9 倍。

预算建议按设备分档：

设备档位单图上限首屏图片总内存单图解码 P90
低端4MB24MB80ms
中端8MB48MB120ms
高端16MB96MB200ms

这些数字不是标准答案，而是你必须显式写下来的假设。

2.2 解码耗时怎么量 ​

最小可用的测量流程：

dart
final Stopwatch sw = Stopwatch()..start();
final ui.Codec codec = await ui.instantiateImageCodec(bytes);
final ui.FrameInfo frame = await codec.getNextFrame();
sw.stop();
final double decodeMs = sw.elapsedMicroseconds / 1000.0;

注意事项：

  • 必须在 profile / release 下测，debug 的 JIT 与断言会显著放大耗时；
  • 先 warm up 一到两次，避免首次加载的动态库/着色器开销；
  • 记录图片尺寸、文件大小、解码格式（PNG / JPEG / WebP）；
  • 同一张图重复解码可能命中引擎缓存，测量时要换图或清缓存；
  • 解码线程数与 instantiateImageCodec 的目标尺寸都会影响结果。

[labs 的 image_decode_probe.dart](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/flutter-tutorial/labs/enterprise_app/lib/performance/image_decode_probe.dart) 用「生成 PNG → 解码」的方式做真实测量；它不是缓存实现，只是把测量流程固定下来。

2.3 编码格式的取舍 ​

格式解码成本适用
JPEG较低照片、渐变
PNG较高（无损 + Alpha）图标、截图、需要透明
WebP中等网络图片，兼顾体积
AVIF / HEIF较高（部分设备无硬解）大图、可接受兼容性成本

不要用「文件更小」直接推导「体验更好」：解码耗时、内存峰值、兼容性都要进预算。

三、网络与首屏 ​

3.1 请求瀑布图 ​

一张瀑布图要能回答四个问题：

  • 谁先发？谁最后结束？
  • 首字节（TTFB）是什么时候？
  • 哪些请求是并行的，哪些被串行阻塞？
  • 有没有重复请求 / 缓存未命中？
dart
class RequestSpan {
  const RequestSpan({
    required this.name,
    required this.startMs,
    required this.ttfbMs,
    required this.endMs,
    required this.bytes,
    this.cacheHit = false,
  });
  // ...
}

在瀑布图上，关键路径 = 最晚结束的请求，而不是所有请求耗时的总和。把非关键请求延后，往往比提高并发更能改善首屏。

3.2 并行与串行的取舍 ​

  • 并行能压缩墙钟时间，但会争抢连接、带宽与解码线程；
  • HTTP/2 多路复用减少了连接数瓶颈，但服务端排队仍可能让并行退化；
  • 串行适合有依赖的请求（token → 用户信息 → 列表）；
  • 首屏只保留关键请求，其余进入空闲预取；
  • 设置超时与降级：关键请求超时后先用骨架屏/缓存，别让整页卡住。

3.3 首屏指标 ​

指标定义建议预算
TTFB最早拿到首字节≤ 200ms
首帧引擎画出第一帧≤ 300ms
首内容业务内容可见（非骨架）≤ 500ms
可交互关键路径结束 + 首帧渲染≤ 600ms

骨架屏要单独度量：骨架出现 ≠ 内容出现。如果骨架屏本身要等网络，那它只是把白屏换成了灰屏。

四、功耗、温控与后台 ​

功耗是最难在 CI 里量的一类指标，因为它依赖：

  • 屏幕亮度与刷新率；
  • 网络制式（Wi-Fi / 5G / 弱网重传）；
  • 设备温度与温控策略；
  • 后台执行限制（Android Doze、iOS BackgroundTasks）；
  • 厂商调度策略。

可用的观测手段：

  1. 系统级：Android Battery Historian / Perfetto、iOS Energy Log；
  2. 应用级：自建采样（CPU 时间、唤醒次数、网络字节、帧率）；
  3. 温控：读取热状态（nominal / fair / serious / critical），记录降频时刻；
  4. 后台：统计 wake lock、定时任务、推送唤醒与后台定位。

本章实验页用一个相对模型做预算演示：

估算 mAh = 亮屏分钟 × (屏幕基线 + CPU 增量) + 流量 MB × 单位成本

它不能预测真实续航，但能比较「同一操作在不同 CPU/网络配置下」的相对成本，并给出温控降级建议。

五、启动深水区 ​

启动时间要拆成可归因的阶段：

阶段内容常见问题
引擎预热引擎初始化、着色器预热首次启动冷、后续热，指标要分开
Dart 初始化绑定、依赖注入、配置读取同步 IO 阻塞首帧
deferred 组件延迟加载的功能模块加载完成前交互不可用
首帧渲染首屏 Widget 构建与布局过度构建、同步图片解码
闪屏衔接原生闪屏 → Flutter 首帧衔接空白、跳变、重复动画

度量方式：

  • 用 Timeline / FrameTiming 记录首帧；
  • 在关键阶段打自定义 trace（Timeline.startSync）；
  • 冷启动与热启动分开统计；
  • deferred 组件要记录「加载开始 / 完成 / 首次可交互」三个时刻；
  • 闪屏衔接用录屏逐帧核对，不要只看日志。

六、回归与预算门禁 ​

性能门禁的最小闭环：

  1. 固定设备、构建模式、图片与网络条件；
  2. 每次跑 N 次，取 P50 / P90；
  3. 与 baseline 比，超过容差即失败；
  4. 失败时保留 trace / 截图 / 采样数据；
  5. 只允许「有理由的放宽」，例如业务需求变化，并把理由写进记录。
dart
final deltaPct = (current - baseline) / baseline * 100;
final pass = deltaPct <= tolerancePct; // 例如 10%

能进 CI 的部分：

  • 纯计算模型（预算、分桶、回归比较）可以单测；
  • 图片解码、首帧、功耗需要真机或设备农场；
  • 网络瀑布可以用本地 mock 服务固定时序，但真实网络仍要单独验证。

可运行示例 ​

下面这段纯 Dart 示例把「图片预算、请求瀑布、首屏、功耗、回归」串成一条可打印的检查链：

dart
/// 纯 Dart 预算校验脚本：可直接 `dart run`，也可作为 CI 原型。
///
/// 它不做真实解码或网络请求，只验证「口径 → 预算 → 回归」这条链路。
void main() {
  _checkImageBudget();
  _checkWaterfall();
  _checkFirstScreen();
  _checkPower();
  _checkRegression();
}

void _checkImageBudget() {
  const int width = 1080;
  const int height = 1920;
  const int count = 6;
  const double budgetMb = 64;

  final double perImageMb = width * height * 4 / (1024 * 1024);
  final double totalMb = perImageMb * count;
  print('图片：单图 ${perImageMb.toStringAsFixed(2)}MB，'
      '$count 张 ${totalMb.toStringAsFixed(2)}MB / 预算 ${budgetMb}MB');
  print('结论：${_verdict(totalMb, budgetMb)}');
}

void _checkWaterfall() {
  final List<_Span> spans = <_Span>[
    const _Span('config', 0, 60, 90),
    const _Span('user', 10, 90, 180),
    const _Span('feed#1', 20, 110, 420),
    const _Span('feed#2', 25, 120, 380),
    const _Span('avatar#1', 200, 80, 330),
    const _Span('avatar#2', 200, 80, 330, cacheHit: true),
  ];
  final int serial =
      spans.fold<int>(0, (int sum, _Span s) => sum + s.durationMs);
  final int critical = spans
      .map((_Span s) => s.endMs)
      .reduce((int a, int b) => a > b ? a : b);
  final int firstByte = spans
      .map((_Span s) => s.startMs + s.ttfbMs)
      .reduce((int a, int b) => a < b ? a : b);
  final int duplicates = _duplicates(spans);
  print('瀑布：串行 ${serial}ms，关键路径 ${critical}ms，'
      'TTFB ${firstByte}ms，重复请求 $duplicates');
}

void _checkFirstScreen() {
  const int firstFrame = 260;
  const int interactive = 540;
  const int frameBudget = 300;
  const int interactiveBudget = 600;
  print('首屏：首帧 ${firstFrame}ms / ${frameBudget}ms，'
      '可交互 ${interactive}ms / ${interactiveBudget}ms');
  print('结论：${_verdict(interactive.toDouble(), interactiveBudget.toDouble())}');
}

void _checkPower() {
  const double screenMinutes = 30;
  const double cpuPercent = 25;
  const double networkMb = 40;
  const double budgetMah = 180;
  final double estimated =
      screenMinutes * (0.6 + cpuPercent / 100 * 0.9) + networkMb * 2.4;
  print('功耗：估算 ${estimated.toStringAsFixed(1)}mAh / '
      '预算 ${budgetMah.toStringAsFixed(0)}mAh');
  print('结论：${_verdict(estimated, budgetMah)}');
}

void _checkRegression() {
  const Map<String, double> baseline = <String, double>{
    '首帧': 210,
    'TTFB': 90,
    '解码': 42,
  };
  const Map<String, double> current = <String, double>{
    '首帧': 236,
    'TTFB': 112,
    '解码': 39,
  };
  const double tolerance = 10;
  for (final String key in baseline.keys) {
    final double delta = (current[key]! - baseline[key]!) / baseline[key]! * 100;
    print('回归：$key ${baseline[key]} → ${current[key]} '
        '(${delta.toStringAsFixed(1)}%) '
        '${delta <= tolerance ? '通过' : '失败'}');
  }
}

String _verdict(double value, double budget) {
  if (value <= budget) return '达标';
  if (value <= budget * 1.2) return '接近上限';
  return '超出预算';
}

int _duplicates(List<_Span> spans) {
  final Map<String, int> counts = <String, int>{};
  for (final _Span span in spans) {
    final String key = span.name.split('#').first;
    counts[key] = (counts[key] ?? 0) + 1;
  }
  return counts.values
      .fold<int>(0, (int sum, int count) => sum + (count > 1 ? count - 1 : 0));
}

class _Span {
  const _Span(
    this.name,
    this.startMs,
    this.ttfbMs,
    this.endMs, {
    this.cacheHit = false,
  });

  final String name;
  final int startMs;
  final int ttfbMs;
  final int endMs;
  final bool cacheHit;

  int get durationMs => endMs - startMs;
}

它不依赖 Flutter 引擎，适合直接作为 CI 里的预算校验脚本原型。

常见坑 ​

  1. 用文件大小估算内存：解码后内存按像素算，和压缩率无关。
  2. 只看单次采样：一次快不代表稳定，必须看 P90。
  3. 在 debug 模式下测解码：JIT 与断言把耗时放大，结论不可用。
  4. 忽略目标尺寸：3x 屏按物理像素解码，内存可能是逻辑尺寸的 9 倍。
  5. 把总和当关键路径：首屏可交互由最晚结束的请求决定。
  6. 盲目提高并发：连接数、解码线程与服务端排队都会让并行退化。
  7. 重复请求未去重：同一资源并发请求两次，带宽与解码都翻倍。
  8. 骨架屏等网络：骨架没有让内容更早出现，只是换了颜色。
  9. 首帧与首内容混为一谈：引擎出帧不代表用户能看到内容。
  10. 冷启动与热启动混在一起统计：两者的瓶颈完全不同。
  11. deferred 组件没有记录可交互时刻：加载完成不等于功能可用。
  12. 闪屏只看日志：衔接问题需要逐帧录屏核对。
  13. 功耗预算用绝对 mAh 下结论：模型只能做相对比较，真实续航要真机。
  14. 温控 critical 仍按 nominal 预算：降频后原预算失效。
  15. 回归容差随意放大：没有理由的放宽会让门禁失去意义。
  16. 只测高端机：低端机的解码与内存问题会被掩盖。

课后练习 ​

  1. 把你的首页图片按「解码后内存」列一张表，标出超预算的图。
  2. 用 instantiateImageCodec 写一个解码 P90 采样器，区分冷/热缓存。
  3. 对比同一张图的 JPEG / WebP / PNG 三种格式的解码耗时与内存。
  4. 画一张真实首页的请求瀑布图，标出关键路径。
  5. 把首屏非关键请求延后，量化首屏指标变化。
  6. 给关键请求加超时与降级，验证骨架屏到内容的切换。
  7. 用 FrameTiming 记录首帧，冷启动与热启动各 10 次。
  8. 给 deferred 组件打三个 trace：加载开始、完成、首次可交互。
  9. 录屏核对闪屏与 Flutter 首帧的衔接，找出空白帧。
  10. 用 Android Battery Historian / Perfetto 记录一次前台操作。
